# 怎么选召回策略

[English](recall-strategies.md) | **简体中文**

每个问题都走同样的两步：检索从索引里取出候选，一次模型调用写出回答。`evidence_strategy` 决定的
只是中间那一件事——有没有人来挑选答案能看见哪些候选，以及由谁来挑。答案有三种，抽象地比没有优劣：
它们在延迟、输入成本与精度之间互相交换，哪一种合适，取决于你的用户在等什么。

这份指南写给替业务做这个决定的人。它说清每种策略到底做了什么、取舍究竟落在哪里，最后落到一张
决策表。三种策略都是**快速车道内部**的选择；深度车道与它们并列，下面有它自己的一节。逐项设置的说明在
[reference/configuration.zh-CN.md](../reference/configuration.zh-CN.md)；
如果回答已经出错、你在找是哪一层丢了事实，那是另一个问题，请读
[recall-quality.zh-CN.md](recall-quality.zh-CN.md)。

## 三种策略

**`ranked`——取头部。** 检索按相关度返回候选，这条路径取每个证据面的头部（`claim_cap` 条断言、
`episode_summary_cap` 条 episode 摘要、`window_cap` 个逐字窗口）交给回答。每个问题一次模型调用。
除了检索分数，没有任何东西评判这一刀切在哪里。提示词最短、延迟最低，失败形态是：某个事实排在第 41
位被检索到了，却从没被展示。

**`select`——花一次调用来挑。** 宽候选池交给一次额外的结构化模型调用，它只返回**坐标**——哪些断言、
哪些 episode 摘要、哪些窗口、哪些正本文档。框架会验证它返回的每个下标，并入一小段确定性的高排名
安全头部（于是一次糟糕的选择也不会产生空上下文），执行最终上限，再把选中的断言追回有界的逐字原文。
每个问题两次模型调用，而且是串行的：这次选择调用位于检索与回答之间，它的延迟是叠加的，不是重叠的。
一旦超时或 provider 失败，这条路径回落到与 `ranked` 完全一致的上下文，并把回答标记为 degraded——
它从不凭空编一个选择出来。唯一不放软的是出处：把选中的断言追回一份 L0 拿不出的来源时，请求直接
失败，而不是拿一份还原不出的证据去作答。

**`all`——把这次选择取消掉。** `select` 本该评判的那个池整体进入回答：没有选择调用，也不按名次截断。
每个问题一次模型调用，提示词长得多。有两件上限表没有明说的事：`all` 读的是 `claim_candidate_cap`
（那个宽的数），不是 `claim_cap`；它取**全部**检索到的窗口，而不是其中 `window_cap` 个；它也从不重排。
它唯一的边界是 `all_context_chars`：超过这个上限，先丢窗口，再丢 episode 摘要，最后丢排名最低的断言，
并在回答的 telemetry 里说明丢了什么。它买下的是「材料检索到了却没被选中」这类失败；付出的是输入
token 和回答模型的注意力。

## 每种策略各花几次调用

```
                        检索（只走索引，不调模型）
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
     ranked                          select                            all
        │                               │                               │
   取排名头部                  在宽候选池上做一次选择调用          整池交给回答
   claim_cap /                 它只返回坐标，随后由框架            claim_candidate_cap
   episode_summary_cap /       验证下标并并入安全锚点              条断言、全部窗口、
   window_cap                          │                          加宽后的 episode 集
        │                               │                                │
        │                               │                  all_context_chars 依次裁剪
        │                               │                  窗口 → episode → 最低排名断言
        │                               │                  并且说明裁了什么
        └───────────────────────────────┼───────────────────────────────┘
                                        ▼
                                  一次回答调用
                      （answer_format: structured 下，`all` 会先写一个有界的
                        `deliberation` 字段——那次没有 selector 来做的证据审视，
                        发生在同一次调用内部）
```

## 顺带的几个旋钮

- **`deliberation` 不是一个设置项。** 当 `evidence_strategy: all` 遇上 `answer_format:
  structured` 时它自己就打开了。结构化 schema 会以一个有界字段开头，模型在**定稿之前**先写它：
  点名交过来的哪些材料与问题相关，其余一口气打发掉。它不多花任何一次调用——它只是同一次调用里排在
  回答前面的一个字段——并以 `deliberation` 回传，从不进入系统消息。当评审必须看见「证据为什么被采纳
  或被忽略」时用它。
- **`answer_reasoning_effort`** 是只绑定在最终回答调用上的 provider 提示。留空则什么都不发送，请求
  与没有这个旋钮时逐字节一致，用 provider 自己的默认。改它需要重启。
- **`selection_reasoning_effort`** 是同一个提示，只绑定在 `select` 调用上，别的策略不读它。热生效。
- **`all_context_chars`** 是 `all` 唯一的边界，别的策略不读。`0` 表示关掉上限，不是「全部丢弃」。
- **候选上限与最终上限。** `claim_candidate_cap` / `window_candidate_cap` 是索引深度——很便宜，也是
  「所需证据根本不在池里」时该放大的那一个。`claim_cap` / `episode_summary_cap` / `window_cap` 约束
  最终提示词——当池是对的、而上下文把回答需要的东西丢掉了，才放大它们。候选上限太小却去放大最终上限，
  只会把提示词撑大，不会把那个事实加进来。

## 取舍究竟落在哪里

延迟并不按调用次数排序。`select` 花掉的那次串行选择调用，可能比 `all` 更长的提示词还费墙钟时间，
所以 `all` 未必就是慢的那条；而正因为不做选择，它让回答站在好几份文档的证据上，而不是一份。
`select` 换回来的是一份更窄、经过刻意挑选的证据集——当回答要被逐条审计时你要的正是这个，当读者
还需要第二、第三份文档时你要的恰恰不是它。`deliberation` 多花一些输出 token 和一点时间，换回一段
可读的证据审视。`answer_reasoning_effort` 并不单调：把它当成一个需要验证的变量，而不是一个该往上
拧的旋钮。

上面这一段里不该出现任何数字：延迟与成本是你的 provider、你的提示词长度、你的库的属性，别处测出
的数迁移不过来。本仓库里唯一被实测过的产物是
[`examples/opc/build-record/eval/`](../../examples/opc/build-record/eval/)，那里的每一条线都记着自己
的测量装置、日期，以及哪两条线之间可比；在定下一种策略之前，用同样的方式测你自己的。

## 与它们并列的：深度车道

三种策略都是**快速车道内部**的选择，而快速车道是本框架出厂的两条车道之一。这两条是检索的两种典型
形态，各实现一次，好让一个项目从一份能跑的参照物出发，而不是从空文件出发——`evidence_strategy` 只
到得了第一条，传给第二条会被拒绝而不是被忽略（API 返回 400，生成项目的 CLI 直接退出）。

**快速车道**是多路检索加一次作答：在编译后的断言面和原文面上分别做词法与向量检索，用 RRF 融合，再
加上已启用索引组件贡献的路由路径，由 `evidence_strategy` 决定这个池子里哪些进入回答。**深度车道**是
在同样这些证据面上的一个智能体循环：它从快速车道本来会据以作答的那份证据开场，外加一份库的
glance，然后换角度重搜任一证据面、列出并整篇读正典文档、顺着文档里的 markdown 链接走、取回逐字
片段。这个循环是有界的——工具预算和逐次调用的轨迹记录都是机械的——最后以作答收场。

两条车道背后是同一套保证：每条结论都带引用，引用走网关与投影共用的那一套寻址，不该留痕的调用者
一点痕迹都不留，每个回答都交代自己花了什么。

它们在机制上有两处不同。**成本：** 快速车道是一次模型调用（`select` 下是两次），提示词多大能从上限
推出来；深度车道是事先没人知道的调用次数，因为循环自己决定需要几次，于是延迟与 token 开销逐题浮
动，不再守着一个近似常数。**够得到的范围：** 一次作答只能在那一次检索返回的东西上作答，而循环走得
动——整篇读到的正典文档带着它的链接，顺着走一条，无非是再读一篇。所以任何一段被检索到的原文都没有
直说的事实——跨文档的连接、跨多份来源的计数——不是检索深度问题：放大候选上限只是让这一次看得更宽，
并不会把回答挪到相邻的那份文档上。

两者之间怎么路由，是应用自己的事。逐题路由、始终只用一条、两条都摆给读者、用你自己的车道替换其中
任何一条——框架把这些全都托得住，也不把任何一种当作教条。这两条车道是什么？是你衡量自己那套安排时
的基线；而每个回答都会交代的那行成本，是让这份衡量属于你自己、而不是借自别人语料的东西。

## 决策表

| 如果这个库服务于…… | 就设 | 因为 |
|---|---|---|
| 交互式助手，等待时间本身就是产品的一部分 | `evidence_strategy: all` | 没有串行的选择调用，等的就是一次作答调用——代价付在输入 token 上 |
| 审计、合规，或者任何「一份窄而刻意的证据集比覆盖面更重要」的阅读 | `evidence_strategy: select` | 那次选择调用是在回答看到证据之前的第二次审视，且失败时软回落到 `ranked` |
| 高频、要最便宜的一问 | `evidence_strategy: ranked` | 一次调用、最短的提示词、不加宽候选池——它是其余一切的比较基线 |
| 必须看见证据**为什么**被采纳或忽略的评审 | `all` + `answer_format: structured` | 这个组合会打开 `deliberation`：同一次调用里，答案之前的一个字段 |
| 需要干净答案字符串加一份独立验证的引用账本的下游自动化 | `answer_format: structured` | 与策略无关；自动化消费 `answer_text`，界面渲染 `answer` |

至于上限，只有一条规则：**池里没有这个事实就放大候选上限，池里有而上下文丢了它才放大最终上限。**
在 `all` 下，能加宽断言池的那个数是 `claim_candidate_cap` 而不是 `claim_cap`，窗口面本来就没有上限
——所以那里真正起作用的旋钮是 `all_context_chars`，它决定这些东西能活下来多少。

这份指南不改任何默认值。框架出厂是 `evidence_strategy: ranked` 加 `answer_format: text`，生成的引擎
写的也是同一套，而 OPC 示例的默认仍然是 `select`——`all` 配 `deliberation` 是针对某类负载的刻意选择，不是新的基线。两项设置也都可以针对单次提问覆盖（recall 请求体里的
`evidence_strategy` / `answer_format`，或生成项目 CLI 上的 `--evidence-strategy` / `--answer-format`），
那是在改动任何东西之前、用你自己的材料比较它们的最便宜方式。
