# 知识库的形状——写入钩子、质检与结构透镜

[English](structure-lens.md) | **简体中文**

## 1. 为什么，以及定下形状的那条裁定

Steward 在库内工作，一次一份源。每一次编译都是契约之下的一个局部决定，而每一个决定都可以是对的，总和却在漂移：一个项目页悄悄被会话叙述填满、一个演进页的带日期小节按摄入顺序而不是按时间到来、一个散落的标题把一页改了名、一个主题以两种写法存在两次、一族页面没有任何东西链接向它。这些没有一个是捏造——每条 claim 仍然引用着它的区间。问题在于谁看得见其中的哪一个，而这个问题把它们分成三层：

- **写入本身就能判定的**，不需要任何人。claim 块里的一个标题、没有真实换行的正文、与兄弟页相同的标题、一个乱序追加的带日期小节：毛病完整地摆在正被写下的字节里，于是机制在写入处拒绝它或把它归正，任何读者都不会碰到它。这是框架的第一条纪律——机制先于劝说——施加在这座库的形状上。**第一层：写入钩子**（§2）。
- **库内的人照着单子查就能发现的**，要的是一张清单，不是一个外部视角。一页二十次点名另一个主题却从不链接它、一个演进页的转折点不引用任何 decision、一个枢纽让自己的三页无人可达：站在这一页上的 Steward 对着契约就能看见它，也能在属于它自己的一轮里修好它。这是这座库的反思。**第二层：质检**（§3）。
- **只有整体才显现的**，是这座库正在变成什么：它作为一个整体是否走得通、知识在哪里堆积、其中多少是会话日志而不是关于主题的知识、它是否会自我纠正、它所积累的知识蕴含的结构是否已经存在、以及它持有的是不是人们问它的。没有任何一页显现得出这些。**第三层：结构透镜**（§4）。

裁定：**一条发现属于看得见它的最低那一层。**第一层的毛病绝不是一条质检项，也绝不是一条透镜读数；一条质检项绝不是一条透镜读数。留给透镜的，是那些非要俯瞰全局不可的读数——它本来就是干这个的。

三层里的一切都是派生的、无模型的：从正本算出（有一条透镜读数还用到被保留的咨询记录），不向正本写任何东西。

## 2. 第一层——写入钩子

每个钩子都是 core `compile/` 里的一条闸门检查或一次工具面拒绝，不论本文其余部分是否部署，它都生效。**拒绝**意为这次写入带着一条点名的违规返回；**归正**意为机制确定性地安放这些字节，模型根本不必知道这条规则。

| 钩子 | 位置 | 内容 |
|---|---|---|
| `heading_in_block` | 工具面 + 闸门 | `append_block`、`edit_claim`、`supersede_claim` 或某个总览 slot 里一行以 `# ` 开头，被拒绝；`create_document` 只在 `# ` 是正文第一个非空行时接受它 |
| `escaped_newlines` / `long_line` | 工具面 | 带着字面 `\n` 却没有真实换行的文字，或任何 ≥ 1 000 字符的行，被拒绝 |
| 打头的标题 | 序列化 | `derived_title` 只读打头的那个 `# `；一份已结卷按它所属的页面标注（`<owner> · vol. NN`）；`title:` 以 YAML 引号写出 |
| `title_sibling_collision` | 闸门 | 与同一目录下另一个活页面相同的标题，被拒绝 |
| `title_degenerate` | 闸门 | 标题为空、只等于一个族角色词（`overview`、`evolution`、`概览`、`演进`、`项目演进`……）、或在非枢纽页上等于项目 slug，被拒绝 |
| `title_shared_with_hub` | 闸门 | 一个编年页（`evolution.md`）的标题与它的枢纽（`overview.md`）逐字相同，被拒绝 |
| 编年顺序 | 归正 | 在编年页上以 `YYYY-MM-DD` 标题 `append_block`，落进该日期已有的那一节，或按它的时间位置新开一节；锚点不动。`reorder_chronology(path)` 是给这条规则之前就存在的页面用的机械写入动词（锚点与字节守恒，只移动小节顺序） |
| `overview_restates` | 闸门 | 一个总览块的文字剥掉引用与锚点之后，与同一页的某条账本 claim 相同，被拒绝——改为引用那条 claim |
| `definition_empty` | 闸门 | 一个没有散文的 `definition` 块（只有引用与锚点），被拒绝 |
| `retitle` | 写入动词 | 改写打头的那个 `# `（没有时插入一行），于是一个取错了名字的页面不必碰任何一条 claim 就能被改名；它过遮蔽标题与兄弟标题两道检查 |

族角色（枢纽、编年、子族、Owner 视图、记忆）按名字从生效的 `path_templates` 读出——core `shape/families.py` 里的一张表，三层共用，不是散文。

延后到一份声明结构的契约：*在一个项目的子族下创建的页面，必须在同一轮里被这个项目的枢纽链接。*闸门今天就能拒绝它，但「枢纽链接自己的子页」是 personal-projects 契约的期待，不是框架的，而一份契约以散文陈述它的期待。当一个 path template 能够携带 `hub: overview.md` 时，这条规则就成为一个钩子；在那之前它是一条质检项（§3）。

## 3. 第二层——质检

### 3.1 它列出什么

质检是一份 Steward 可以据以动手的页面级发现清单，每条带着页面、逐字的证据、它的代价与该做什么。两种条目：

- **判断项**——契约的那些期待，没有钩子判定得了：

| id | 谓词 | 证据 |
|---|---|---|
| `nav.hub_incomplete` | 一个枢纽没有链接到自己子树里的每一页 | 缺失的那些目标 |
| `nav.chronology_unlinked` | 一个有 ≥ 3 个带日期小节的编年页，在自己项目确实有 feature 或 decision 页面时，却不链接其中任何一个 | 那些子页 |
| `nav.decision_unlinked` | 一个没有出向链接的 decision 页 | — |
| `nav.mention_unlinked` | 一页的 claim 正文 ≥ 3 次点名另一个活主题的确切标题（≥ 4 字符，且不是自己的），却从不链接它 | 那个标题 |
| `nav.dead_link` | 一条指向没有任何文档占着的路径的链接 | 那个 href |
| `id.title_duplicate` | 两个活主题在不同目录下有相同的归一化标题 | 那个标题 |
| `corr.single_source` | 一个有 ≥ 8 条 claim、且全部引用同一个源的主题 | 那个 source id |
| `form.legacy_sections` | 一页有总览头，下面却仍然带着 `## definition\|summary\|introduction\|connections` 小节 | 那些小节 |

- **第一层毛病的遗留实例**——在钩子存在之前写下的页面：一个散落的标题、一段塌掉的正文、一个退化的、与枢纽同名的或与子页撞名的标题、一个乱序的编年、一个复述 claim 的总览块、一个空的 definition、一行带着引用却没有锚点的字。钩子把新的挡在外面，质检把旧的连同修复各自的那个动词一起列出来（`retitle`、`reorder_chronology`、一次普通的编辑）。

发现的形状见 §5.1；每一句话都从提示词目录在两种语言包下渲染。

### 3.2 反思回合

质检以**属于它自己的一轮**到达 Steward，绝不作为另一个作业任务里的一条 note。一个 `review` 作业（canonical lane，与 `groom`、`challenge` 同列）在整座库上开一份不带任何源的草稿：它的任务就是这座库的质检报告，它的指令是修好一轮修得了的东西——链接、标题、顺序、编辑——经由普通的草稿动词，在普通的闸门之下，并在 brief 里说出它留下了什么、为什么。它由 Owner 入队（`pkc jobs enqueue review`，或控制台），本版里没有别的东西入队；给它排期是之后的决定。

既没有修好任何一条发现、也没有说出为什么不修的一轮，是**未完成，而不是 ok**：finish 拒绝它
（`review_incomplete`），作业以 `ok=false` 记下，harness 自己说的话留在行上，并按 harness 崩掉时
同一个上限重新入队——因为一座库最不该被告知的，就是它被一个什么也交代不出的回合「自查过了」。
什么都没修但说清了为什么，是完成的一轮；质检读下来没有可修之处的库上的那一轮也是，它的任务里
写的就是这件事。

这是库内人的反思：Steward 对着契约读自己的库，并改正它。它不往任何别的作业的上下文里放任何东西。

### 3.3 各个面

- `GET /v1/users/{uid}/review?at=<ref>` 与 `pkc library review [--path] [--at] [--json]`——那份报告；`--json` 从不分页。
- 控制台里的 `#/review`：按页面列出的那些发现——透镜从前展示的就是这一行行条目——以及最近一次反思回合的 brief。

## 4. 第三层——结构透镜

### 4.1 它读什么

一个 ref 上的每一份正本文档、生效的 path templates，以及——为了一个维度——被保留的咨询记录与 attention 组件的访问账本，在它们存在时。主题、边与 claim 只算一次，由共用的 `shape/` 模块算出，质检与透镜的算法完全相同（一卷折回它所属的页面；一条边是某个 claim 块内或总览区域内的一个 markdown 链接，经由闸门那个解析器；一条 claim 是账本里的一个锚点，总览块不算）。

### 4.2 六个维度

透镜不列页面。它沿六个维度读这座库，并为每一个说出：它看见什么、这意味着什么、以及自上一次读数以来它怎么动的。每个维度有一小组指标、一个由具名阈值选出的**档位**、每个档位一句渲染好的**陈述**，以及一个**方向**——这次读数对契约或对 evolve 意味着什么——和每一句话一样从目录渲染。

| id | 问题 | 指标 | 档位阈值 |
|---|---|---|---|
| `walkability` | 一个读者能不能走通这座库，还是只能按名字查？ | 每主题的边数；死路占比；无人抵达占比；处在最大连通分量里的主题占比；孤岛（没有任何边通向或来自外部的项目） | open：死路 ≤ 15 % 且无人抵达 ≤ 15 %；thin：两者任一 ≤ 40 %；broken：其余 |
| `shape` | 知识在哪里堆积？ | 领先主题的份额与领先倍数；每个族的 claim 份额对它的页面份额；声明了却空着的族；簇的数量 | even：领先 ≤ 10 %，且没有族 ≥ 它页面份额的 2 倍；leaning：领先 ≤ 20 % 或有一个族 ≥ 2 倍；collapsing：其余 |
| `knowledge_vs_log` | 其中多少是关于主题的知识，多少是会话日志？ | 带日期、单源叙述的 claim 占比（会话特征）；叙述 ≥ 60 % 的主题占比；每族的 claim 份额 | knowledge：叙述 ≤ 20 %；mixed：≤ 50 %；log：其余 |
| `liveness` | 这座库会不会自我纠正？ | 自创建以来从未被写过的主题；每 100 条 claim 的 supersede 数；每 100 条 claim 的编辑数；分卷次数；在 ≥ 8 条 claim 之后被改写过的总览数；每个主题距上次写入天数的中位数 | living：supersede ≥ 1 / 100 且未被动过的主题 ≤ 50 %；still：supersede < 0.5 / 100 或未被动过 ≥ 80 %；settling：介于两者之间 |
| `type_structure` | 正在积累的是哪一类知识，它蕴含的结构存在吗？ | 落在任何编年族之外的带日期 claim；落在 decisions 族之外的 decision 形态小节（`decision`/`rationale`/`scope` 标题）；在 ≥ 3 个主题里反复出现、却没有 people 页的人名（在 people 组件已注册时）；有页面的声明族对没有页面的 | aligned：每个代理指标 ≤ 它基数的 5 %；strained：任一 ≤ 20 %；misfiled：任一高于此 |
| `demand_supply` | 它持有的，是不是人们问它的？ | 每族的咨询数对每族的 claim 数；被咨询过的主题对从未被咨询的主题；答复中不带任何引用的咨询（缺口） | 仅在存在咨询记录时读；matched：缺口 ≤ 10 % 且被问得最多的族在它 claim 份额的 2 倍以内；skewed：其余；没有任何咨询时为 `unread` |

这些阈值是透镜模块的常量，只命名一次，控制台不重复它们。一个维度的陈述是写给 Owner 的，用的是一个外部读者的口吻：它看见什么、它会问什么，而不是一份页面清单。`direction` 点名的是杠杆——一条契约条款、一次 evolve、一次 groom、一轮反思回合——绝不是一页。

### 4.3 趋势

一次读数在存在上一次读数时携带它——默认是上一个正本 commit，按需也可以是任意 ref 或冻结快照——每个维度陈述它的移动：哪些指标动了、朝哪个方向动、以及档位是否变了。旧视图那个分数没有了；六个档位与它们的移动就是全部摘要。

### 4.4 透镜与 evolve

`type_structure` 的读数，恰恰是设计哲学要求 evolve 去掂量的那份证据——正在积累的是哪一类知识，而它蕴含的结构并不存在。把它渲染成 `evolve_evidence` 是透镜朝这座库自身流程唯一有意为之的出口，本版不做：它与反思回合的排期一起设计。

### 4.5 各个面

- `GET /v1/users/{uid}/lens?at=<ref>&previous=<ref>` 与 `pkc lens [--at] [--previous] [--json]`——那次读数。
- 控制台里的 `#/lens`：六节，每个维度一节——档位作为一个词、那句陈述、指标连同它们的移动组成的一张小表、那个方向——外加一个为上一次读数选 ref 的选择器。页面上任何地方都没有发现清单；质检有它自己的。

## 5. 数据形状

### 5.1 一条质检发现

```
Finding
  key          "<id>:<path or scope>:<evidence hash>"——同样的证据，同样的 key
  id           §3.1 里的某一个，或第一层某个毛病的遗留 id
  kind         "judgement" | "legacy"
  paths[]      它所关于的那些页面（当前页路径）
  targets[]    牵涉到的其他路径
  evidence[]   只来自库里的逐字字符串（一条路径、一个标题、一个小节标题、一个
               日期、一个 href、一个 source id）；计数住在字段里
  impact       {key, fields, text: {en, zh}}
  action       {key, fields, text: {en, zh}}   有修复动词时点名它
```

```
CheckReport
  ref, read_at, subjects, files, claims, edges
  findings[]   顺序：legacy 在前（一个钩子毛病是无歧义的），然后 judgement；
               同一 kind 内按 id，再按路径
```

### 5.2 一次透镜读数

```
LensReading
  ref, read_at, previous_ref
  subjects, files, claims, edges
  dimensions[]
    id            §4.2 里的某一个
    band          档位 id
    statement     {key, fields, text: {en, zh}}
    direction     {key, fields, text: {en, zh}}
    metrics[]     {name, value, previous, delta}      没有上一次读数时 previous/delta 为 null
    evidence[]    逐字字符串（领先主题的路径、一座孤岛的目录……）
```

文案走目录：每一句话都是一个带具名字段的提示词目录键，在源头以两种语言包渲染，于是控制台自己不留副本，而一个经由 overlay 缝改写某个键的应用，改变的是每一个读者看到的东西。

## 6. 各个面小结

| 面 | 层 | 读 / 写 |
|---|---|---|
| 闸门 + 工具面（`compile/`） | 一 | 写入时拒绝 / 归正 |
| `pkc draft retitle`、`pkc draft reorder-chronology` | 一 | 修复动词 |
| `GET /review`、`pkc library review`、`#/review` | 二 | 读 |
| `review` 作业、`pkc jobs enqueue review` | 二 | Steward 自己的一轮 |
| `GET /lens`、`pkc lens`、`#/lens` | 三 | 读 |

不注册任何组件，不往任何编译任务里放 note，不为一条发现在闸门上设任何规则。`#/graph` 重定向到 `#/lens`；`#/graph/node/<id>` 仍然解析到它的文档。

## 7. 怎么衡量它

对一座固定的库，质检与透镜在同一个 ref 下逐字节稳定；评估集的 D 组（`navigability.reachability`）与 `walkability` 的指标按构造一致（共用那个解析器、共用那条卷规则）。反思回合是否改善了质检所列出的东西，按任何质量主张的衡量方式衡量——同一座库，回合前后各读一次——这里不作主张。

## 8. 下一步（本版不做）

- 按排期跑的反思回合，或每 N 次编译跑一轮，等它的无人值守行为在一座真实的库上被看过之后。
- `type_structure` 作为 `evolve_evidence`。
- 一条给结构性期待用的契约缝（path template 上的 `hub:`），它把「枢纽链接自己的子页」那条质检项变成一个钩子。
- people 组件未注册时，`type_structure` 的人名代理指标。
