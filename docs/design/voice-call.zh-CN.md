# 和知识库交谈

[English](voice-call.md) | **简体中文**

## 1. 原本希望的体验

Owner 应当能像与一位会查阅知识库的同事交谈：提问、补充条件、纠正名字、打断回答，再沿着实际说过的话追问。
成功意味着答案切题、有依据，而且以适合对话的节奏交付。仅把麦克风接在一连串独立的文本查询前面，还做不到这一点。

证据是后台支撑，不是口头体验的中心：Owner 不必听引用或查看卡片才能继续交谈。已有仍有效的结果能支持概括、
解释时，语音可直接回应；事实缺失或变化时才重新查。保留不确定性、否定和适用范围，比念出来源重要。
多记录问题仍需要后台综合，但无需额外调用模型仅把简短结果改写成口语；召回负责综合，Live 负责自然表达。

分别衡量三个结果：是否理解了问题、是否从正确证据得出了答案、是否在对话中讲清楚。
更快的一声应承不等于更快的答案；后端生成完毕也不代表 Owner 已经听到了。
通话只读，不执行编译、草稿写入、Owner 陈述或来源入库。

## 2. 分工与官方建议

GPT-Live 是与用户交谈的图书管理员，负责澄清、接话、节奏、打断及后续表达。
委派后端是知识检索助手，只接收独立子问题，返回事实、证据范围和未解决部分。
它没有完整对话或播放历史，不能判断用户实际听过哪些内容。应用从冻结转写重建子问题、
管理任务版本，这是适配职责，与检索结果综合分开。

GPT-Live 负责全双工交谈；应用维护任务状态并运行知识后端。稳定的语音提示词只承载角色、应声、打断策略、
实际具备的后端能力和明确的委派条件。检索流程与业务规则留在后端。日期、时区等动态信息与稳定指令分开。

依据 OpenAI 的 [Live 指南](https://developers.openai.com/api/docs/guides/live)、
[提示词指南](https://developers.openai.com/api/docs/guides/live-prompting)和
[委派指南](https://developers.openai.com/api/docs/guides/live-delegation)。本次文档工具无法取得用户给出的中文路径的
Markdown，因此读取了对应的官方英文页面。

| 方案 | 判断 |
|---|---|
| Client delegation 接现有召回后端 | 保留。可控制上下文、证据处理和哪些结果进入 Live，复用租户隔离及归档范围。 |
| Responses delegation 配知识查询函数 | 可行，**并非天然绕过闸门或不安全**。它管理对话上下文与后端连接，但在现有问答后端外又加一个编排模型，需要不同的函数结果生命周期；采用前应作端到端比较。 |
| 检索事实直接交给 Live | 对明确的单一事实有用。整段时间范围的庞大结果不适合直接塞入语音模型，相关性判断与综合仍要有人承担。 |
| 每次都先让模型筛选证据 | 适合宽而嘈杂的候选池；对完整的小池，是可以省去的串行等待。 |
| 固定缩小候选条数 | 不作为提速捷径：可能在模型看见之前就删掉唯一相关记录。 |

Client delegation 是控制权选择，不是真实性保证。canonical 写入有来源检查；选中证据会在限额内回查来源。
目前的**文本**答案流仍是模型生成，不是逐句语义验证器。文本里有引用标记，不意味着经过结构化答案路径的引用准入。
Live 会转述，也可能独立发言；引用存在和注入确认都不能证明语义忠实或实际播放。

## 3. 连接与范围

浏览器通过 WebRTC 与供应商直接交换音频；引擎用项目密钥交换 SDP，再连接 sideband 接收转写、委派、结果与用量事件。
浏览器只拿 SDP 答案与标识，不拿凭据。其数据通道只允许关闭、静音和取消静音，供应商拒绝它追加指令。

- `GET /v1/users/{uid}/call`：是否可用及不可用原因。
- `POST /v1/users/{uid}/call`：提交浏览器 SDP，创建通话。
- `WS /v1/users/{uid}/call/{call_id}`：后端卡片、计时、用量、关闭事件；`{"type":"end"}` 请求挂断。

每位 Owner 同时一通；新通话关闭旧通话。空闲、最大时长与失去浏览器连接的限制约束存活时间。
托盘打开浏览器控制台，在适合处理麦克风授权和持续对话的界面通话。

## 4. 对话状态

委派事件只有 ID 与时间，**没有问题文本**。引擎保存双方转写片段及之前的查询、结果。片段不代表回合边界；
双方各自分组，避免一声应承切断另一人的句子。

经过有上限的稳定等待后，在读取词表或调用模型之前冻结转写输入。问题形成读取这份快照、有限的 canonical 页面标题词表、
先前问题与结果，解析指代和纠正；只有有依据时才修正误听名字，也可以返回澄清问题。
辅助调用失败时，目前仍退回 Owner 最后说的话；模糊追问是这种降级方式尚未解决的局限。

### 4.5 通话拼写参考

[Live 提示指南](https://developers.openai.com/api/docs/guides/live-prompting) 建议设置语言、读音和不清楚名字时的澄清，但不保证精确识别。
独立的[转写 API](https://developers.openai.com/api/docs/guides/realtime-transcription#add-transcription-context) 支持 `keywords`，
当前 `gpt-live-1` WebRTC 配置没有该字段。因此使用初始 developer context 放置有界拼写参考，
后端问题解析也读取同一份参考；原始转写仍可能拼错，不伪造一个 ASR API 参数。

预处理独立于拨号，使用部署环境执行：

```sh
uv run python scripts/ops/build_speech_lexicon.py USER --dry-run
uv run python scripts/ops/build_speech_lexicon.py USER --model openrouter:openai/gpt-5.6-luna
```

扫描有效 canonical 标题与全部正文，分段有重叠。Luna 筛选生僻专名、生造词、混合语言词和易错缩写；
高频本身不构成入选理由。词必须逐字出现在该段原文，拉丁词还检查边界；这证明来源出现，不能证明模型判断的易错程度正确。
再经有界的跨页面模型筛选，剔除代码标识和通用概念，按口语用途排列短名单；页面覆盖数只影响已合格生僻名称的优先级，不能让常用词入选；只能从已验证来源的候选词中选择。筛选仍是模型判断，不等于识别测试。
不接受模型编造的别名或读音。明确的 `--confusion 'Lyrra=leera'` 更正仅在标准拼写仍存在于有效页面时使用。

结果按租户哈希写入 `ENGINE_DIR/derived/speech-lexicons/` 的 JSON，记录页面指纹、模型/提示版本、术语、风险及来源页。
无 engine 目录时放在 `canonical_root.parent/derived/speech-lexicons/`，不进入 canonical git。
未变页面复用，变更页面重扫；失败保留旧结果且下次可重试，整份文件原子替换。
编译批次后显式重跑即可；此版不增加定时抽取或 canonical 写入。拨号时排除删除、归档页及当前正文中已不存在的拼写。
无缓存时只用已维护元数据，不回退到全部标题。这是可删除重建的派生数据。

术语随正常编译维护：通过 `create_document`、`set_fields` 或 `rewrite_overview(fields)`，
在同一草稿、同一提交里更新。共享编译契约和工具说明同时覆盖模型与 coding-agent 执行器：
筛选生僻口语词，保留适用项，补新词，没有合适词时明确清空。易错程度和覆盖完整性仍是模型判断，
写入闸门不证明这些质量；这些页面不需要另加后台抽词任务。

```yaml
speech_terms: [{"term": "Lyrra", "confusions": ["leera"]}, "洛芮"]
```

这个结构化字段以单行 JSON（合法 YAML）保存，不沿用其他标量字段的压平规则。
写入入口和最终闸门检查最多 40 项、拼写长度、规范化去重，以及 term 必须逐字存在于正文（含标题）。
confusions 最多 6 项，只用于拥有者明确提供的误听更正。正文改动导致已存词不再出现时，提交前必须修正字段。
事实正文和引用继续通过原有闸门。

新通话直接汇总有效页面的字段并全局去重。字段存在即覆盖该页旧预处理缓存，`[]` 也不会被缓存补回。
尚无字段的历史页暂用已有缓存，待其元数据维护后切换；缓存只是迁移兼容，不是另一份权威词表。
汇总不调用模型，归档页排除；保留原拼写、剔除歧义误听映射，并限制在 80 词、3,000 JSON 字符内。
提交后的字段用于新通话；正在进行的通话保留开场参考。
识别、原始字幕和后端理解应使用同一音频分别测量，词在原文出现或单测通过都不是 ASR 准确率证明。

明确点名主体时，首段先在已加载的 canonical 中解析唯一的规范化标题，再考虑词法索引。
标题身份优先于共享 slug（例如同项目的演进页）；同名歧义留给完整检索。
只有匹配页面中能追溯来源的定义、摘要槽位进入首答候选，模型同时看到页面定位，并在不能回答所问维度时拒答。
已匹配主体但没有可用总览时，不回退到旁支词法记录凑首答；没有匹配主体的问题仍走词法路径。
读取范围及归档过滤保持一致，不做模糊身份猜测，也不把标题命中视作语义准确性的证明。


问题形成后才启动两阶段工作流。已移除按原始转写投机查询的路径，避免两种问题表述各启动一对检索和模型调用。
需要澄清时，两条检索都不启动。

每个供应商委派只认领一次。新委派使旧委派停止继续交付语音；旧任务可完成屏幕卡片。
单纯的语音打断不会自动取消后台任务。本地版本检查也无法撤回供应商已经接受的上下文。

## 5. 同一次委派，两路重叠查找

每个成形的问题都同时启动两路查找，不再按结果大小二选一；此前的小池大小捷径已移除。
两路共享解析后的租户、`as_of`、canonical 文档集与归档规则。这是共享读取上下文，不是覆盖所有索引的事务快照。

```text
独立子问题 ──┬─ 有界先行查找 → 局部记录 + 范围 ──→ Live
             └─ 较广的 fast 召回 → 事实 + 范围 + 限制 → Live
                                             对话决策由 Live 负责
```

**先行查找。** 复用普通 fast 的 evidence-only 模式，不调用 embedding、选路、筛选或回答模型，也不继承证据评分器：
8 条 claim 候选、保留 6 条；3 个原文窗口候选、保留 2 个；不构造语义摘要；在限额内回查来源。
归档过滤与来源跨度检查仍走既有路径。一次结构化调用将首查分为 ready、needs_review 或 no_answer。
ready 必须同时满足主体明确、直接支持所问维度、记录属于主体事实；标题命中也不能让定义代替最新版本答案。
测试说明、引用的问题、界面示例不能作为主体事实。首段只允许从单条记录逐字摘取不超过 300 字符的完整句子，
程序拒绝新写措辞与截断子句，不再自由概括。主体对应、相关性及其他句子中的限定是否必要仍由模型判断，
这些检查不能证明语义蕴含。

候选保留检索范围和引用来源的时间，采用与广查相同的 as_of 和 Owner 时区。
标题命中的概览通过租户隔离 L0 读取补齐日期，缺失日期仍未知。单条完整记录最多 6,000 字节，
候选连同元数据合计最多 4,000 字符，超限整体省略。继续排除 superseded、archived claim。

没有合格首答且广查尚在运行时，通过 `session.thinking.append` 发送固定任务状态，不转发未核实的候选文字。
定时进度不会重复这条通知；只有 ready 事实进入 commentary。静默进度不计首答时间、不占事实预算。
轨迹保存 `first_disposition` 和 `first_reason`，没有新增模型调用轮次。

首段明确标为局部发现，期限为六秒；为空或不能回答时记录 `no_supported_finding`，超时单独记录，
都不取消较广检索。如果较广检索先于首段完成，就取消尚未完成的首路，立即基于完整证据作答，首段为空。
轨迹将此记为 `first_skipped: broader_ready`，不是失败；已经完成的首段仍先于后续回答交付。
返回前会等待所有取消任务清理。这避免完整证据已到却仍等待六秒首路期限，但也可能用更早的完整答案
替代一条即将完成的局部发现。不截断完整记录中的限定；来源可追溯并不能保证记录仍然正确、最新或转述忠实。

**较广检索。** 与首路同时开始，使用部署已有的词法、语义和已启用组件检索面。
它继承部署的证据选择器：配置为 TypeSafe/JEV 时，由该评分器对完整跨检索面候选池做一次筛选，
沿用配置的分数阈值与各检索面的结果上限。JEV 负责选证据；`call` 聊天模型角色仍负责形成问题和综合子问题结果。
跨证据面的筛选仍有五秒超时与显式排名降级；时间组件内部不加入名称包含过滤。
较广证据就绪后，结构化综合只读取所给证据和独立子问题，返回：

- `status`：answered、partial 或 unresolved；
- 最多六条独立可懂的事实，每条携带本轮精确引用地址；
- 证据能证明的主体、日期与覆盖范围；
- 所问但尚未确定的部分，包括“最新版本”只有带日期记录时的时效限制。

结果不再包含 retained/new 分类、先前口播输入或单独的口头脚本。
全部有据的子问题事实都会交给 Live，包括与先行发现重复的事实；Live 根据实际对话决定如何表达。
最终事实放行前，所有引用必须匹配已准入的证据地址；只有来源编号的引用展开为实际跨度，不填补间隙。
这验证地址，不证明语义蕴含，也不证明模型对范围的判断正确。unresolved 使用固定事实说明并剔除推测事实。
卡片保留带引用答案及结构化 `lookup_result`；两阶段用量继续记录，`FastEvidence` 保留检索和筛选用量。


这是复用 fast recall 的固定流程，没有新增自主代理或写入车道。综合调用负责比较记录、解决独立子问题；
没有再额外调用一个模型，仅仅把结果改写为口语。

## 6. 把委派任务的结果流式交给 Live

OpenAI 明确支持对同一个客户端 `delegation_id` 多次发送 `session.commentary.append`。
因此一项委派可以先交付发现，稍后继续更新，不需要新开委派。每次追加最多 500 token。
确认事件表示估计已经注入上下文，不代表播放完毕。

应用跨阶段流式交付的是**已经完成的结果**。后续结构化答案解析、引用地址检查通过后才放行语音更新，
不把尚未验证的 JSON 或 token 片段读出去。一份结果内仍按完整句子交付，引用和显示标记不进入口头内容。
所有追加，包括澄清，都限制在 480 个 UTF-8 字节和 420 个字符以内；过长句子优先在单词边界拆分。
最终结果失败时，缓冲的文本全部不交付。已经注入的内容不能撤回，所以修正必须明确说明改变了什么。

4,000 字符的交付上限可容纳最多六条各 600 字符的事实及一条先行发现，避免遗漏最终限定；单次追加仍遵守原有界限。

进度、澄清、失败不进入 `said`、不占答案预算、不创建结果关联，也不计入首个结果延迟。
一次进度通知不会压掉只支持一次返回的模型答案。首段之后失败时，明确说明进一步核对没完成，前面仍是局部发现。
取消时两路任务都会取消并等待清理；新委派会阻止旧委派任何迟到的语音更新，旧卡片可以继续完成。

证据范围、限制及任务进度通过 `session.thinking.append` 静默交付，先于对应事实；
事实通过 `session.commentary.append` 交付。进度只报告任务仍在处理，不把综合阶段说成仍在搜索，也不规定口播台词。可信控制指令与检索内容分开。
语音提示词要求保留范围、自然接上补充、明确承认修正，避免从头重讲。

## 7. 屏幕与度量

屏幕显示双方字幕，每次委派一张证据卡。`said` 表示交给 Live 的文本，不表示 Owner 听到的文本。
只有结果注入确认进入 `deliveries`，其时间戳可与转写关联。UI 按时间关联卡片只是导航提示，**不是逐句来源验证**。
尤其不能因一句话晚于上次注入，就认定它的全部内容由该结果支持。

分别测量委派到首个有效结果、首个应承、后台总时长与实际可听答案延迟。`elapsed_ms` 测第一份结果交付；
真实说话需检查输出转写与音频。质量与成本、延迟分开评估。

答案尚未完成时，新的主人话语会暂缓回写，经过有界语义判断区分应和、取消和改口。
取消或改口即使没有触发新委派，也阻止旧结果继续发声；判断超过三秒时保守停止旧结果回写，并记录原因。
已经被服务端接受的注入不能撤回。

每张卡片的可展开时间线保留首段、每次追加原文、阶段、event ID、发送/确认/错误状态、改口判定及
同期 Live 输出转写，并支持导出 JSON。`first_sent` 和 `sent_ms` 从后端收到委派开始计时；
确认中的 `start_ms`/`end_ms` 是服务端会话时钟上的估计注入区间。两者都不证明用户已经听到。
同期转写只是时间关联，不构成某次更新导致某句话的因果证明。

真实知识库评估将固定证据重放与匀速 PCM WebSocket 通话分开，分别检查取消、改口、确认和补充。
合成输入与接收的音频不能验证浏览器麦克风权限或物理播放。Live 仍可能转述或重复，小样本不能证明
普遍的质量或速度提升。私人转写只保存在被忽略的 `local/` 目录。

### 2026 年 9 月 18 日后端实验

`pneuma_knowledge_eval.progressive_call.compare` 对三个合成情景各运行两次：局部区域数量扩展为较广清单、
开通日期被后续记录变更、补充更多细节。使用生产环境的证据渲染器（包括 `as_of`）与中文提示词。
模型是当前部署的 `openrouter:openai/gpt-5.6-luna`，关闭推理。六次首段都逐字引用了完整记录；
六次后续更新都选择了预期关系并包含检查的新信息。这些是诊断检查，不是整体语义质量评分。一次首段选择调用耗时 3.773 秒：
不设超时的后端诊断保留它供检查，但实际应用会在 2.5 秒首路截止时跳过。六次中五次选择调用本身在期限内，
真实检索还会消耗同一预算。

首段生成的中位等待 **1.429 秒**，从开始到最终更新 **3.332 秒**；同样已准备好的较广证据，
直接一次性作答的中位等待为 **1.786 秒**。这展示了多一个阶段的成本，不代表端到端提速：
实验不包含检索、ASR、问题形成或音频，目的是检查交付和修正行为。
另有确定性测试证明，较广检索仍被阻塞时，首段确实能先交付。

最初的简化样例缺少实际时间上下文，一次运行编出了具体公历日期。改用生产渲染器与明确时间后，
小样本重跑没有再出现该问题，但不能据此声称模型绝不会编造日期。首阶段的逐字拷贝具有比后续模型综合更强的机械边界。
这些文本后端调用没有实测 Live 语音。

## 8. 验证与剩余工作

确定性测试覆盖进度与结果分离、一次性答案交付、失败流清理、提问快照、展开回答、多字节分块、
两路并发、明确修正、取消清理、旧结果抑制、引用准入，以及保留的租户、归档和来源检查。现有路由与会话测试覆盖所有权、重复委派、新问覆盖旧问和关闭；
这些测试不评价语音自然度。

声称生产对话质量前，应对误听名字、“第二个”、查找中与说话中的纠正、重复与展开、无证据、日期冲突、
宽时间范围问题重复真实通话，保存后台卡片与实际音频，用同一组情景对比旧实现。
Owner 报告的失败应进入此集合。自动播放、跨浏览器 WebRTC、托盘跳转仍是独立的端到端检查。

### 本地部署后的运行修复

口语召回允许 `[cite: s01]` 这样的来源级简写。补充回答现在将它绑定到该来源实际展示、
且存在于类型化证据清单里的精确跨度；结构化输出只提供这些合法引用选项，仍拒绝未知编号和捏造的显式跨度，不把不连续的跨度合并。
先前只接受带段落号的校验会误拒绝普通口语回答格式。

语音召回保留四个原文窗口、三个 episode 摘要，最多回查四个 claim 来源段落和一个 episode 来源段落。
回查地址验证后，超过 6,000 字符的扩展段落整体省略并记录组装降级原因，保留有引用的 claim。
这防止整段代理会话为口语回答额外引入十万字符。这些上限是在覆盖度和延迟之间取舍，
不代表已经证明回答质量更好。前面的合成选择器测量描述的是旧的纯原文首段实现。
