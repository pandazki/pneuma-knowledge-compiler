# 协助用户建立知识库的 agent 指南

[English](AGENT-GUIDE.md) | **简体中文**

引导用户从自己的材料走到能够检查、提问和维护的知识库。用用户的语言一次解释一个检查点，
自己执行已获授权的工作，不要给新手堆一屏命令。主张数量多或编译成功，不足以证明知识库
有用。下面的步骤同时覆盖可运行的环境和对知识含义的检查。

## 1. 先形成预期

读 [README](README.zh-CN.md)，再读覆盖不同来源类型、时间段和主体的代表性材料。
说明你期望知识库保留什么，读者以后会回来查什么、做什么。区分来源中的证据与自己的预期。
知识库可以属于团队、领域或组织，不要为了填表而编造一个个人拥有者的背景。

只有缺失信息会改变重要决策、且不能合理推断时才提问。沿用已有授权，不要给每个可逆步骤
再设一道审批。演示是可选的，应在独立项目运行；开始有用的工作不需要先跑演示、删数据，
也不需要先写完一份完全定制的契约。

**完成检查：** 能说清材料目录、谁会使用知识库，以及两三个值得它帮助查找的问题。
未知的个人资料留空。

### 检查本机前置条件

找到框架目录，以及框架目录之外的新项目路径。验证 Git、`uv`、Docker Compose 和已经
启动的 Docker 引擎：

```bash
git --version
uv --version
docker version
docker compose version
```

生成器需要 Python 3.11+；必要时会通过 `uv` 使用 Python 3.12 重新执行。缺什么就协助
安装什么；Docker 连接不上引擎时先协助启动。真实构建需要 OpenRouter key，不要让用户
把 key 发给你。如果只是先体验，可以用 `scaffold/init.py --demo` 生成独立的无 key 浏览
项目；它是可选项，不是用户建库的前置任务。

**完成检查：** 命令可用，两个目录已明确，用户知道接下来是真实构建还是浏览演示。

## 2. 先保全材料，再谈优化

结构化导出优先使用框架[来源契约](../docs/reference/source-contracts.zh-CN.md)。保留身份、
时间戳、回复/线程关系、媒体，以及标明来源的派生表示，不要压成匿名散文。不支持的导出
格式不能假冒成另一供应商；应明确适配其语义，并记录信息损失。普通笔记可以用 Markdown；
`type: conversation` 只支持有限的说话者行语法，无法忠实保留结构的对话应使用 JSON。

评价编译器之前，先验证来源数量、处理顺序和代表性归一化结果。区分观察时间、事件时间和
导入时间，未知日期、时区和人物保持未知。不相关的租户应隔离。不得存储或发给模型的材料
应在导入前移除，编译准入不会过滤 L0。

**完成检查：** 文件数量和处理顺序可核对，代表性来源归一化后仍保留身份、日期和结构。

## 3. 用现成契约起步，按证据具体化

生成的契约可直接执行，以 `subjects/{slug}.md` 为起点，每个独立演化的主体一页。这是可
调整的基线，不是普适本体。主体的未来用途决定细节价值：项目意味着进展与承诺，决策
意味着理由，事件意味着时间线。值得保留的事实应进入账本，即使概览无需提及。粗略总结
不能替代知识留存。

材料支持具体化时，读[契约指南](../docs/guides/compile-contract.zh-CN.md)，明确：

- 知识库用途与未来使用方式。
- 主体族、分页边界、身份/别名判断，以及对应的 `path_templates`。
- 准入与排除，附领域内的具体例子。
- 权威、归属、不确定性、更正与状态变化的区别，以及时间精度。

不要用工具语法填满契约，也不要重复架构文档。机械机制属于框架，领域判断属于契约。
没有具体的模型提示问题时，保持 prompt overlays 为空。只有存在真正的人物族和带身份
的来源时才启用 `people`，不要把所有主体都绑定到人物组件。

## 4. 运行普通应用，保留回执

### 生成空项目

用户亲自在终端操作时可交互运行 `scaffold/init.py`。agent 执行时，用用户的实际路径
编写 answers 文件，再调用同一个生成器：

```toml
language = "zh"
project_name = "my-kb"
[data]
mode = "path"
path = "/absolute/path/to/material"
```

```bash
./scaffold/init.py --answers /absolute/path/to/answers.toml --target /absolute/path/to/my-kb
```

不写 `[data]` 时，可稍后把材料放进生成项目的 `my-data/`。起始契约可以直接运行；阅读
它和 `engine/engine.yaml`，只根据材料和用途调整有必要的部分。
**完成检查：** 项目已有 `.env`、`engine/`、`app.py`、`start.sh` 和自己的 README。

**谁来编译：API 模型，还是他机器上的编码代理。** answers 文件里一个字段 `compiler`，默认 `"api"`——除非用户主动提起，否则别动它；只有当他说「我更愿意花 Codex / Claude 的订阅，而不是 API 预算」时，才取 `codex` / `claude-code` / `all`。把「变什么、不变什么」直说。

*变的*：谁来跑一轮编译。`api` 时是 `[models].compile` 里的模型读材料、写正本；换成代理，就由他机器上已有的编码代理来跑，生成器会往项目里装一份**技能**来教它。代理的全部词汇从此是 `pkc`——读库的一条命令行、写库的一道门——一次编译于是变成一串用户能看见、也能叫停的小命令。`./start.sh` 通过配置的代理执行编译。关闭无人值守执行时，先用 `ingest` 把材料加入队列，再让 Steward 通过 `pkc` 完成；待处理任务不算构建完成。

*不变的*：密钥这一问（嵌入、检索、问答仍然要密钥，无密钥部署在两种方式下同样是无密钥）、引用、闸门，以及库的形状。同样的材料、同样的契约，产出同一种库；改回去是 `engine/engine.yaml` 里的一行。

具体来说：`compiler = "codex"` 会把 `compile: agent:codex` 写进 `engine/engine.yaml`，装上 `.agents/skills/pkc-steward/`，往项目的 `AGENTS.md` 里拼一个 `pkc:start` 块，并生成 `bin/pkc`。`claude-code` 同理，落在 `.claude/` 下、用 `CLAUDE.md`，旁边还多一个 workflow；`all` 两个都装，于是同一个项目里开哪个代理都行，而由 Codex 负责编译。前提是那个代理已经装在这台机器上并且登录过——答应之前先确认，没有就退回 `api`。

如果契约将拥有者与其他人物区别处理，应先声明这个身份。Steward 项目用 `bin/pkc profile show` 检查，再用 `bin/pkc profile set --field display_name=... --field bio=...` 同步修改文件与持久化记录；无关或未知资料保持留空。

### 让用户亲手填写凭据

请用户在自己的编辑器里打开生成的 `.env`，填写 `OPENROUTER_API_KEY`。密钥绝不经过
对话、agent 编写的含密钥命令或 stdin。不要打印 `.env`，不要把凭据放进 answers 文件。
已有明确授权的秘密存储可供运行时使用，不需要复制到对话。只验证字段是否非空，不返回
它的值；`start.sh` 自带这个检查，会安全提示空字段。

**完成检查：** 凭据保存在本机，没有出现在对话、命令文本或版本库中；用户知道真实构建
会产生模型费用。

### 构建并检查

在生成的项目目录运行：

```bash
./start.sh
./app.py status
./app.py glance
./app.py ask '一个关于材料的实际问题' --sources
./app.py audit
```

`start.sh` 先验证整批输入，再按文件名顺序逐文件导入并处理普通 worker 队列。一个来源 bundle 可能展开为多个自然
来源单元。要分开摄入和处理可用 `ingest`、`compile`；console worker 是另一种队列消费者，
不应和 CLI 编译器同时消费同一队列。

检查 `data/run-reports/`：输入哈希、来源 ID、完整任务历史、未解决失败、engine 文件哈希、
提问时间与降级。重试是新增尝试，不能抹去失败。CLI 每次处理队列会对未解决的 compile
任务追加一轮尝试；反复处理会增加尝试次数。再次处理前先检查反复出现的失败。
compile token 回执只统计该模型，不代表全部模型和 embedding 成本。

`status` 在中间件或知识库不可达时退出 1；退出 0 表示检查成功，仍需查看 pending 和
failed 数量。`audit` 只读检查整库，包括归档和已结卷，报告出处链、来源地址和总览问题，
不修改任何内容；发现问题时退出 1。审计通过不证明语义忠实。未改动的历史缺陷可以出现在
这里，而不阻塞无关编译；新增写入不能制造这样的缺陷，也不能破坏原本有效的依赖。
不要为了让审计变绿而自动取消归档或改写受保护的历史。

**完成检查：** 预期输入已导入、待处理任务已完成、未解决失败有交代；用户已看过主体页，
以及一份能追到引用原文的回答。

## 5. 从三个层次验收

**来源完整性：** 预期材料是否忠实导入，归属、顺序、时间精度和媒体表示是否保留？这里丢了
字段，不是推理能力问题。

**知识忠实度：** 对照原文段落、账本主张与概览，检查具体细节、否定、计划与结果、时间关系、
取代和遗漏。既看漂亮的总结，也看小事实。闸门验证出处地址和结构，不证明原文蕴含主张。
closed volume 是仍被读取的活跃知识；archive 会使材料退出默认检索，两者不是同一操作。

**可用性：** 提出实际问题，检查 `ask --sources`，即使检索传入的是编译主张，也要追到答案
引用的精确 L0 段落。记录回答和证据选择的降级。历史问题应传带时区的 `--as-of`，省略表示
当前时间。scaffold 默认结构化回答，区分答案正文、类型与引用。

canonical 既承载已保留的知识，也提供进入材料的地图。主体页应把相关知识组织在一起，
页面链接让读者沿关系继续阅读，出处链让读者核对原始表述。出现来源地址，不代表回答模型
已经读过这些 block：索引主张、派生摘要和打开的原文段落是不同视图。应检查答案实际收到
了什么，尤其注意会改变意思的限定条件。

默认 `select` 路径先针对问题选证据，再按最终上下文预算截取，并在原文段落数量预算内
回溯所选出处。它需要一次 recall 模型调用，选择失败时退回排序证据并报告降级。
成本或延迟更重要时，对照 `--evidence-strategy ranked`。两条路径都可能漏证据；
这里的改变影响下一次回答，不改变已编译知识。需要继续阅读的问题，
可用 `./app.py ask '…' --deep --sources`：deep 能再次搜索、打开关联页面、抓取原文，
并留下工具轨迹。它的预算有限，仍可能漏读或误读。如果两条路径答案不同，沿证据找到
最早遗漏或误用的事实，不要仅凭哪份回答更完整就接受它。保留已被取代的状态作为历史，
并与当前状态区分。

改模型前，先找到最早出错的一层：

| 观察 | 优先检查或修改 |
|---|---|
| 来源缺少事实或身份 | 来源适配与归一化 |
| L0 保留了标题、消息时间或线程，编译输入却没带上 | 来源到编译器的上下文渲染 |
| L0 有信息，但账本遗漏或改写了意思 | 契约、编译轨迹与模型 |
| 账本正确，概览却说得更强 | 概览维护与总结 |
| 正确证据存在，却没传到回答端 | 检索候选、预算与选择 |
| 回答端看到了证据，仍理解错误 | 回答指令与模型 |
| 成功提示掩盖失败任务或非法地址 | 框架实现与报告 |

修改负责的环节后，再次对照来源、生成的知识和回答。

检查来源结构，也检查段落正文。编译器会收到保留的章节路径，以及对齐的消息或片段时间和身份；
IM 的线程标识用于分组，邮件回复标识保留回复关系。这些属于来源上下文，不是新主张。
缺失或无法对齐的元数据不能靠猜补齐。更完整的编译输入影响后续编译；要验证对已有知识的影响，
必须重新编译受影响材料，控制变量时优先在独立空库中进行对照。

## 6. 让改动可维护

策略放在 `engine/` 并提交有意保留的状态，凭据和私人材料不入版本库。改契约只影响未来
编译，不会自动改旧主张。不要把派生重建说成重编译：它从权威数据恢复索引，并回放已保留
的语义切分边界。换 embedding 模型需要兼容维度并重建向量，相同维度不意味着两模型的
向量可以混用。

评估新契约时保留原库，在新项目中构建。需要有意重组时使用 evolution，检查提案 diff，
在用户授权范围内采用；`evolve step` 默认保留草稿。不要把破坏性重置当作日常入门步骤，
也不要用它替代迁移判断。

**最终完成标准：** 用户能找到项目、查看主体和来源、提出问题，并知道下次如何加入材料。
交付材料覆盖情况、代表性忠实度检查、未解决问题和准确命令；仅完成环境配置不算建库完成。
明确要求独立评测时，使用单独的[评测协议](../docs/guides/evaluating-libraries.zh-CN.md)。
