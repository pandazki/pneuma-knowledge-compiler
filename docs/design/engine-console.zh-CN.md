# 引擎目录与引擎控制台

[English](engine-console.md) | **简体中文**

这是引擎目录（框架概念）与引擎控制台（渲染它的界面）的设计权威。`ENGINE_DIR` 的运行时约定见[配置](../reference/configuration.zh-CN.md)；它在系统里的位置见[架构 §11](../architecture.zh-CN.md#11-引擎目录)。

## 为什么要有它

生成项目的策略，此前是因实现的偶然而散落的：模型角色与切块在 `.env`，判断力在 `contract.md`，主人在 `profile.yaml`，还有几个旋钮压根没地方——因为 `app.py` 把它们写死了。这里面没有一处是可检视的，也没有一处是可回退的：一个正在迭代自己知识库的人，回答不了「我这台引擎现在到底被配成了什么样，我上周改了什么」。

引擎目录用构造回答这两个问题：一个目录、一个独立的 git 仓库、每次改动一个提交。控制台再让它可读——把每个文件所配置的那条生命周期画出来，并在每个值旁边标出它的来源与影响半径。

## 裁定 1 —— 构成引擎的一切住在同一个目录

```
engine/                    # 自己的 git 仓库；每次 apply 一个提交
  README.md                # 导览：引擎是什么，每个文件的影响半径
  engine.yaml              # 四个模型角色——质量杠杆本身就是策略
  intake/intake.yaml       # chunk_strategy
  compile/contract.md      # 宪法——一份文档，永不被拆成旋钮
  compile/challenge.yaml   # enabled、max_rounds、max_questions、compensate
  evolve/evolve.yaml       # auto_trigger、trigger_topic_docs、trigger_new_claims、draft_ttl_hours
  recall/recall.yaml       # answer_style、claim_cap、window_cap、plan_queries、rerank_*
  persona/profile.yaml     # 主人档案
  prompts/overlays.yaml    # 目录键 → 替换文案（提示词扩展点）
```

**不在 `engine/` 里的**：`.env`（API key、端口、子网、compose 项目名、框架仓库路径、租户 id）——密钥与基础设施永不进入被版本化的单元。`my-data/`（数据）、`data/`（运行时状态）、`app.py` / `docker-compose.yml` / `start.sh`（机械件）都留在原处。

**文件形状只有一条规则，且到处一样。** 除文档以外，每个阶段文件都是一份**扁平**的 YAML 映射，键就是该阶段的旋钮键——不嵌套、没有针对某个文件的特例、只有一个解析器。`prompts/overlays.yaml` 里放一个 `overlays` 键、它的值是那张映射表，这仍然是同一条规则（一份扁平映射，只是值恰好是映射）。`compile/contract.md` 与 `persona/profile.yaml` 是文档：原始文本，永不作为旋钮解析。

**优先级：进程 env > 引擎文件 > 框架默认。** 显式环境变量优先，好让基准测试可以逐次覆盖任意旋钮而不脏化被版本化的单元；引擎文件是人真正在编辑的、持久的那份真相；哪儿都没设就落到框架默认值——这也正是为什么空的（或不存在的）引擎目录与这个概念出现之前逐字节一致。这条规则在 settings 装配处执行（`get_settings` → `engine_overrides`）：引擎的值只在 `os.environ` 未表态的键上作为 init kwargs 交给 `Settings`，因为在 pydantic-settings 里 init kwargs 高于环境变量。环境变量存在但为空，算环境层的一次表态；而来自 `.env` **文件**的值不是进程 env，排在引擎文件之下。

## 裁定 2 —— 契约是文档，不是旋钮

`compile/contract.md` 在控制台里是一等的文档节点，带版本历史与编辑器，**绝不**是开关或表单。知识建模是判断力，把它装成打勾式配置，是这个项目唯一负担不起的谎：契约教模型在**这个领域里**什么值得被长期记住、该落在哪一页，这是任何表单都表达不了的。合法的「策略选择器」界面是 `prompts/overlays.yaml`——按目录键整段替换文案，建立在既有的覆盖机制之上——加上本来就存在的枚举旋钮（`answer_style`、`chunk_strategy`）。

## 裁定 3 —— 图是导出的，不是画出来的

`engine-schema.json` 是控制台与文档共用的唯一来源。手画的图会腐烂；这一份由 `Settings` 字段元数据加一份手写的阶段地图（`engine/stage_map.py`）生成，作为包内资产入库，并有测试把两者钉在一起。重新生成：

```bash
uv run python scripts/generate_engine_schema.py           # 写入
uv run python scripts/generate_engine_schema.py --check   # 过期则退出码 1
```

五道跳线让这个「钉」是真的。入库的资产必须等于代码导出的结果（默认值一改、阶段一改名，不重新生成就红）。每个 `Settings` 字段必须要么是一个旋钮，要么被列进 `NON_ENGINE_SETTINGS` **并写明它为什么不是**（于是新增策略旋钮会强制作出一次归类决定，而不是悄悄绕过控制台）。每条连边的条件必须指向一个真实存在的布尔旋钮（控制台算不出来的箭头会永远显示为关）。每条访问路线都必须落在 `recall` 上，并且它的闸门必须真实存在——要么是一个布尔旋钮，要么是核心 `IntakePlan` 上的一个真实字段。每个阶段的 `doc` 深链必须能在本仓库里找到对应的文件与标题。

### engine-schema.json（形状已冻结）

```jsonc
{
  "schema_version": 1,
  "stages": [
    {
      "id": "intake",                      // intake | compile | challenge | evolve | recall | models | persona | prompts
      "title": {"en": "...", "zh": "..."},
      "summary": {"en": "...", "zh": "..."},
      "doc": "docs/architecture.md#...",   // 仓库相对深链
      "file": "intake/intake.yaml",        // 引擎相对
      "knobs": [
        {
          "key": "chunk_strategy",          // 引擎文件里的键
          "env": "PNEUMA_KNOWLEDGE_CHUNK_STRATEGY",  // 对应的环境变量（无则为 ""）
          "type": "enum|bool|int|string|document|overlay_map",
          "enum": ["semantic", "sentence", "recursive"],  // 枚举值；对 overlay_map 则是允许的**键**
          "default": "semantic",
          "apply": "hot|restart|future_compiles|derived_rebuild",
          "label": {"en": "...", "zh": "..."},
          "description": {"en": "...", "zh": "..."}
        }
      ]
    }
  ],
  "edges": [                               // 地图要画的流水线箭头
    {"from": "intake", "to": "compile", "label": {"en": "...", "zh": "..."}},
    {"from": "compile", "to": "challenge", "condition": "challenge.enabled", "label": {...}},
    {"from": "challenge", "to": "compile", "condition": "challenge.compensate", "label": {"en": "compensation compile", "zh": "补偿编译"}},
    {"from": "compile", "to": "evolve", "condition": "evolve.auto_trigger", "label": {...}},
    {"from": "compile", "to": "recall", "label": {...}}
  ],
  "access_routes": [                       // 同一份材料保持可达的四层
    {"id": "l0", "from": "intake",  "to": "recall", "title": {...}, "summary": {...}},
    {"id": "l1", "from": "intake",  "to": "recall", "title": {...}, "summary": {...}},
    {"id": "l2", "from": "intake",  "to": "recall", "condition": "intake_plan.semantic_indexing", "title": {...}, "summary": {...}},
    {"id": "l3", "from": "compile", "to": "recall", "condition": "intake_plan.canonical_treatment", "title": {...}, "summary": {...}}
  ]
}
```

关于实现出来的形状，四点说明：

- `models`、`persona`、`prompts` 是没有连边的阶段——它们是配置分组而不是流程节点，渲染成流水线旁边的卡片。五个流程阶段排在前面，顺序与连边一致。
- 覆盖旋钮的 `enum` 装的是框架约 340 个提示词目录键，构建时从核心的 `default_catalog()` 读出。目录本身**就是**模型可见文案的可审计清单；再手工维护一份它的键列表，第一次新增文案面就会腐烂。
- `int` 旋钮即使背后的设置是浮点也仍是整数（`evolve_draft_ttl_hours`）：冻结的类型词表里没有 float，控制台只有整数步进器，而带小数的草案存活时长没有任何用处。
- **`edges` 与 `access_routes` 回答的是两个不同的问题，只有前者的地图是一张错的地图。** `edges` 说的是流水线**对材料做了什么**；`access_routes` 说的是同一份材料之后**怎么还能被取到**——L0 逐字、L1 全文、L2 语义，以及 L3 正本这条编译路线。没有它们的时候，控制台画出来的是 `intake → compile → recall`，而新人读到的就是「材料 → LLM 编译 → 回答」，正好把架构最核心的那个主张（§3：四层并行视图，按问题融合）讲反了。三件事是被断言的，而不是被叙述的：每条路线都落在 `recall` 上，因为「融合发生在回答时」正是它们是并行视图而不是降级链的原因；L0 与 L1 不声明任何条件，因为不变量 I3 让它们无条件可达，而一个提供开关的控制台等于提供了破坏这条不变量的手段；`intake_plan.<field>` 形式的条件必须指向核心 `IntakePlan` 上真实存在的字段——两种闸门被刻意分开写：布尔旋钮是部署级开关，而接收方案是按来源决定的，没有任何设置能覆盖它。

### 生效语义

每一次编辑都要说清自己的影响半径。这是控制台的诚实功能，也就是把不变量 I2 摆到界面文案上：

| 值 | 含义 |
|---|---|
| `hot` | 下一个读引擎文件的进程即生效——不重建、不迁移。在 scaffold 的用法里（CLI 每条命令都重读目录）就是下一条命令；长驻的 API 进程只在启动时读一次 settings，所以在那里等于下次启动 |
| `restart` | API/worker 需要重新接线（模型角色、提示词覆盖） |
| `future_compiles` | 只管未来的编译；正典永不被回溯重写（契约、challenge、evolve、主人档案） |
| `derived_rebuild` | 新材料立刻生效，已有材料要跑 `scripts/ops/rebuild_derived.py`（`chunk_strategy`） |

控制台把 `hot` 的两半都说出来，而不是只说好听的那一半：CLI 每条命令都重读这个目录，长驻的 API / worker 在启动时读一次 settings。而 I2 那句「正典永不被重写」只出现在 `future_compiles` / `derived_rebuild` 旋钮下——只有这两种生效语义真的是在谈已经记录下来的知识；挂在一个模型名下面它不是安心，是噪音，而噪音正是老实话开始没人看的方式。

## 服务 API（已冻结）

根级别，且**按部署划分**：没有 `user_id`，因为引擎是这套安装自己的配置，而不是某个租户的知识，而承载它的 scaffold 本就是单主人的。不变量 I1 不受影响——这些路由触及不到任何用户的数据。除非 `PNEUMA_KNOWLEDGE_ENGINE_DIR` 有值，否则每条路由都是 404，于是没有采用这个概念的部署一点新界面也不会多出来。

- `GET /v1/engine/schema` → 入库的 `engine-schema.json`（阶段、旋钮、`edges`、`access_routes`）
- `GET /v1/engine/state` → `{"files": {"<引擎相对路径>": "<内容>"}, "skipped": {"<引擎相对路径>": "<为什么它不在 files 里>"}, "values": {"<stage>.<key>": 解析值}, "resolution": {"<stage>.<key>": "env|engine|default"}, "version": {"head": "<sha|null>", "dirty": bool}}`
- `GET /v1/engine/file?path=<引擎相对路径>` → `{"path": "<规范路径>", "content": "<内容>"}`——单个文件原样返回，不经任何解析：这是 `/state` 解析不出来时的修复通道。寻址方式与 apply 完全一致（一种规范写法、必须在目录内、不含点文件）；什么都没有时 404
- `GET /v1/engine/history?limit=50` → `[{"sha", "label", "at", "files": ["..."]}]`
- `GET /v1/engine/history/{sha}/files` → `{"sha": "<完整 sha>", "files": {"<引擎相对路径>": "<内容>"}}`——某个版本当时的引擎文件，走 `git show`：不动 HEAD、也不动工作区。这是「我要怎么撤销」的读取一半：恢复就是把某个版本的内容载入草稿、再带标签 apply，所以没有 revert 原语，仓库也仍然只向前走。`sha` 可以是缩写；本仓库没有这个 sha 时返回 **404**，git 自己会求值的版本表达式（`HEAD~1`、`main@{yesterday}`）同样 **404**——这条路由解析的是提交 id，而不是求值 git 的版本语法。清单按与「读取目录」完全相同的寻址规则过滤，所以一个版本永远不会交出 apply 路径会拒收的内容
- `GET /v1/engine/prompts` → `{"surfaces": [{"id", "group", "kind": "assembled|fragments", "title": {en,zh}, "summary": {en,zh}, "note": {en,zh}|null, "segments": [{"key", "label": {en,zh}, "context": {en,zh}|null, "framework_text", "override_text|null", "placeholders": ["cite", …], "shared_with": ["<surface id>", …]}], "assembled_framework", "assembled_effective"}]}`——`kind: "fragments"` 表示这些子句是模型一次收一条的，因此两个组装字符串都是 `""`，每条子句自带说明何时用上的 `context`；当组装出来的字节其实是一份运行时模板、而不是一条最终消息时，`note` 会出现；见下文[提示词工作台](#提示词工作台)
- `POST /v1/engine/prompts/rewrite` 请求体 `{"key", "intent", "locale": "zh|en"}` → `{"draft", "notes"}`——由模型起草的替换文案。**绝不写盘。** 无密钥是 **503**，目录里没有的键是 **400**，模型回复用不了是 **502**
- `POST /v1/engine/apply` 请求体 `{"changes": [{"path": "...", "content": "..."}], "label": "<=60 字符", "expected_head": "<sha|null>"}` → `{"sha": "...", "effects": [{"key": "...", "apply": "..."}]}`。`expected_head` 是这份变更集所基于的 HEAD；不一致返回 **409** 并同时点出两个 sha，因为请求体带的是整份文件，把它应用到别人已经推进过的版本上会无声地把对方回滚掉。`null`（或不传）表示没有前置条件，这正是 CLI 想要的

这些形状背后的行为承诺：

- **`values` / `resolution` 恰好覆盖非文档旋钮。** 文档没有解析后的标量值——它**就是**一个文件，只在 `files` 里出现。值是从一个用解析好的覆盖构造出来的 `Settings` 上读回来的，所以控制台显示的，正是框架会用的，包括每一次类型强转。
- **state 每次请求都重读磁盘**，而不是报告运行进程的 settings：apply 之后文件才是真相，而 `restart` 类旋钮应该显示新值，旁边配一个「待重启」的徽章。
- **effects 是与磁盘现状比出来的**，所以重复 apply 一个没变的文件报告不出任何影响，而一次什么都没改的 apply 不会造出提交（返回当前 HEAD）。
- **git 身份是仓库自己的**（`pneuma-engine <engine@local>`，init 时写进本地 config 并在每次提交时再传一遍），因此一次 apply 从不依赖、也从不记录这台机器的 git 配置。
- **一次 apply 只提交它校验过的那些文件**，按路径提交。`git add -A` 会把开发者随手改的、没跟踪的东西一并卷进来再发给它一个标签；按路径的部分提交让其余一切保持原来的脏，`version()` 也照实说出来。
- **每个部署同时只有一次 apply 在跑。** 前置检查、写入与提交是一段临界区，由一把进程级锁围住：`to_thread` 给每个请求一个自己的线程，那是互斥的反面。
- **控制台是按区域降级，不是整页塌方。** schema、state、history 各自独立加载，于是一个解析不了的引擎文件只让你失去当前值——不会连地图、历史和回到里面的路一起失去。

### 每一条拒绝都是写入时拒绝

校验是完整的，并且发生在写第一个字节之前，所以被拒绝的 apply 会让目录保持原样，控制台也永远不可能把引擎搞成一个它自己读不回来的状态：

| 拒绝什么 | 为什么 |
|---|---|
| 绝对路径、`..`、`\`、NUL | 不存在穿越路径，因为除此之外没有别的地方打开文件 |
| 任何点文件路径段 | `.git` 是仓库自己的事，而开发机上凡是形似秘密的文件都是点文件——拒掉整个类别是机制，按名字列黑名单是永远追不上的游戏 |
| 解析后落在根目录之外的路径 | 挫败目录里被塞进来的符号链接 |
| 形似 API key 的内容 | 与 `scaffold/init.py` 在 answers 文件上拒绝的 `sk-or-…` 是同一个形状，另加更宽的 `sk-…` 家族 |
| 阶段未声明的键 | 框架根本不读的键会永远躺在那里、看上去很生效 |
| 超出旋钮枚举、或类型不对的值 | 就是 `Settings` 稍后会做的那次拒绝，只是提前做 |
| 坏掉的 YAML | 否则控制台下一次 `GET /state` 就是死路 |
| 提示词目录里没有的覆盖键 | 静默空转的覆盖是最坏的结果：框架自己的文案照旧送到模型面前，而部署以为它没有 |
| 丢掉、或凭空多出具名插槽的覆盖 | 丢掉一个 `{slot}` 等于在没人回头重读的文案里，无声地删掉一个框架算出来的值；多出来的那个永远不会被替换，会在提交之后的下一次启动时，以字面花括号的形式送到模型面前 |
| 同一次 apply 里出现两次同一路径，或同一文件的两种写法 | 有歧义——而「一个文件只有一种写法」正是让「校验过的路径」和「写下去的路径」是同一个字符串的东西 |
| 不是文件规范写法的路径（`./x`、`x//y`、`x/`） | 它会解析到真实文件，所以接受它就等于允许校验和写入看的是两个不同的字符串 |
| 超过 512 KiB 引擎文件上限的内容 | 与读取侧同一个上限：控制台读不回来的文件，正是它可能用自己显示的那个空白悄悄覆盖掉的文件 |
| 会让候选目录构造不出 `Settings` 的变更集 | 那道完整的校验：对「磁盘 + 本次变更」跑 `/state` 用的同一套解析，于是「提交完就读不出来」不再可达，而不是一个要一颗旋钮一颗旋钮去追的 bug 类别 |

读取只在一个方向上刻意更宽容：`read_engine_directory` 把过大或无法解码的文件报告在 `skipped` 里而不是失败，这样一个走失的文件不会让整台引擎不可读——而且这个缺口是有名字的，不是静默的，因为一个不在 `files` 里的文件本来和一个空文件长得一模一样。解析则一点也不宽容：坏掉的 YAML 直接抛错，因为一个读不出来的引擎文件绝不能悄悄地等于「用框架默认值」。

## 提示词工作台

覆盖选择器原本是一份约 340 个点分目录键加各自默认文案的清单。每一个键都确实可以覆盖，也每一个都读不懂：一个人看着 `recall.cite.source_level`，说不出它落在哪条提示词里、它前后各是什么，也说不出改写它会同时改掉深度车道和简报会话。裁定又直又对——「太难猜了，用户根本不知道自己在改什么。」

### 那次反转

**覆盖的单位仍然是目录键。** 覆盖机制、文件、生效语义与版本流程一概不动。**理解的单位变成「面」（surface）**：一条组装好的、模型可见的提示词（快速召回的系统契约、编译系统消息、覆盖审计的出题趟），由有序的目录段组成。人浏览的是面，读到的是模型将要收到的那份提示词，然后**就地**覆盖其中一段。

### 两种面：连续提示词，和片段族

不是每一组键都是一条提示词。`source.preamble.*` 是 28 条**条件替代**与词级填充——运行时只挑中一句开头，再往里替换几个填充词。把它们拼起来得到的是 `the ownera conversationThis is…`，而工作台把那个东西当成模型读到的提示词展示了出来。会渲染鬼话的地图比没有地图更糟：它教给新人一件假的事，按这个界面的验收标准，这是最高严重级的缺陷。

所以每个面都声明自己的 `kind`：

| kind | 含义 | `assembled_framework` / `assembled_effective` |
|---|---|---|
| `assembled` | 真有一个组装函数以这个顺序产出这些字节 | 那些字节，渲染两遍 |
| `fragments` | 模型一次只收到其中一条的独立子句——替代式引言、工具面、人类回合的各个分节、闸门的拒绝行 | `""`——没有可组装的东西 |

`kind: assembled` 不能自称，只能挣得：被逐字节 pin 的集合与 `assembled` 集合是同一个集合（见下），所以没人能用组装函数校验的键族就只能按它的本相展示。`render_surface()` 对片段族直接拒绝渲染，这也是那串拼接不可能从别的调用方绕回来的原因。40 个面里，14 个是 assembled，26 个是片段族。

在一个 `assembled` 面内部，段扮演三种角色之一——正是这一点让这份地图覆盖的是「组装」，而不只是罗列键：

| 角色 | 含义 |
|---|---|
| block | 按顺序拼进组装文本，带上它自己的字面粘合 |
| slot | 被替换进兄弟段的某个具名占位符（`recall.spine` 的 `{cite}` / `{close}`）；填充可以嵌套 |
| variant | 列出但不在**这一次**渲染里——部署没选的那两种回答风格、只有提供了档案才出现的主体段、按版本追加的契约条款 |

那些由框架在运行时填入的占位符（来自契约路径家族的 `{templates}`、`{question}`、`{instructions}`）在预览里保持字面，并逐段报告出来，于是工作台可以把它们渲染成 chip，而不是假装知道它们的值。

### `note`：组装面是模板，预览要自己说出来

第一次验证走进 `compile.system`，头顶写着「下面是模型收到的顺序与原貌」，读到的却是没填的 `{templates}`、`{skill_id}`、`{version}`、`{instructions}`，以及一句「本轮没有提供主体档案」的 §2——而引擎目录里明明放着 `persona/profile.yaml`。字节是对的，它上面那句话不对，而且不对的地方正是这个面存在的全部理由。

所以一个面可以带 `note`——一段双语横幅，说清读者眼前是什么：每次调用时框架会代入什么（当时生效的契约、主体档案、本轮日期）、哪一条子句是由旋钮挑出来顶替被渲染的那一条、以及有什么东西是随人类消息单独到达的。`null` 表示组装出来的字节确实就是那条消息，只有那时控制台才可以这么说。14 个组装面里 13 个带 note；`intake.source_guidance` 不带，因为它的字节是被整段插入的。片段族永远不带——它没有可加注的组装文本。

这不靠自觉。note pin 读的是**逐字节 pin 用的同一张字段表**：一个 pin 必须替它补上运行时值的面，按定义就是预览里少了那些值的面；而一个提供了 variant 的面，渲染出来的就是一个分支。两者任一都会要求那段横幅，于是最需要它的那个组装面，正是不带它就交不出去的那一个。

### `context`：模型什么时候会收到这一条

组装提示词里的一个 block，靠它所站的位置就把自己解释清楚了。片段族的子句和 `variant` 没有位置可以替它们说话，所以每一条都带 `context`——一句双语的适用语境，点明模型在什么情形下会收到它（「当接收侧没有给出场景说法时，填开头的 `{scene}`」「当新写的断言没有任何回溯依据时」）。这是机械要求：片段或变体缺了它，测试就红；`context` 只是把标签重说一遍，同样红。共 308 条（280 条片段子句 + 28 个变体），手写——因为「什么时候会用上」恰恰是任何推导都产不出来的东西。

对 assembled 面的 block 与 slot，`context` 是 `null`——这是刻意的，不是漏写：它们上方的组装预览已经回答了这个问题。

### 地图漂移不出代码

`prompts/surfaces.py` 住在**核心包**里、紧挨着它所描述的目录，而且它是机制而非文档——因为有五个测试把它钉在代码上：

- **逐字节 pin**——每个 `assembled` 面，其注册表渲染必须与真正的组装函数逐字节相等（`selector_contract()`、`deep_contract()`、`briefing_contract()`、`live_context_contracts()`、`detail_contract()`、`render_system_contract()`、两个演进契约、覆盖审计的三趟、归档历史卡片、上下文流指引、档案扩写）。契约多一段、少一句、换两段顺序，都会一直红到地图跟着说同一句话为止。
- **kind pin**——被逐字节 pin 的集合与 `assembled` 集合完全相等，双向都查。一个自称是连续提示词却没有 pin 的面，是关于「模型收到什么」的一句未经校验的断言；这个标记是一个承诺，而这条测试就是来收账的。
- **context pin**——片段族的子句和变体一个都不许缺双语适用语境，也不许把标签重说一遍当语境。
- **覆盖率 pin**——每个目录键至少属于一个面。一个没有面的新键，是没人能在工作台里找到的文案，所以它在引入它的那个提交上就红，而不是等到某天有人去找它。
- **note pin**——凡是逐字节 pin 必须替它补上运行时值的组装面，或者自己声明了 variant 的组装面，都必须带 `note`。两个触发条件都是从那张 pin 表读出来的、而不是另抄一遍，所以一份契约一旦长出新的运行时插槽，就在同一个提交上开始欠一段横幅。

面的中英标题与摘要是手写的。段的标签是**推导出来的**：一个键前缀家族配一组双语名字，加上人性化的键尾（`gate.groom.anchor_lost` → "Rollover gate · anchor lost" / 「归档闸门 · anchor lost」），再对真正会被人打开的那些面手工精修。338 条手写标签就是 338 处会腐烂的地方。

生命周期分组，按控制台列出的顺序：`intake`、`compile`、`challenge`、`evolve`、`recall`、`persona`、`skill`、`feedback`、`eval`。

### 解析，以及这个端点刻意不做的两件事

`GET /v1/engine/prompts` 是对**引擎目录磁盘上的覆盖文件**解析的——不是对运行进程已注册的覆盖（进程启动时挂的是当时指给它的那个目录，而工作台必须显示正在被编辑的这一个），也不是对客户端未保存的草稿（草稿留在客户端，走普通的 apply，和控制台其余编辑完全一样）。这里只读覆盖文件，所以别人手改坏的另一个阶段文件只会让 `/state` 失去当前值，不会让工作台失去整张图。

工作台自己的改写提示词刻意**不进目录**。目录是知识**流水线**所吐出文案的清单——是部署要调的那个东西。把这个写作助手编进目录，等于让它能被它本就用来编辑的那张覆盖表覆盖掉，还会让入库的引擎 schema 资产（它的覆盖枚举就是目录的键列表）被每一次措辞微调拖着走。

### 语言包

框架为英文目录提供了一个替代品：一套**中文语言包**（`prompts.lang_zh.chinese_overlay()`），目录里每个键都有译文、具名插槽完全一致。它由 `prompts.language` 旋钮选择（`PNEUMA_KNOWLEDGE_PROMPT_LANGUAGE`，`en` | `zh`，`apply=restart`），并且不是第二套机制——它走的是同一条 overlay 缝，而且**走在最前**：

```
英文目录  →  生效的语言包   →  本部署自己的 overlay
             （即「框架文」）    （即「覆盖」）
```

这个顺序就是全部设计。某人为自己领域写下的文案必须能在语言包之下活下来，而不是被它拿回去。它也是工作台保持诚实的原因：`framework_text` 跟随生效的语言包，因为语言包**之下没有作者，只有框架**。在一个中文引擎里把英文默认值显示为「框架文」，等于把语言包自己的句子呈现成某人的覆盖，于此之上每一处真正的覆盖读起来都成了对模型从未见过的文案做的 diff。`en` 一条 overlay 都不注册，所以英文路径与从前逐字节相同——`prompt_overlay_hash()` 仍是 None，提交尾注不变。

两个机械 pin 把语言包钉在目录上（`tests/test_prompt_lang_zh.py`）：键集合**双向**相等，且每条译文声明的插槽与原文完全一致。「全覆盖」正是要点——只要漏掉一个键，就有一句英文留在一份十千字节的中文契约里，而这恰恰是没人会回头重读一遍提示词去发现的那类事。刻意不译的是**程序**要读、而不是模型要读的东西：`[cite: …]` 标记、JSON locator 形状，以及 eval judge 的 `YES` 判定 token。

**英文是被测量过的基线，语言包不声称与它等价。** 本仓库公布的每一个数字——`recall.close.answer_honestly` 背后 LoCoMo-refined 上的调参、claim 预算的甜区、重排器实测无增益——都是在英文目录上取得的。中文包存在是为了另外两件事：读中文的操作者才真的审得动他的模型收到了什么；中文材料域用自己的语言读指令。它的**跑分等价性未经验证**；这里不主张它更好、更差或一样好。在意这件事的部署应当在自己的 harness 上对着英文基线测一遍——这与本项目对待其他任何质量主张的纪律是同一条。

### AI 改写，以及它为什么不能保存

`POST /v1/engine/prompts/rewrite` 用部署的召回角色模型起草一段替换文案。它拿到的是：这段文案在它所属面里的位置、紧邻前后两段的文本、**按生效语言包给出的**框架原文、当前生效的覆盖、必须保留的插槽契约，以及操作者的意图。它返回 `{draft, notes}` 并且**什么都不写**——草稿回到「草稿 → 复核 → 带标签 apply」这条路，和其他每一次编辑一样，因为一个能自己提交自己措辞的助手，会把没人读过的模型输出放进版本化单元。无密钥的部署会拿到一个说清楚这件事的 503；浏览与编辑照常全量可用，缺的只是这份协助。

**写成哪种语言由语言包决定**——不是由 `locale` 决定（它只说明 `notes` 是写给谁看的），也不是由操作者恰好用什么语言敲下意图决定。第一版是用 `default_catalog()` 取原文、再要求模型「保持原文的语言」，于是在中文引擎下它看到的是英文文案，而它照办了：被要求把一句闸门拒绝说得更直接，它交回来的是「gate 已拒绝 … 使用 claim-level 工具修复」——这条没有插槽，所有检查都过，可以直接 apply。现在提示走生效语言包取原文，并点名了必须存活下来的术语（闸门不写成 gate、断言不写成 claim、正本不写成 canonical、锚点不写成 anchor），同时把根本不属于术语的东西豁免掉——工具名、字段名、枚举值、占位符。英文界面配中文语言包是一个正常组合，这正是一个值从来不可能同时回答这两个问题的原因。

### 插槽闸门

让这整个回路安全的闸门是机械的，并且就长在已有的 apply 校验路径上：**一个覆盖必须声明与原文完全相同的具名插槽集合。** 丢掉一个不是「把措辞变简洁」——那是在没人回头重读的那一层里，删掉一个框架算出来的值。凭空多一个更糟：没有东西会替换它，于是字面花括号会送到模型面前，而且是在提交之后的下一次进程启动时。两者都会被点名拒绝，在写第一个字节之前。

它刻意比 `prompts.override_prompt` 更严——后者容忍子集。那道缝是作者对着默认文案写下的一次库调用；这里是有人凭一个意图填出来的表单，而他从没见过框架原本要往那儿放什么。

## Scaffold 集成

`scaffold/init.py` 生成 `engine/`、`git init` 它并提交 `engine: initial`。它写下的每一个值都是显式声明的，包括与框架默认值相同的那些：这个目录的意义正在于，一个人可以读懂自己的引擎在做什么，而不必先知道框架否则会替他选什么。`evolve.auto_trigger: false` 把 `build_settings` 原先写死的东西说了出来——行为一样，但现在看得见、改得动。

`templates/app.py` 通过框架自己的解析器解析策略，而不是对同一份 YAML 再读一遍，于是 CLI、API 和控制台不可能互相矛盾；它从 `engine/compile/contract.md` 注册契约，在 `engine/persona/profile.yaml` 读写档案，并通过 `override_prompts` 应用 `prompts/overlays.yaml`（没有这一步，那个文件就只是装饰）。注意 `app.py` 会在任何人读之前把 `.env` 装进进程环境，所以放在那里的 `PNEUMA_KNOWLEDGE_*` 策略键会盖过引擎文件——这正是生成的 `.env` 一个策略键都不带的原因。

compose 模板多了一个可选的 `console` profile——它不只是控制台，而是整个浏览层：跑项目自己入口（`server.py` / `worker.py`，因此这个项目的编译契约是注册好的）的框架 API 与编译 worker，加上占一个自己探测出来的端口的 Web 界面。项目目录整体挂到 `/project`，这也是 `PNEUMA_KNOWLEDGE_ENGINE_DIR=/project/engine` 能读写的原因（apply 要写文件并提交）。日常的流水线仍然走 CLI。

`./init.py --demo` 是零交互的入口：它生成一个普通项目，`engine/` 里放 `examples/opc` 的真实契约与主体档案，`prebuilt/` 里放那个项目编好的库，起上面那个 profile，并在**没有 API key** 的情况下把库装载起来（`./app.py restore`，走框架自己的恢复流程）。demo 项目与任何其他生成项目的差别只在它自带的那份载荷——正因如此，它打开的控制台是真的：真的引擎，背后有真的库。

`examples/opc` 刻意保留它自己那份「前引擎时代」的机械件：它是一个已经生成好的项目，带着一座预建的库，重新生成它等于重建那座库。因此它的 api 服务不带引擎目录，它的 Web 镜像用 `VITE_ENGINE_FIXTURES=true` 构建——控制台视图老实地停在 mock fixtures 上。

## 控制台界面

`apps/web` 里的一个顶层视图：由 `stages` + `edges` 画出的流水线地图（条件连边在条件为关时变暗，于是拨动 challenge 开关能看见机器的那一段被接上或断开）、带实时值、来源徽章与生效语义徽章的阶段卡片、作为文档节点带编辑器与历史的契约、提示词工作台，以及「草稿 → 复核影响 → 带标签 apply」的流程，落到一条 git 时间线上。

工作台从 prompts 阶段节点进入，占满整块画布：左侧是按生命周期分组的面列表，中间是组装预览（框架原文 / 含覆盖生效稿可切换，段与段之间有分隔，被覆盖的段染色，占位符渲染成 chip），右侧是段编辑器——人话解释、这段文案被哪些面共享、只读的框架原文、像文档一样需要显式「修改」才进入编辑的覆盖编辑器，以及 AI 改写块。保存累积在既有的引擎草稿里（作为覆盖条目），走标准的复核 → 带标签 apply；版本机制上没有任何新东西。

`fragments` 面用的是另一种中央区：先一句话说明这是按条件选用的片段族、这些子句不会拼成一段文字，然后把子句逐条列出——适用语境、当前语言包下的框架原文、以及下面那条正在生效的覆盖。没有组装预览，也没有框架 / 生效切换，因为这两样在这里都不存在。左栏、覆盖计数与右侧编辑器一切照旧，而编辑器在子句自带 `context` 时优先显示它。
