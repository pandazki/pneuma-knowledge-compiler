# personal-knowledge 领域指引

本参考策略服务于跨项目、协作、研究和运营整理知识的个人。编译目标是以所有者为主体的
**长期、可追溯知识**，并非会话摘要，也不永久保存每一条输入。

每次判断：**这条信息以后是否会用于行动、判断、解释、协作或审计？** 是则进入 canonical，
否则保留在原始来源与检索层。知识类型隐含着将来的使用方式：事件需要时间线，项目需要
持续的进展记录，协作者需要不断补充的往来记录。根据材料推断用途，随材料变化而演进，
将用途依赖的事实作为一等断言记录。起点最容易遗漏：何时开始、最初由谁承担，应像结果
一样认真记录；只有留下起点，才能计算时长和先后关系。

## 1. 高价值含义

优先保留产品假设与定位、架构决策与约束、实验设计与结果、明确承诺与验收条件、用户
反馈及原话、影响发布／现金流／合规的运营事实，以及稳定的工作偏好。问候、重复广播、
未被采纳的建议、背景噪声与短期细节不进入长期知识。

- 正例：“首版明确不做团队权限，因为当前流程不需要” → 记录范围决策及其理由。
- 反例：将“今天感觉不错，多写了两个小时”写入长期知识（没有未来用途的一次性状态）。

## 2. 证据层次

每个结论都区分以下来源：

1. **直接事实**：来源原文或结构化字段直接支持；
2. **观察**：日志、访谈、指标或运行结果；
3. **解释**：所有者或模型对观察的归因；
4. **假设**：仍需实验检验的预测；
5. **决策**：所有者明确接受、会影响后续行动的选择。

owner-dialogue 来源是所有者用自己的话对知识库作出的修正、指令或补充。它对已有断言的
表述是关于该断言的证据：引用这段陈述纠正或替代旧断言，避免在相矛盾的旧断言旁另存
一条。转录、模型摘要、搜索结果与代理输出都只是观察。原话与解释分开；指标携带定义、
样本与范围；模型建议不是决策，代理日志不是完成证明，相关性不写成因果。

模态不会消除出处。本 v2 运行时的原生媒体边界很明确：附在 IM 消息块上的 JPEG、PNG、
WebP、GIF 图片。音频、视频与通用文件尚不是原生输入。编译模型实际以图片内容块收到、
且能通过断言所引 L0 地址取回的受支持原图，可以支持直接观察。模型、数据集或适配器
产生的描述、OCR、转录或搜索词是派生观察，但仍可作为证据：只有这种表示且无反证时，
按它支持的置信程度记录具体观察。来源上下文保留表示标签与已知生产者，不把出处变成
每条断言或简短回答都重复的通用免责声明。歧义、冲突或当前决策需要时再说明区别。
单独的 URL 不是视觉证据，描述也不能冒充直接看图。

- 正例：带机器生成标签的描述说分享的照片有向日葵纹身，且无反证 → 记录“分享的照片被
  描述为向日葵纹身”；简短回答可说“向日葵纹身”，引用仍保留完整证据路径。
- 反例：因只有派生描述就完全不记录纹身，或模型未收到图片却写“图中显示向日葵纹身”。
- 正例：“EXP-014 在 24 个合成任务上的召回率高于纯向量检索” → 作为观察，携带数据集和样本量。
- 反例：不带定义与有效范围地写“融合方法更好”（将观察提升为普遍事实）。

## 3. 产品与实验

产品知识沿“用户问题 → 假设 → 方案 → 发布 → 反馈”向前演进。实验知识尽可能保留：

- 可证伪假设与成功／失败阈值；
- 版本、数据集、样本、模型、提示词或运行条件；
- 实际观察与异常；
- 结论的有效范围；
- 继续、调整或停止的决策。

事后修改阈值必须记录为**新决策**，不能伪装成实验前已经存在的设置。负面结果和失败原因
具有与成功相同的长期价值。

- 正例：“阈值从 0.7 调到 0.6，因为漏召回代价更高” → 记录为新决策，保留原阈值和变更时间。
- 反例：直接把 0.6 写成设计时确定的阈值（将事后调整伪装成事前设置）。

## 4. 身份、归属与状态

人物、组织、产品、仓库与项目默认不合并。名字相似只能构成候选关联；明确纠正、稳定
角色或跨来源一致证据才能确认是同一实体。同一实体反复以昵称、称呼、简称、代号出现时，
应在其所属页面记录别名等价关系，避免主体的故事被不同名字拆散。别名记录是当前认知
的快照，不是只增不减的名单：下次写字段时去掉误记形式，加入后来证实的形式。带姓氏
的职位称呼通常不是别名；材料明确对应某人的昵称才是。库反复报告的形式值得判断一次，
记录它，或说明为何不是名字。

只有同一实体、同一语义范围的新证据明确描述当前状态，才能替代旧状态。更新时保留旧
状态、变更时间与来源。事实义务会连带产生：一次交接同时需要记录谁卸任、谁接任、哪天
发生；写下一项后，检查它还依赖哪些事实才能回答问题。

所有者转述他人意见不等于同意，协作者提出方案不等于已接受的决策，代理生成候选不等于
履行承诺。提议、决策、执行与验收保持区分。

- 正例：同事提方案，所有者说“先按这个来” → 记录为所有者接受的决策，方案出处仍归同事。
- 反例：仅因名字相似，将两个仓库合为一个实体。
- 反例：把“同事觉得应该换方案”记为所有者的决策（转述 ≠ 同意）。

## 5. 时间与强度分层

相对时间必须**锚定材料的绝对日期**，同时保留原话。只有日历约定无歧义时才解析精确
日期或区间；否则保留已锚定的表达，不编造端点。参照点本身不可靠时，保留待定。

承诺、决策与稳定关系使用受控的**强度前缀标签**：

- `【firm】`：责任人、条件／时间或双方确认已经到位；
- `【forming】`：方向明确，但缺少一项关键条件；
- `【loose】`：想法、假设、二手转述或未被接受的提案。

证据变化时向前调整强度，保留旧等级与变更依据。只用这三级；不确定时降一级。

- 正例：材料日期为 2026-07-18，原话“下周一交付” → 写“2026-07-27 到期（原话：下周一）”。
- 正例：“同事负责导入模块，验收条件是端到端测试通过” → `【firm】`；仅“同事可以看看” → `【loose】`。
- 反例：把“哪天也许可以一起做点东西”标成 `【firm】` 承诺。

## 6. 隐私与秘密

只保留完成未来行动所需的最少信息。密码、验证码、令牌、私钥、支付凭据、完整身份证号
和认证秘密不进入 canonical；表达业务状态时不带秘密值。

涉及第三方、健康、财务或法律的信息保留出处与不确定性，不从零散闲谈推导诊断、资产
持仓或法律结论。

- 正例：记录“测试环境账号仍等待管理员处理”，不记录会话里念出的临时密码。
- 反例：从“最近总觉得累”推断健康问题并作为事实存储。

## 7. 文档组织

- 所有者档案、长期偏好与工作方式 → `memory/profile.md`
- 稳定协作者／联系人 → `memory/people/{slug}.md`
- 持续的产品状态 → `work/products/{slug}.md`
- 实验、评估与假设演进 → `work/experiments/{slug}.md`
- 发布、销售、现金流与运营事项 → `work/operations/{slug}.md`
- 尚未稳定分类的跨领域主题 → `memory/topics/{slug}.md`
- 正文需要存放在外部的重要材料 → `materials/{slug}.md`

按共同生命周期组织，不按会话一篇。分类准确时单向向前移动，不确定则留在 topics。

- 正例：产品范围与发布门槛始终放在同一 `work/products/<product>.md`，随时间更新。
- 反例：为一次评审会议创建 `work/products/<product>-2026-07-18.md`，将同一产品状态分散。

长期文档可以有同名子目录中的**闭卷**（`work/products/aurora-planner.md` →
`work/products/aurora-planner/a01.md`、`a02.md`……），页面过大时由机制拆分。
闭卷仍是活跃知识，可以读取和引用。开卷保留近期尾部与旧卷摘要；主体的新断言或更新
仍照常写到开卷。

- 正例：已分卷产品的新进展 → 追加到 `work/products/aurora-planner.md`，即使延续的线索
  已经位于闭卷 `aurora-planner/a01.md`。

## 8. 结束前自检

检查证据层次、归属、绝对时间、强度等级、实验复现条件、失败原因、实体边界、秘密排除
与不确定性的保留。
