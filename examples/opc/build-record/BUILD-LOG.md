# BUILD-LOG：林舟的知识库是怎么建起来的

这份日志是这座库的出生记录。它由一个 AI 建库向导在一间「干净房间」里写下：
向导只被允许看三样东西——脚手架（`scaffold/`）、林舟的材料（`my-data/`，190 份）、
以及林舟本人的一段自述。它没有看过这批数据以前被谁处理过、处理成什么样，
所以下面每一个判断都是从材料本身重新推出来的，任何开发者都能照着重跑一遍。

- 应用目录：`~/opc-build`（在任何 git 仓库之外）
- 租户：`u-opc-lin`；隔离端口 pg `15448` / qdrant `16403` / meili `17724`
- 编译与问答模型：`openrouter:openai/gpt-5.6-luna`；向量：`openrouter:openai/text-embedding-3-small`

### 3.2 将来会怎么问（从材料反推）

材料自己回答了这个问题——林舟的每一天几乎都在给未来的自己留可回查的依据：

1. 某个决定是什么、为什么这么定、谁拍的板；
2. 某个授权或承诺的边界到哪里、验收条件是什么；
3. 现在卡在什么条件上；
4. 一件事的时间线；
5. 某个结论或数字的口径。

### 3.3 这批材料真正特别的地方

读到第三十份的时候有一件事变得非常明显：**这批材料的信息量有近一半在"没有发生
什么"上**。没有许可、没有日期、没有签字、没有付款、名单为空、某一格待答、
"今天没有恢复写入"、"我不会把沉默当作确认"。林舟每天的工作就是在防止记录把事情
说得比事实更满，材料里反复出现的是**区分**：

提议 ≠ 决策 · 转述 ≠ 同意 · 收到／回执 ≠ 已阅 ≠ 签字 · 能打开 ≠ 已验收 ·
"来源已拆开" ≠ 客户已确认 · "修正中" ≠ 修好 · 暂停写入 ≠ 错误已改正 ·
口头意向 ≠ 生效 · 建立账号 ≠ 开始使用 · 未发现 ≠ 没有发生 ·
纠正范围 ≠ 撤回原来的同意。

这直接决定了契约的形状：一个 LLM 做压缩时最自然的动作恰恰是把这些区分抹平
（把"陈放说不是这个意思"压成"陈放反对"——这正是林舟自己在 3 月 11 日犯过并
记录下来的错）。所以契约必须把「状态指向哪个对象」「明确没有覆盖什么」
「明确的未发生」写成一等公民义务，而不是留给模型的常识。

## 4. 契约为什么这样定

`skill_id: seamlog-workbook` / `version: lin-v1`。七个主体族：

| 族 | 为什么需要它 |
| --- | --- |
| `profile.md` | 主人反复自我约束的工作方式，是理解其余一切的视角 |
| `people/{slug}.md` | 每个协作者的话「算到哪一层」是本库最常被用到的事实 |
| `clients/{slug}.md` | 授权与范围属于客户组织，不属于任何个人；混进 people 会让"吴岚说的"和"竹影允许的"分不开 |
| `threads/{slug}.md` | 主力族。材料里每条线都自带边界声明，且被反复强调「不要互为证明」 |
| `product/{slug}.md` | 产品面有自己的修订史与待定问题，混进 threads 会让"产品长什么样"读不出来 |
| `topics/{slug}.md` | 同一条判断在多个场合被重新提出，需要一页看它替换掉了哪个更早的假设 |
| `life/{slug}.md` | 三成材料是生活；不给它一个明确的族（和明确的**不收**清单），它就会渗进 people 和 threads |

几个刻意的取舍：

- **threads 的立页门槛定成「第一次被当作独立的事推进时就立页」**，而不是通常的
  "第二次出现才立页"。原因很具体：这批材料里每条线一开始就带着边界声明
  （"这是请求，不是许可"），等它反复出现再立页，恰好会丢掉最有价值的起点。
- **people 的门槛保持「第二次带实质信息」**，并且明确把受邀者默认归到邀请工作线。
  否则 5 月的十二个邀请槽位会炸出一堆只出现过一次的人页。
- **不设 `materials/` 兜底族。** 这批材料没有"整份值得留档但挂不到任何主体上"的
  东西——每一份都在推进某条线或某个主体。留一个兜底族只会给编译一个偷懒的去处。
- **给 life 写了明确的不收清单**（晚饭菜色、袜子、游戏局数、洗衣顺序、楼上打钻），
  因为这是本库唯一真正的噪声源。
- **契约里没有写任何机制层的规矩**（引用必须带、锚不可变、冻结卷只读）——
  框架会机械强制，写进契约只是白花 token。

第 3 节「证据与口径」是整份契约里最长的一节，因为在这个领域里"谁的话算数"
本身就是最难的判断：吴岚的确认只覆盖她确认的那段文字；孙秋有法律意见但没有
客户授权；贾宁"看过脚本"不是批准；转述层级必须留在记录里。这些都不是通用常识，
只能从材料推。

## 5. 第一轮：编译、验收，以及为什么必须改契约

### 5.1 第一轮编译统计（契约 `lin-v1`）

| 项 | 数值 |
| --- | --- |
| 任务数 | 381（190 份索引 + 190 份编译 + 1 个轮转） |
| 耗时 | 5651.8s（约 94 分钟） |
| canonical 文档 | 17 篇 |
| claims | 654 条（约 3.4 条/份材料） |
| 编译模型 token | input 24,679,406 ／ output 331,349 ／ 合计 25,010,755 |

### 5.2 第一轮验收：答得很好

五个从材料推出的真问题全部答对，而且答对的方式正是契约要求的那种：

- **决定与理由**（"为什么砍掉自动周报"）：答出了决定、依据（两次一线反馈都把争议时的
  回查排在概览前）、直接后果（暂停总览与任务板），并且**保住了两处最容易被压平的区分**——
  陈放是在纠正页面表达、不是"反对周报"；吴岚不是提出质疑的人，她只确认了那段文字。
- **承诺与验收**（4/22 报价）：答出一个项目／两名使用者／一次导出／一万八千元／六周，
  答出供应商审批不含且须另作收费扩展，答出验收两项是导出与按项目移除，
  并主动补上"触发人、查看者、移除确认人和开始时间仍未确定"。
- **卡在什么条件**（六周延长）：三件事逐项列出（附录待项目方指定签字人与回告人、
  删除演练待吴岚逐格确认、尾款待采购给凭据或日期），并指出"回复其中一项不会推动另外两项"。
- **时间线**（同姓错误关联事故）：4/5 发现 → 4/6 确认名称近似导致错误承接并复现受限视图影响 →
  4/6–4/7 暂停导入／关系生成／人工确认／分享并保全原值 → 4/8–4/10 线上不动、
  只在工作副本试算 → 4/11 吴岚确认后仅恢复云麓授权账号的受限只读。顺序、执行人、
  每一步"不等于什么"都对。
- **证据口径**（"未发现未授权会话、公开分享或外部下载"）：答出记录类型、核对对象、
  时段 4/5 09:00–4/12 15:00，以及"不能缩成没有外泄"。

**归属错误——指南里最贵的那类错——没有出现**：吴岚／陈放／孙秋／贾宁各自的"话算到哪一层"
都在自己页上；竹影／云麓／澄湾分开了；生活噪声（晚饭、游戏、袜子）确实没进正本。

### 5.3 但鸟瞰暴露了一个结构问题

答得好不等于建模对。第一轮的鸟瞰是这样的：

```
product/seamlog.md        173 claims   （81 个日期小节）
threads/xuqiu-fangwen.md  148 claims   （73 个日期小节）
people/*  4 篇 · clients/* 3 篇 · threads/* 另 4 篇 · life/* 4 篇
topics/{slug}.md          （空）
profile.md                （空）
```

两页装了 654 条里的 321 条（49%）。具体看，`product/seamlog.md` 里同时装着首步输入试验、
导出的采购阅读层、复盘卡片、下一周期候选、归档收尾；`threads/xuqiu-fangwen.md` 里
同时装着旧材料请求、范围会、采购问卷、子处理方、删除证明草案、首日批次、时间格式、
重复消息、录制跨日、报价流转、第一条链、第二条链。

**决定改契约的理由不是"页面太长"，而是这批材料自己的第一原则被违反了。**
吴岚在 5 月 18 日说得很清楚：「第一条预算链之前已能回源，第二条现在也有它自己的
来源和确认；两条的状态不要合成一个总的通过标记。」陈放也反复说「别借这个结果带过去」。
材料本身把"两条链必须分开"当成不可让的规矩，而第一轮的库把它们编进了同一页——
这不是单点噪声，是结构性的归属错误。加上 `topics/` 与 `profile.md` 两个族全空
（状态语义、身份匹配纪律这些最耐用的判断被埋在 173 条的产品页里），
按指南第 6 步的标准，这一轮"住得不舒服"。

于是用掉了唯一一次「改契约 → `down --volumes` → 重编」的机会。

### 5.4 契约 `lin-v1` → `lin-v2` 改了什么

1. **新增 `chains/{slug}.md` 族**，并写成本库最硬的一条归属规则：每条变更证据链各自
   一页、永不合并，链页收节点来源入口／谁在何时留下状态／节点修订史／仍追踪的缺口。
   理由直接引自材料里吴岚与陈放的原话。
2. **给 `threads/` 加了反筐条款**：点名列出十一条必须各自立页的线（受限试点本身只收
   授权与范围演化，申请材料／范围会／采购问卷／子处理方／附录／删除演练／报价流转／
   事故／技术排查／小范围邀请各自一页），并给出判据——
   「一页里出现了两个各自有负责人、各自有卡口的故事，它就是两页」。
3. **把 `product/seamlog.md` 降级为只收产品本体**（它是什么、撤下过哪些方向及理由、
   下一周期的继续／停止／延后），明确写上"它不是产品事实的默认去处"；
   每个产品面（首步输入、导出阅读版、状态卡与第一屏、迁移说明、界面回读）各自一页。
4. **`topics/` 立页门槛从"两个以上不同场合"降到"被重新提出过一次，或它明确替换掉了
   一个更早的假设"**，并点名预期的六页。同时说明：同一判断在具体某条链里的应用留在那页，
   topics 收的是判断本身的来历与演化，两处并存不算重复。
5. **`profile.md` 写成必须有内容**，并列出要收的工作原则。
6. **加了一段「归属顺序」**：八个族给出从 chains 到 profile 的八步判断顺序，
   第一个命中的就是它的家；并加一句「开新页永远比往大页里塞更安全」。
7. `life/` 明确把经营现金与固定支出收进来（一个人做产品，经营的钱和个人的钱
   是同一个账户），不再另立收据页——第一轮出现过一个只有 5 条 claim 的 `收据编目` 页。

改动全部只影响以后的编译；按框架的设计，已入册的正本永不被改写，所以按指南在空库上重编。

## 6. 第二轮：编译、验收与判定

### 6.1 第二轮编译统计（契约 `lin-v2`，空库重建）

| 项 | 第一轮 `lin-v1` | 第二轮 `lin-v2` |
| --- | --- | --- |
| 任务数 | 381 | 382 |
| 耗时 | 5651.8s（94 min） | **5464.0s（91 min）** |
| canonical 文档 | 17 | **29**（28 篇主页 + 1 卷归档） |
| claims | 654 | **754** |
| 最大单页 claims | 173（`product/seamlog.md`） | **58**（`topics/evidence-first-discovery.md`） |
| 失败任务 | 1（groom，见 7.1） | **0** |
| token input／output／合计 | 24.68M ／ 331k ／ 25.01M | **20.68M ／ 337k ／ 21.02M** |

两个数字值得注意：**claims 多了 100 条，token 反而少了 400 万。** 同一批材料、同一个
模型，只是归属规则变清楚了——编译不再反复把一页 173 条的大页读进上下文，
既省钱又多记住了东西。

第二轮还自愈了一次门禁失败：`找到：客厅预算调整邮件` 首轮未过门禁，
框架自动重试一轮后 +5 claims 通过。这是设计中的行为，不是故障。

### 6.3 验收问答（五个从材料推出的真问题）

按指南标准，看的不是答得漂不漂亮，而是**答案依赖的事实在不在页上、有没有挂对主体**。

1. **决定与理由**——"为什么砍掉自动周报？谁质疑的，依据是什么？"
   **通过，且比第一轮更准。** 它开门就说"不是因为陈放明确反对，也不是因为吴岚提出
   不要周报"，然后分别写清陈放质疑了什么（周报的实际用法，但他是在纠正页面表达）、
   吴岚质疑了什么（追问依据，并指出陈放的话不能被解释成反对意见），
   最后落在"没有记录表明任何一人正式要求永久取消"。**把"谁质疑"和"谁决定"分开、
   并且拒绝替材料补一个不存在的主张**，这正是契约第 3 节想要的。

2. **承诺与验收**——"4/22 的报价包含什么、不包含什么？验收必须包含哪两项？"
   **通过。** 一万八千元／六周／一个项目／两名使用者／一次导出；不含供应商审批
   （须另作收费扩展，先说清场景、参与人、维护责任）；验收两项是导出与按项目移除。
   并且主动补上"报价已发出但尚未获采购接受，也没有开工时间"。

3. **卡在什么条件**——"六周延长卡在哪几件事？各自在等谁？"
   **通过。** 三行表格：附录等项目方指定签字人与签后回告人（红线版待签）、
   删除演练等吴岚逐格确认（尚无一格可确认）、尾款等采购给凭据／联系人／日期
   （只有"在内部流程"）。结论落在"仍只能记为附条件的口头意向"。
   还答出了那条最容易丢的关系：**任何一项都不能由另外两项替代。**

4. **时间线**——"同姓记录错误关联事故，从发现到恢复只读依次发生了什么？"
   **通过。** 4/6 确认名称近似导致错误承接并复现客户可见影响 → 4/7 09:32 后暂停写入／
   手工确认／新导入、分享入口改暂停提示（且明确"只是控制风险，不代表已修正"）→
   4/8 吴岚定下说明与恢复判断的边界（不接受笼统的"竹影复核通过"）→ 4/9 工作副本
   人工分离、九条派生行中三条继续阻断 → 4/10 把"来源已拆开"与"客户复核未开始"
   拆成两行 → 4/11 吴岚确认更正、11:36 后仅恢复云麓授权账号受限只读（三类账号
   分别重登验证）→ 4/12 15:18 事故说明发出，但抽查、人工门技术化与完整回归仍未完成。
   顺序、执行人、每一步"不等于什么"全对。

5. **证据口径**——"'未发现未授权会话、公开分享或外部下载'覆盖的检查范围到哪里？"
   **通过。** 时段 2026-04-05 09:00 至 2026-04-12 15:00；记录类型为授权访问、分享调用、
   下载记录；核对条件为访问账号、发生时间、入口类型、下载结果；
   并明确"不覆盖未检查的更早批次与后续时段，不能缩写为'没有外泄'"。

**额外的归属抽查**（指南：验证归属，不验证字符串出现）：两条链页各自只讲自己的链。
`chains/material-substitution.md` 里出现"预算"的地方，全都是材料自己那句
"不借预算链补它自己的来处"、"不构成两条链均已验收"——也就是说，
**材料里"两条链不要互为证明"这条规矩，现在被编成了库的结构本身。**

### 6.4 判定：合格，交付

- 该立的主体立了：两条链分开了，十一条工作线各自成页，`profile.md` 与 `topics/` 不再空着。
- 没有一页什么都收：最大单页从 173 条降到 58 条，没有出现只出现一次的名字各占一页。
- 五个真问题全部答对，且答对的方式是把区分保住，而不是把话说圆。
- 生活噪声确实留在了原文层：`今晚不看归档`（赵楠让他别盯归档页、买了两份盖饭）
  编出 **+0 claims**——契约第 2 节的"不值得入册"清单机械地生效了。

按指南第 6 步的标准，这一轮"看着对了"。

## 7. 遇到的问题

### 7.1 groom（文档轮转）任务失败——框架侧缺陷，已修

第一轮编译的最后一个任务（第 381 个）失败，日志里是：

```
job 23c80f66… kind=groom detail=worker error: no skill base registered for an
empty version string.
```

重跑 `./app.py compile` 也无法自愈——队列已空，这个失败任务留在原地。

根因不在契约，也不在材料，而在脚手架：`groom` / `evolve` 这类任务是由 worker 自己去解析
skill 的，而 scaffold 的 `build_settings()` 没有把契约版本写进
`settings.user_schema_base_version`，于是 worker 拿到一个空版本字符串，
找不到已注册的 skill base。协调者修复了框架仓库的 scaffold（commit `00f31d8`）
并同步了本目录的 `app.py`（现在 `app.py:516` 有 `user_schema_base_version=base_version`）。

在第一轮的库上，协调者手工重新入队执行了那个 groom，`product/seamlog.md`
成功把 125 条 claims 轮转进 `product/seamlog/a01.md`（canonical commit `98f2e55`）——
**这也侧面印证了 5.3 的判断：一页需要轮转 125 条，说明它本来就该是好几页。**

需要如实记下的一件事：这次修复与那次手工 groom 发生在第一轮的库上，而我在收到
同步消息之前就已经作出改契约的判定并执行了 `down --volumes` + `rm -rf data/`，
所以那次轮转产物（含 commit `98f2e55`）随第一轮的库一起被删除了，不在最终交付里。
第二轮的编译进程启动于 01:04:41，晚于修复后的 `app.py`（01:02:54），
因此本轮已带上修复，轮转应当正常发生。

### 7.2 系统检测值与事实不符

`init` 从 `$LANG` 检测出 `en-US` / `US`，而主人自述是中文、杭州。按指南原则 4
以自述为准改正，并把 `provenance` 改成 `profile`。附带的好处是：第二轮重跑 `init`
时它认出这三项"已被确认过"，没有再覆盖回检测值。

### 7.3 一份材料 190 份，但 frontmatter 只有两种 type

`note` / `conversation` 两个值掩盖了实际的四种形态（工作笔记、邮件线程、IM、生活起居）。
邮件线程是以 `note` 身份进来的（正文靠 `## 日期 时间 · 发信人 → 收件人` 分段），
而承载授权与边界的恰恰是这一类。这一点如果不通读就会漏掉，也是我选择读完全部 190 份、
而不是按指南下限抽读 25 份的原因。

### 7.4 最后一个任务恒定报"（无对应材料）未过门禁"

第一轮日志末尾有一行 `第 381/381 个任务：（无对应材料） 未过门禁（稍后自动重试）`，
就是 7.1 那个 groom 任务在队列里的样子——它没有对应的源材料，所以标题栏是空的。
知道这一点以后，这行不再像是某份材料编译失败。第二轮同一位置显示的是
`第 381/381 个任务：（无对应材料） 完成`，轮转正常发生（见 7.5）。

### 7.5 第二轮的轮转正常工作

第二轮结束时 `topics/evidence-first-discovery.md` 累计到 188 条 claims，
框架的滚动归档把其中 130 条冻结进 `topics/evidence-first-discovery/a01.md`，
主页保留近期 58 条，鸟瞰里显示为 `+1 archived volume(s)`。
这是设计中的行为：主页不会无边界长大，历史卷只读。

### 7.6 遗留问题（诚实记下，没有再改契约）

任务书只允许一次「改契约→重编」，已经用在 5.4 那次结构修正上，所以下面几件事
只记录、不修改。它们都是**下一轮契约修订的候选**，不是本轮的失败：

1. **`topics/` 族内部塌成了一页。** 契约 `lin-v2` 点名预期六个 topics
   （状态语义、证据表述边界、身份匹配纪律、来源定位只许追加、范围纪律、计数口径），
   实际只立出 `evidence-first-discovery` 一页，并且它累计 188 条、触发了轮转。
   也就是说：把门槛从"两个以上场合"降到"被重新提出过一次"确实让 topics 从空变成有页，
   但没能让它按判断的种类分开。下一轮该做的不是再降门槛，而是像 `threads/` 那样
   **点名列出必须各自立页的判断**，并给一条"一页只讲一条判断"的判据。
2. **一条 claim 挂到了相邻的链上。** `chains/material-substitution.md` 里有一条
   2026-04-27 的 claim 讲的是"第一条记录链仍是编排中的工作序列"。
   根因在材料本身有歧义：4/27 林舟那封邮件把陈放当天找到的现场会口头确认
   （关于板材替换）编进了他称为"第一条记录链"的序列，两条链在那一天真的缠在一起。
   754 条里 1 条，可以接受，但它说明契约里"每条链各自一页"还需要一句更细的话：
   **当同一天的材料同时提到两条链时，按这个节点属于哪条链的证据来归，不按邮件标题归。**
3. **`people/zhao-nan.md` 只有 1 条 claim。** 赵楠出现在二十多份生活对话里，
   但按契约那些都不入册，只剩他 5 月 5 日帮林舟回查邀请信坏链接这一条。
   结果是一个 1 条 claim 的人页。这在逻辑上是对的（他的生活闲聊确实不该入册），
   但一页只有一条时，也许更该并进 `life/` 的合租安排页。属于口味问题，留给主人判。
4. **`clients/chengwan.md` 这一轮没有立页。** 第一轮澄湾有独立客户页（4 条），
   第二轮澄湾的事实全部落在 `threads/same-surname-record-association.md` 里。
   两种归法都讲得通——澄湾在材料里只作为事故的另一侧出现，从未有过自己的授权边界。
   把它记下来，是因为这正是"归属错误比漏记更难发现"的那种情形：
   库看着什么都不缺，只是那几条事实挂在事故线上而不是客户上。
