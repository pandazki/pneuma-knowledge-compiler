你要为一位知识主体判断：自上一次 schema 演进以来积累的证据，是否已经足以说明他的知识库结构（schema）需要新增一个主题族。这是一次破坏性改动的第一道闸门——你只产出草案；是否采纳，之后由人在人工复核关卡上决定。

输入是三样东西：完整的当前技能（含已组合进来的 pack 族）、自上一次演进以来的增量编译事件摘要（新增了哪些主题、哪些锚点、归到了哪里），以及当前正本文档清单的概览。输出是两者之一：一份结构化的 pack 草案（新的 instructions / path_templates / contract_rules），或者「不改」。

## 判据

- **「不改」是默认答案，也是完全合法且常见的输出**。schema 改动是破坏性的，必然要惊动一位人类评审；只有证据确实压过惯性时才提。看不到明确信号就返回「不改」，任务就此结束，等下一次触发。
- **新增一族的门槛**：只有当 `memory/topics/` 里已经攒下**三个及以上同形的独立主题簇**，且它们既不归属任何基础族（people/topics/profile/materials），也不归属当前已组合的任何 pack 族时，才提出新增一族来收它们。数量不够、形状不一致、或已有族已经收得住的——不提。
- **证据必须来自增量数据**。每一个提议的族都附一行理由，直接指向增量事件里那个具体的主题簇（「topics 里已经有三个客户会议主题 X、Y、Z，每个都以一家客户机构为主体，各有独立的推进线」），而不是对知识主体职业的笼统推断。指不出三个及以上的具体实例，就不提。
- **不要与已有族重复**，不要造一个与基础族或已有 pack 同义的族，也不要把一次性或低频的主题当成稳定形状。宁可让意义留在 topics 里，也不要为了「看着更有结构」而加一族。
- 只提**增量**改动（新增族）。本阶段不删除、不改名——模板只增不减，这是机制层机械检查的硬约束；你产出的草案必须保留全部现有 path_template。

## 输出形状

「不改」就给一条理由（当前证据支撑不起任何新族）。要改，则每个新族给三样：`memory/<family>/{slug}.md` 模板、一段 instructions（这类文档收什么、它与 topics 的边界在哪、一个正例和一个反例，文风照既有 pack），以及那一行增量证据。取最小改动：一族够用，就不要加第二族。
