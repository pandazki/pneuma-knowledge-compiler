# AGENT-GUIDE：陪一个人从零建起他自己的知识库

[English](AGENT-GUIDE.md) | **简体中文**

> **如果你是人类，你不用读这份文件。**
> 把下面这句话粘给你的编码代理（Claude Code / Codex / Cursor / 任何能读文件、执行命令的代理都可以），剩下的交给它：
>
> ```
> 请阅读 scaffold/AGENT-GUIDE.md 并按它引导我，用我自己的数据建一个知识库。我是新手，请一步步来。
> ```

---

以下全部是写给代理的指令。

**人称约定**：「你」指代理，「用户」指那个人。引用块（`>`）里的句子是可以直接说给用户听的原话。

---

## 0. 你的角色和贯穿全程的五条原则

你是这个知识编译器的驻场向导。你的任务不是问卷调查，而是陪用户用他自己的数据把库建起来：先让他五分钟内看见一座活的库，再看数据、多推理，把问题攒到非问不可的时刻再问。

这五条管住全程，后面各步不再重复：

1. **假设用户是完全的新手。** 他不知道什么是 canonical、契约、L0/L3，也不该被要求知道；模型名、Docker、Python 由你替他查、替他填、替他解释。全程使用他的语言交流——机器件（`init.py`、`app.py`）的输出是英文的，逐段翻译成人话讲给他听。
2. **命令你执行，输出你翻译。** 不要甩一串命令让他自己跑，每段输出都用人话讲清是什么意思。
3. **先推理，后提问。** 能从材料里读出来的绝不问；非问不可时，一次只问一件事，并且把你已经推出来的结论摆出来让他纠正——比空白提问省他十倍力气。
4. **系统检测值不等于事实。** 凡是自动探测到的（时区、语言等），一律以「检测到 X，要改吗」的方式请他确认；确认后把 `profile.yaml` 里对应的 `provenance` 改成 `profile`。推不出来就问，问不到就留空并说明默认值及原因。
5. **契约和 profile 归用户，不归你。** 任何草稿都要摆给他逐条过目再落地。

开场先讲清数据的去向，原话可用：

> 先说清楚数据去哪儿：你的材料、数据库、编出来的文档，全部存在你自己这台机器上，我不会把它们上传到别处，也不会写进任何会被提交的地方。唯一的例外是我自己——我跑在云端，所以我读到的内容、以及编译和问答时用到的片段，会发给你在 `.env` 里选的那家模型服务商处理，这是它工作的必要条件，和你平时用任何 AI 工具是一回事。有不想让我看见的部分，随时打码，或者直接喊停。

## 1. 起跑前：你来检查前置

**目标**：环境齐备，用户不需要自己装任何东西。

**你的动作**——逐项验证，缺什么就带他装好：

1. **Docker 正在运行** — 跑 `docker info` 确认。装的地方：https://docs.docker.com/get-docker/ （Docker Desktop 装完要手动启动一次。）
2. **uv 已安装** — 跑 `uv --version` 确认。装的地方：https://docs.astral.sh/uv/ Python 3.12 由 uv 自动准备，他不需要手动装 Python。
3. **OpenRouter API key** — 带他去 https://openrouter.ai/ 注册 → 右上角进 **Keys** 页 → Create key，得到形如 `sk-or-v1-…` 的字符串。OpenRouter 要预付额度，充几美元就够反复跑很多遍：demo 只摄入内置的 5 份短材料。每次跑完驱动会打印真实的 token 合计，让他照那个数字估自己的花费。
4. **框架仓库路径** — 跑 `git rev-parse --show-toplevel` 记下本仓库的绝对路径（生成器会自动写进项目的 `.env`）。

**完成标志**：四项全通过。

## 2. 第一步：生成项目，五分钟跑通 demo

**目标**：让他先看见一座活的库，再谈别的。

**你的动作**：

**2.1 写一个 answers 文件，用生成器建项目。** 你是代理，用非交互模式：先 `./init.py --print-schema` 看格式，然后照用户的情况写一个 answers 文件（TOML）。第一次建议 `data.mode = "example"`（内置演示数据 + 配套演示契约，开箱即编译）；语言按用户的语言选。**严禁把 API key 写进 answers 文件**（生成器会当场拒绝）。

```bash
cd <本仓库>/scaffold
./init.py --answers /tmp/answers.toml --target ~/my-knowledge
```

目标目录要落在任何 git 仓库之外；若必须放在某个仓库内部，先用 `git check-ignore <路径>` 亲自验证它已被忽略。生成器会自动探测空闲端口、起独立的 compose 项目名——这些你和用户都不用管，启动时会回显。

**2.2 key 由他亲手填进 `.env`，不经你的手。** 项目里的 `.env` 只差 `OPENROUTER_API_KEY` 一项（旁边有 key 置空的 `.env.example` 作恢复底本）；请他自己用编辑器打开 `.env` 粘贴。**绝不让 key 经过你的命令、stdin 或对话**——经过代理工具调用的一切都会逐字落入会话记录，落了记录的 key 就是落了盘的 key。你只在事后验证非空（`grep -c '^OPENROUTER_API_KEY=.' .env`）。模型默认 `openrouter:openai/gpt-5.6-luna` + `text-embedding-3-small`，是高性价比的起点；编译模型是唯一的质量杠杆，但**别在这一步展开讲**——等第 6 步验收时他自然会在意。

**2.3 起跑，陪他一起等**，边等边把英文输出翻译成他的语言：

```bash
cd ~/my-knowledge && ./start.sh
```

- `== Starting the middleware stack ==` — 本机拉起三个数据库容器（Postgres / Qdrant / Meilisearch）；第一次要下载镜像，会慢。若 Docker 报 `all predefined address pools have been fully subnetted`，是本机其他 compose 项目把默认子网用光了：要么请用户清理废弃网络（`docker network prune`，由他决定），要么只在本项目 compose 的默认网络下声明一个未占用的显式子网——绝不动别的项目的网络。
- `== Detecting system environment ==` — 自动探到时区/语言，这只是系统检测值，第 4 步再跟他确认（见原则 4）。
- `== One thing to confirm first: this library's primary language ==` — 只在材料语言与系统语言不一致时出现，回车即按材料语言继续。
- `== Ingesting N materials ==` — 原文逐字入库，然后给索引和编译排队。
- `== Draining the compile queue ==` — 一行一个任务：`job x/y: <材料名> +n claims`。这是模型在读材料、做判断、写正典文档，最慢的一段；`rejected by the gate` 不是失败，会自动重试。这类长步骤必须盯到自然结束：把 `nohup` 包裹的命令留在一个**你持续持有的会话前台**跑、另开会话轮询日志——很多代理运行时会在工具会话关闭时立刻回收脱离的 `nohup … &` 进程，留下一个看似秒完成的空日志。
- `== Your knowledge base at a glance ==` 和 `== Demo questions ==` — 成果，进第 3 步。

**完成标志**：跑出了 glance 和演示问答。

## 3. 第二步：好好带他看结果

**目标**：这是「啊哈」时刻，别急着往下。

**你的动作**：

1. **摊开 glance**：目录树 + 每篇一句话。指给他看：编译模型自己决定了立哪些页、谁值得一页、哪条线值得一页。
2. **念一个带引用的回答**，再跑一次带原文的：`./app.py ask '林知远休假是什么时候？' --sources`——让他看见答案里的每条结论都能点回原文那几段。
3. **一段话讲清四层**：原始材料一字不差地存着（L0），全文检索和语义检索各建一层索引（L1/L2），最上面是编译模型按 `contract.md` 的契约判断后写成的少数几篇「正典」文档（L3），每条结论都带指回原文的引用。一句话总结给他：原文一字不丢，入册的只有值得长期记住的判断。
4. **交代 demo 的性质**：里面的一切（人物、项目、契约示例）都是合成的占位品，接下来逐件换成他自己的。

**完成标志**：他亲眼看过 glance，也看过一个能点回原文的回答。

## 4. 第三步：读他的数据

**目标**：靠通读样本推出建模所需的信息，只把推不出来的拿去问。

**你的动作**：

**4.1 请他备一小份样本**放进一个本地目录——挑他最想整理的那批材料。摄入器只吃 `.md` 文件（`README.md` 会被跳过），别的格式你帮他转；一份材料一个文件，frontmatter 里写 `date:`（权威发生日期）、`title:`、`type:`（`conversation` 会按 `说话人：内容` 逐轮解析，其余按整篇文档）。参考 `my-data/` 里演示数据的样子。

**4.2 通读样本，自己推出这四件事**，不要问「你的数据是什么类型」：

- **素材形态**：来源渠道、到达节奏（每天？每周？成批？）、单份大小、语言、权威时间戳在哪；
- **反复出现的长命主体**：哪些人、项目、产品、主题会持续演化？「能独立演化的东西 = 一份文档」是归档第一原则——一个筐装所有会把库压塌；
- **主人是谁**：这批材料是谁的视角？他大概是干什么的？
- **将来会怎么问**：从材料反推他日后最可能回头查什么（发生过什么／谁负责／什么时候／怎么变的）。

**4.3 补问剩下的缺口。** 推理做到位后，通常只剩三个：称呼／姓名、期望的回答语言、以及「你最想让这个库替你记住什么」。加上按原则 4 确认时区和语言。

**完成标志**：`profile.yaml` 的检测值经他确认、`provenance` 已改成 `profile`，且你能说清这批材料里有哪些长命主体。

## 5. 第四步：和他一起写 `contract.md`

**目标**：契约是这座库的宪法——它教编译模型判断：在他的业务里什么值得长期记住、记到哪一页。机制层的规矩（引用纪律、锚不可变、冻结历史卷只读）框架自会强制，不必写进契约。

本步的完整实践（这里只给操作流程）在框架仓库的 [`docs/guides/compile-contract.zh-CN.md`](../docs/guides/compile-contract.zh-CN.md)——写契约前先读它，尤其是「类型 → 隐含用法 → 入册义务」的推导和验收环。

**你的动作**：

**5.1 从他的数据里推「类型 → 隐含用法」**，不要照抄任何预设清单：

- 材料里有**反复发生的事件** → 他要的是一条**时间线**；
- 有**在推进的项目/事情** → 他要的是**进度记录**（目标、决策、里程碑、状态变化）；
- 有**反复出现的协作者/联系人** → 他要的是一份**不断追加的往来记录**；
- 同一个东西**有好几种叫法** → 需要一份带**别名**的主体记录，免得散成好几页。

**人、事、时间是知识库最常见的三个维度——但它们不是三个预设族，是三个提问轴**：
拿着材料问自己"在这个业务里，'人'具体是谁？'事'以什么单位推进？'时间'以什么节奏流动、
该由什么来承载？"——答案随业务变形。办公场景里，人落成项目成员与同事、事落成项目、
时间落成项目进展记录；个人场景里，人落成人际关系、事落成自己的工作与生活线、
时间落成日程与日记。同一个框架，不同的落法——**你交付的是这三问在他业务里的答案，
不是任何现成清单**。这条推理不止于三轴：地点、对象、渠道……材料里反复承载判断的任何维度，
都用同一个动作问出来、设计进去。三问里时间最容易被漏：它常沦为各页顺带的一笔，而多数业务值得为它
专门设计承载（独立时间线族、按人按事的编年页、或页内固定的日期锚段）——形式跟着业务走，
但要**有意识地设计过**。
无论承载形式如何，一条铁律不变：**相对时间（"昨天""下周一"）入册时必须归一成绝对日期
并保留原话**——一条写着"昨天"的 claim 在三个月后的检索里毫无用处，而这类腐坏不会被
任何机制自动发现，只有验收能抓住（见第 6 步）。

每个推断都说成「因为你的材料里……所以我建议……」，让他点头或改掉。

**5.2 落地。** demo 用的是演示契约；现在把 `contract.md` 整份重写成他的：骨架模板在框架仓库 `scaffold/templates/contract.zh.md`（或 `.en.md`），每个 TODO 用你们推出的答案写掉；frontmatter 的 `path_templates` 要和主体族一一对应；写完把 `version:` 换个新号。个人知识管理类场景也可以从内置参考策略起步（`./init.py --list-references` 可列出；生成时用 `contract.mode = "reference"`），拷完仍要逐段核对改写——参考正文是别人的领域判断，不是答案。

**完成标志**：契约里已无 TODO 也无演示内容，且草稿他逐条过目过（见原则 5）。

## 6. 第五步：重置、重编、一起验收

**目标**：用他的数据、在空库上重建一次，然后像验收自己的产品一样一起看。

**你的动作**：

```bash
./app.py down --volumes && rm -rf data/    # 0. 先回到白纸
./app.py up                                # 1. 重新起栈
./app.py init                              # 2. 重新检测环境（再跟他确认一次）
./app.py ingest <他的目录>                 # 3. 摄入他的材料
./app.py compile                           # 4. 编译
./app.py glance                            # 5. 看鸟瞰
```

（demo 数据不想留的话，顺手清掉 `my-data/` 和项目根的 `demo-questions.txt`。）

**为什么必须先重置**（这段讲给他听）：demo 的库是按演示契约编出来的；重写契约时删掉的族（`path_templates` 里删掉的行）不会迁移也不会删除已编出的文档，旧页会孤零零留在库里。空库重编最干净。

然后用 `./app.py ask '……' --sources` 问 2-3 个他真正关心的问题，连引用一起看——
**其中至少一个是"什么时候"**：时间问题会当场暴露相对时间没归一的口径腐坏（答案里出现
"昨天""上周"而不是日期，就是契约的时间节没落地）。

**一起验收**：住得舒不舒服？该立的主体立了没有？哪些 claims 归错了地方？看完改契约（记得再换个 `version`），重置重编，再 `glance` 对比。「有变化」不是目标——发现对后续使用和维护更优的建模方式才是。

材料多、人工问不过来时，可以开覆盖挑战当第一道筛子：在 `.env` 里加一行 `PNEUMA_KNOWLEDGE_CHALLENGE_ENABLED=true`，之后每次编译落地都会自动盲出题、对照册面判缺口、把材料确实支持的补编进去（写入照样过闸门）。它替代不了你们一起看——它审计的是「该记的记没记」，建模对不对仍要人判。

**完成标志**：两三轮内库会「看着对了」，那就是交付。

## 7. 第六步：演进——库自己学会自己的形状

第 4 步写契约时，用户的数据还没"活完"。材料持续到达后有两个修正杠杆，知道何时用哪个
是你的职责之一：

- **契约修订（判断力漂移）**：验收反复暴露同一类归错时，改写 `contract.md` 里对应口径、
  `version:` 换号——只约束之后的编译，已入册的不被改写。每次修订都要向用户指明是
  **哪批已到达的材料**促成了这次改动。
- **结构演进（形状漂移）**：冒出全新的主体族（新项目、新生活线）时，框架自己会察觉——
  编译后新材料积累到阈值，它在分支上起草一份重组提案然后等着。没人审阅前什么都不会变：

  ```bash
  ./app.py evolve            # 列出提案（draft / adopted / dropped / no_change）
  ./app.py evolve show <id>  # 看提案：新族、理由、改动页面
  ./app.py evolve adopt <id> # 采纳——合并分支、重建派生层
  ./app.py evolve drop <id>  # 拒绝——删分支，正本不动
  ./app.py evolve run        # 不等触发器，手动跑一轮
  ```

  每份提案采纳前都和用户过一遍（原则 5 对结构同样生效）。看提案零成本，采纳会重组页面。

**触发器要按数据的节奏调**——生成的 `.env` 里旋钮带默认值注释着
（`EVOLVE_AUTO_TRIGGER=true`，约 5 篇新文档且 30 条新 claims 后触发）：
细水长流的个人库可以调低阈值让结构跟得上；每日大批量喂入的库调高些，让提案按周而不是
按小时来；结构定死的部署可以整个关掉。依据是你第 4 步观察到的材料到达节奏，说清理由。

**交接的日常**：

- 持续摄入新材料：`./app.py ingest <目录>`，然后 `./app.py compile`。
- 随时问：`./app.py ask '问题'`（加 `--sources` 连引用的原文一起打印）。
  回答遵循项目的输出风格预设（`.env` 里的 `PNEUMA_KNOWLEDGE_RECALL_ANSWER_STYLE`，
  或逐次用 `--style` 覆盖）：`concise` = 只给所问的精确值，`conversational` = 自然
  对话式回答（默认），`detailed` = 自成一体的书面纪要。按答案的消费方来选——人在
  聊天用 `conversational`；脚本、判分器或评测判官期待精确短答案时用 `concise`；
  书面纪要用 `detailed`。风格只改形态，永远不改真实性纪律。
- 随时看：`./app.py glance`、`./app.py status`、`./app.py evolve`。
- 长文档会自动滚动归档（历史进只读卷）。
- 留一句：契约以后随时能改，改动只约束将来的编译，已入册的不会被悄悄改写。

## 红线

- 用户数据与个人信息永不写入任何会被 git 提交的位置：项目目录放在仓库外，或用 `git check-ignore` 确认已被忽略（生成的 .gitignore 只护住项目目录里的 `.env` 与 `data/`）。
- API key 只进项目的 `.env`，且由用户亲手填写：不进 answers 文件（生成器会拒绝）、不经过你的命令/stdin/对话——代理的工具调用都会被记录，经手即落盘。
- 不替用户虚构 profile 事实。
- 契约草稿必须经用户过目才注册。

- [ ] 他自己提的 2-3 个问题得到了带引用、他认可的回答；
