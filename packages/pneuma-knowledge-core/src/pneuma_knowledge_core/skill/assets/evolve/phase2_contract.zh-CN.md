schema 已经定下一个新族，你现在要为这位知识主体做一次全库重组：把散落在 `memory/topics/` 里、其实属于新族的意义搬到位。你工作在一条隔离分支上，新技能与重组后的数据在这条分支上原子地一起改变；是否采纳，之后由人在人工复核关卡上决定。

主动词是**搬移，不是改写**。这条纪律统辖整趟重组：

- **能搬就不要写。** 一条断言（claim）该归入某个新族时，连它的锚点注释一起**逐字**搬走——不动措辞、不换说法、不「顺手改好一点」。锚点身份必须保持连续，L3 投影、事件流和 git blame 才能一直跟着它走。你几乎不该产出任何新写的断言；这不是一次重新编译。
- **不合的就留在原处。** 只把明确属于某个新族的意义搬过去。放不下的、形状含混的、放进两个族都说得通的，一律留在 topics——「未分类 → 准确分类」是单向流动；不在族之间来回倒腾，也不为凑数硬分。留在 topics 不是失败。
- **合并冗余是例外，不是目标。** 只有两条断言确实语义等价时才合并，且每一次合并都要说得出**这两条为什么等价**（同一实体、同一语义范围、同一确定度）。合并会让一个锚点消失，机制层会把真正消失的锚点机械收进一份消失锚点清单交给复核；不要为了「看着更整齐」而合并，两条是否等价拿不准就不合——两条都留。
- **引用标准不降。** 你能够到旧知识库和原始材料（`store.fetch` 按需取来源块）；搬移后的、以及新写的每一条引用，都会当场对着 store 校验——来源必须存在，¶ 区间必须落在它的边界之内。逐字搬移天然保住原引用；确实必须改引用时，按同一标准核对，绝不为省力写一条到不了证据的引用。

收尾自检：有没有哪条断言被改写而不是逐字搬移；有没有该留在 topics 的意义被硬塞进新族；每一次合并都说得出等价依据吗；每条搬移过的断言，引用还能对着 store 校验通过吗？任何拿不准的地方，就留在原处、留下痕迹、交给复核。
