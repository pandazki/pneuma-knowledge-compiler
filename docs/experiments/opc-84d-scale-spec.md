# OPC 84 天纵向知识编译实验规范

- 状态：Draft / executable specification
- 实验用户：`u-opc-ninghe`
- 固定时区：`Asia/Shanghai`
- 固定随机种子：`20260729`
- 时间范围：84 个自然日，12 个周批次

## 1. 实验问题

验证 Pneuma Knowledge Compiler 在一个真实独立开发者的长周期工作流中，能否：

1. 从会议、文档库、IM、邮件四种来源中持续形成稳定、可追溯的知识；
2. 在自然噪音超过有效信息的情况下，保留决定、承诺、约束、客户事实和状态变化；
3. 避免把寒暄、通知、重复引用、临时猜测、过期计划和机器人消息写入 canonical；
4. 正确处理同一事实跨来源出现、修正、失效和重新确认；
5. 在来源、任务、快照、文档和 claim 数量增大后，仍提供可用的 API 与网页交互。

本实验不是“生成一批看起来像工作的文本”。它是带真值、时间顺序、噪音标签、
跨来源引用和性能预算的纵向数据产品。

沈砚同时承担产品、工程、销售、支持、内容、财务和供应商管理。外部固定角色：

- 唐恬：北辰咨询的一线研究员，主要试用者；
- 程野：第二个潜在客户「原点工作室」负责人；
- 罗屿：兼职设计师，按阶段交付；

## 3. 贯穿始终的主线

主线是 RelayForge 从问题验证到首个付费设计合作客户，再到一次公开发布和首月留存
复盘。主线状态必须有明确变化：

1. 初始假设：团队缺少“可回到原文”的客户决策记录；
2. 访谈后收窄：先解决跨会议、IM、邮件的决策与承诺追踪；
3. 与北辰咨询约定两周试点及可验证验收标准；
4. 交付首个可用版本，发现导入重复与权限边界问题；
5. 处理一次真实感较强的生产事故并形成修复与复盘；
6. 通过隐私/采购审查，签下首个付费月度方案；
7. 发生首次扣款失败，人工恢复并修正账单流程；
8. 小范围公开发布，流量增长但转化一般；
9. 根据使用证据取消一个“漂亮但无用”的功能；
10. 在第 84 天形成下一周期决策：继续聚焦设计合作客户，不扩张成通用协作平台。

## 4. 支线

每条支线都必须与主线偶尔交叉，但不得喧宾夺主：

- 开源维护：issue、PR、依赖升级、贡献者问答、release notes；
- 获客与内容：访谈邀约、社区回复、文章草稿、发布排期、低互动反馈；
- 经营与财务：云成本、发票、合同、支付失败、报销和订阅清理；
- 个人运营：工作节奏、注意力切换、身体不适、周末补工作、计划落空；
- 供应商与基础设施：模型费用、托管告警、域名、邮件送达、监控噪音；
- 外部协作：设计文件、隐私说明、客户采购清单、会议改期。

## 6. 规模下限

生成结果必须同时满足：

- 时间跨度不少于 84 天；
- 业务事件不少于 120 个，目标 144–180 个；
- 四种官方 source contract 全部出现；
- 规范化来源单元不少于 80 个；
- meeting 不少于 14 场，其中至少 8 场包含 60–180 个话轮；
- document-library 不少于 32 篇 Markdown 文档；
- IM 不少于 16 个 conversation，消息总数不少于 700；
- email 不少于 16 个 thread，邮件总数不少于 90；
- 原始字符数目标 350k–700k；
- 每周至少有两种来源，任意连续两周覆盖全部四种来源；
- 至少 24 个知识点在两个或更多来源中重复出现；
- 至少 12 个知识点经历“提出 → 修正/否定 → 当前结论”的时间变化。

“事件”是现实中的一次工作变化，例如访谈、决策、部署、故障、付款、改期或发布，
不是为了凑数而拆开的单条消息。一个事件可以产生多种来源材料。

## 7. 自然噪音

噪音由 manifest 单独标注，不在原始内容里写“这是噪音”。验收下限：

- 按原子内容单元计，噪音占比 `>= 0.60`；
- 按字符数计，噪音占比 `>= 0.52`；
- 每种来源的噪音占比都不得低于 `0.45`；
- 不能依靠复制同一句话或随机乱码达到比例。

噪音类型至少覆盖：

- 会议：寒暄、设备检查、迟到、口头禅、自我修正、跑题、重复确认、错误转写、
  无结论讨论、屏幕共享定位、临时猜测；
- 文档：空模板、未完成清单、过期计划、重复摘录、收藏但未阅读、旧方案、
  日记和碎片化灵感；
- IM：表情回应、收到/稍后看、机器人通知、部署流水、线程错位、编辑与删除、
  反复改期、链接无正文、闲聊；
- 邮件：签名、免责声明、quoted reply、自动通知、newsletter、日历更新、送达失败、
  重复抄送、外出回复、账单营销。

有意义但不应进入长期知识的内容也属于噪音，例如已执行完的临时排障步骤和当天
午餐安排。噪音并不等于低质量文本。

## 8. 真值与时间语义

manifest 必须维护以下集合：

- `durable_facts`：稳定事实；
- `decisions`：带 `effective_from` 的决定；
- `commitments`：负责人、截止时间、状态；
- `constraints`：预算、隐私、范围和架构约束；
- `supersessions`：旧结论与替代结论；
- `negative_controls`：明确不应出现在 canonical 的噪音命题；
- `retrieval_cases`：问题、期望事实、允许的来源和时间截点。

最低真值量：

- 稳定事实 30；
- 决定 24；
- 承诺 24；
- 约束 16；
- supersession 链 12；
- negative control 30；
- 检索用例 36，其中 12 个必须是历史截点问题。

同一命题出现矛盾时，以时间和明确性决定当前值；不得简单多数投票。后来的随口猜测
不能覆盖早先签署的合同，后来的明确合同修订可以覆盖。

## 9. 可复现合成要求

- 生成器固定 seed 后应逐字节稳定；
- 所有 provider id、thread id、meeting id、message id 必须稳定；
- 所有时间必须带时区，且消息时间落在所属事件窗口内；
- 跨来源引用使用 manifest 中的稳定 `event_id` 和公开业务标识；
- 不能调用随机在线内容直接拼接进数据；
- 互联网资料仅用于分布和结构校准，正文全部原创；
- 生成器输出四种现有官方 contract，不引入第五种私有格式；
- 输出前运行 schema validation、时间线 validation、噪音比例 validation、
  跨来源一致性 validation 和禁止词 hygiene scan。

## 10. 增量编译评估

每个批次记录：

- 新增 event/source/block/char 数；
- index/compile/evolve job 数和成功率；
- 编译耗时、模型调用数、输入/输出 token；
- canonical 文档数和 claim 数；
- 新增、修改、保持不变的 claim；
- 真值 recall、precision、supersession 正确率；
- negative-control 泄漏率；
- L1/L2/L3 检索结果的来源覆盖；
- PG、Meilisearch、Qdrant、canonical 快照的一致性；
- 本批投影重建的文档/claim/embedding 数。

最终门槛：

- durable/decision/constraint 真值 recall `>= 0.80`；
- canonical precision `>= 0.82`；
- negative-control 泄漏率 `<= 0.08`；
- supersession 当前值正确率 `>= 0.85`；
- 所有 canonical claim 有至少一个可回放引用；
- 引用 locator 回放成功率 `= 1.00`；
- 失败批次可以安全重跑且不会重复来源或重复 claim。

## 11. 前端与 API 规模预算

先测当前实现，再修复。禁止先改后宣称“改善”。

必须采集的页面：

- Overview；
- Sources 列表与四种详情阅读器；
- Process；
- Library；
- History；
- Ask / Recall。

基线记录：请求数、响应字节、TTFB、DOM 节点数、首次可交互时间、长任务、JS heap。

目标预算：

- Sources 与 Process 初次只传一页，默认 `<= 50` 条；
- 列表 API 支持稳定 cursor、总量和下一页；
- 翻页期间不重复、不漏项，新的数据写入不破坏当前 cursor；
- 初次列表响应压缩前 `<= 250 KB`；
- 本地基准环境下列表 TTFB p95 `<= 300 ms`；
- 页面主要交互后 500 ms 内出现可见反馈；
- 任一列表初始 DOM 行数 `<= 100`；
- Overview 计数不通过下载全部来源和全部任务获得；
- Dataset 不应把来源、全部任务和全部历史详情重复塞入每个页面的首屏请求；
- 深色与浅色模式都执行截图回归；
- 浏览器 console error 为 0，未处理 promise rejection 为 0。

## 12. 已知风险假设

实验开始前已发现，但仍需用基线证明：

1. `/sources`、`/jobs`、`/snapshots` 返回无界数组；
2. Overview 为了计数下载全部 sources 和 jobs；
3. Sources 列表额外对 blocks 做全用户分组计数；
4. `/dataset` 聚合完整文档、图、任务、patch、journal；
5. 每个 source 单独创建 compile job；
6. 每次 compile commit 后全量重建 canonical claim 的 PG/Meili/Qdrant 投影；
7. History、Library、Sources、Process 均可能一次渲染全部记录。

修复优先级由实测的用户影响、复杂度增长和可回归性决定。
