# 诊断召回质量

[English](recall-quality.md) | **简体中文**

召回质量是整条流水线的属性。同一个聊天界面上，「流畅但错误」与「事实缺失」看起来可能一样，修法却
相反。先找到信息最早在哪一层丢失；不要默认把所有预算一起放大，也不要默认再增加一次模型调用。

## 先读证据账本

对一个有代表性的问题，按下面顺序检查响应：

1. **L0 来源**——规范化后的 source 是否含有精确材料、正确发生时间，以及可解析的
   `source_id + block span`？
2. **L2 表示**——词法／raw 命中或带明确派生标签的 episode 摘要是否找到了事件？摘要扩大宽泛语义
   覆盖，但不是逐字证据。
3. **L3 正本**——compile contract 是否把值得长期保留的事实提升到了正确主体？只要 L0/L2 仍能正确
   回答，L3 缺失不自动等于故障。
4. **候选检索**——所需 claim／窗口是否出现在宽候选池？
5. **最终编排**——受限的回答上下文是否保留了所需证据组合？
6. **答案投影**——模型是否准确回答所问而没有扩大范围？下游是否使用不含引用的 `answer_text`，而非
   带引用的展示字符串？

最早失败的那层负责修复。重新编译无法恢复从未被规范化的来源；放大最终提示词无法找回缺失候选；
模型已经拿到精确证据时，再加候选也修不了答案生成。

## 一个控制只解决一种问题

- 所需证据不在候选中时，放大 `claim_candidate_cap` 或 `window_candidate_cap`。候选广度是索引工作，
  不是最终提示词大小。
- 候选正确、最终上下文却丢覆盖或太嘈杂时，调整 `claim_cap`、`episode_summary_cap` 与 `window_cap`。
  episode 承载高密度语义，逐字窗口承载精确措辞。
- 没有连贯 episode 表示时修 semantic chunking；长期事实持续归错主体时修 compile contract。
- 把 `evidence_strategy: ranked` 保持为直接基线。只有实际证明存在跨证据面编排缺失时才用 `select`。
  对比候选数、模型实际入选数与最终证据数：模型几乎不选、最终账本却很大，说明真正干活的是安全
  锚点，不是那次串行 selector。
- 下游需要干净语义答案和独立验证的引用账本时，使用 `answer_format: structured`。自动化消费
  `answer_text`，交互界面渲染带引用的 `answer`。
- 只有问题必须直接核验时才请求原始模态。caption／OCR 与原生媒体是不同证据选择，不能因为模型有
  能力就隐式带入。

## 保持时间语义诚实

`as_of` 是提问时间；来源发生时间是另一份元数据。实时问题可省略 `as_of`，使用当前 UTC 时刻；历史
回放必须传原始、带时区的时间戳。否则即使检索与来源日期都正确，相对时间计算仍可能被改错。

```bash
./app.py ask "这件事发生在多久以前？" \
  --as-of 2025-06-20T21:00:00Z \
  --style concise
```

## 不要混合测量轴

冻结一小组真实且有权限使用的验收问题，覆盖精确事实、多证据联结、时间和业务支持的模态。每次变更
保持数据与问题集不变，并分开记录：

- 回答验收与引用有效性；
- 候选数、模型实际入选数与最终证据数；
- 分阶段延迟，包括串行 selector 或 planning 调用；
- 分阶段 token 与金额；
- 降级和回退比例。

质量提升不会抹掉延迟回退，成本降低也不能证明答案更好。只有控制自身的作用轴与代价都可见时，才把
它升级为长期设置。
