# 索引组件

[English](index-components.md) | **简体中文**

这是**索引组件**——框架第二条扩展缝——的设计权威。它在系统里的位置见[架构 §6](../architecture.zh-CN.md#6-编译契约skill)与[§7](../architecture.zh-CN.md#7-检索)；旋钮见[配置](../reference/configuration.zh-CN.md#索引组件)；契约作者对 `people` 族欠下的那份判断力，见[编译契约指南](../guides/compile-contract.zh-CN.md)。

## 1. 为什么需要这个接缝

框架不持有任何领域观点，这是有意的：正本就是带 frontmatter 的文本文档，加上带锚点、带引用的 claim，core 知道的仅止于此。它不知道什么是人、什么是项目、什么是地点。正是这份中立，让同一个框架既能服务销售团队又能服务研究组，而两边谁都不必继承对方的模型。

它也有代价，而且这代价是结构性的，不是风格上的。有些问题根本不是关于*相关度*的：

- *"供应商那边，三月以来出现在任何一次对话里的都有谁？"* 问的是一个**闭合集合**。检索给的是命中列表，命中列表没有残差，据此作答的人说不出自己漏了谁。这个集合是存在的——它写在每份来源的边界上，就在参与者名单里——但 L0/L1/L2/L3 里没有任何一层把它当成集合来索引。
- *"六月到八月之间发生了什么？"* 问的是主人的**日历**。正本没有日历。用词法或语义检索回答它，等于指望"六月"这两个字恰好出现在某件六月发生的事的正文里。
- *"阿宝是哪一页？"* 问的是**身份**。一个从未在任何文档里出现过的昵称，放到全库尺度上却毫不含糊，因为它开启的那些轮次，被同一个人接了上百次。

这三个问题都能**机械地**从系统已经持有的材料里得到答案，而没有一个是靠更好的排序能答的。组件就是把那些材料索引起来的东西——它之所以是一条缝而不是一个功能，是因为*哪些*结构值得索引是一个业务问题，而框架是回答这个问题的错误位置。

## 2. 组件是什么、不是什么

**组件只持有结构和指针——身份、边、计数、区间，每一项都解析到一个来源区间或一个 claim 锚点——从不持有散文知识：它索引，它不"知道"。**

这一句就是全部设计约束，下面每一条规则都是它的推论。

| 组件可以 | 组件不可以 |
|---|---|
| 从 L0 与正本推导出一份投影 | 持有一条无法从这两者推导出来的事实 |
| 返回身份、日期、计数、区间、锚点 | 返回摘要、判断或叙述 |
| 在闸门上拒绝一次落在自己族里的写入 | 以任何形式写正本（I7） |
| 向各通道提供工具与查询路 | 决定它返回的东西有多少进得了提示词 |
| 在编译任务里说明自己在某份来源下观察到了什么 | 告诉编译模型该由此得出什么结论 |

最后两行最容易做错，所以各自有一节（§5 与 §7）。

组件也不是一种作业。worker 仍然只排空六种作业；组件搭的是其中本来就存在的那两种（§4）。

## 3. 各个面

组件是一个满足 `IndexComponent` 协议（`pneuma_knowledge_core/components/__init__.py`）的 Python 对象。每个面都有空操作的默认实现，因此组件只实现自己需要的那几个，`BaseComponent` 把这些默认值一次性写清。

| 面 | 框架何时调用 | 它贡献什么 |
|---|---|---|
| `gate_checks(docs, base_docs)` | `run_gate` 内部，草稿成为提交之前 | 针对本族里**本轮动过的**文档（§4）的写入时拒绝：frontmatter 字段全库唯一、形状必须合法、某个值明摆着是别人的 |
| `outline_tail(doc)` | 渲染编译提纲时 | 本族文档下的附加一行，让决定*往哪写*的模型看见组件索引了什么 |
| `validate_fields(path, fields, docs)` | `set_fields` 与 `rewrite_overview` 内部，写下任何一个字节之前 | 针对这次写入将要设置的 frontmatter 给出拒绝理由——把闸门的规则提前说一遍，于是组件能证伪的事实只花一次调用，而不是一整轮 |
| `compile_tools(draft, sources=)` | 装配编译工具面时 | 给编译模型的读工具，输入是草稿**与本轮的来源** |
| `recall_tools(user_id, documents=)` | 装配深召回工具时 | 给 agentic 通道的工具，限定在一个用户内（I1），作用于该通道已钉住的文档 |
| `fast_paths(user_id)` | 组装快召回时 | 路由查询路（§7） |
| `source_preamble(source)` | 渲染编译任务时 | 某份来源下的机械一行：这份来源的*边界*知道、而转录看不出的事实 |
| `prepare(user_id)` | 编译作业开头、任何同步面渲染之前，在作业窗口内（§4） | 同步缝的异步面（§4） |
| `on_source_indexed(user_id, source)` | 某份来源的 L1/L2 完成时 | 投影通道的增量写入 |
| `rebuild(user_id)` | 显式的 `rebuild_derived` 时 | 从 L0 与正本重新推导整份投影 |

这一组面里，有两条性质比任何单个面都重要。

**框架从不 import 任何组件。** 和编译契约一样，由*应用*注册它启用的那些（service 装配里的 `register_components`，由 `PNEUMA_KNOWLEDGE_COMPONENTS` 驱动）。名字不认识就在启动时大声失败。一个都不注册时，上面每条缝的渲染都与这个概念出现之前逐字节相同——包括编译 system message，它在每一个给定的启用集合下保持字节稳定（I5）。

**启用的组件集合会盖进每个正本 commit 的 trailer**，与契约哈希、overlay 哈希并排。于是一个提交自己就说清了：哪份契约、哪套措辞、哪些组件，产出了它。

## 4. 投影通道

一个想在一次查询里就把问题答完的组件需要自己的索引，而索引需要一条写入路和一条重建路。这条通道恰好就是那两个调用，外加一个解决部署问题的调用。

- **`on_source_indexed`**——增量写入。索引作业在 L1/L2 落地之后调用它。
- **`rebuild`**——整份重新推导。`scripts/ops/rebuild_derived.py` 调用它。
- **`prepare`**——同步缝的异步面。

`prepare` 是机制，不是优化，这一点值得说明白。上面有三个面（`source_preamble`、`outline_tail`、`compile_tools`）是在提示词装配里**同步**渲染的：它们没法 await 一次数据库读取。因此投影存在 Postgres 里的组件，读的是一份进程内的镜像。而索引与编译是两个进程里的两种作业——常常还在两台机器上——所以编译进程手里那份镜像**按构造就是冷的**。没有 `prepare`，一条全库尺度的缝会永远安静地渲染一座空文库，而这种失败看上去和"本来就没什么可说的"一模一样。

**一个进程同一时刻只跑一次编译，而这条约束由守卫说出口。** `prepare` 是**进程级**的一次告知：这次作业是给哪个用户跑的。于是一个同步缝读镜像的组件，手里对"这是谁"只有一个答案。两次编译在同一个进程里交错，就意味着第二次的 `prepare` 重新定义了第一次口中的*自己*，而第一次的闸门会拿另一个用户的文库去判一个页面。I1 说的是不存在跨用户的读路径——不是"现行调度器碰巧没走那条路"。所以这条约束被写成协议约束，并被机械地守住：`run_compile` 跑在 `component_job(user_id)` 里，那是一把作用于注册表、从 `prepare` 一直罩到作业结束的 asyncio 锁，同进程里的第二次编译会等。有两点值得知道：**没有**任何组件注册时这把锁根本不会被取（一个没有组件的框架和从前一模一样，这里也不例外）；而拿到了自己那份用户身份的组件面（`compile_tools` 经由它的来源、`source_preamble`）会**断言**它就是 `prepare` 告知的那个用户，否则抛错——绕开这个窗口的调用方会被拒绝，而不是拿着错的镜像被回答。

**以及一次作业可以留下什么。** 组件可以把它从 L0 读到的东西跨作业地镜像下来，键是**真实的 source id**。它不可以拿编译任务给模型看的东西做键：runner 把 source id 别名成每次作业自己的 `sNN` 句柄，交给组件的正是那份*别名后*的来源，于是 `s01` 在下一次编译里指的是另一份来源，而以它为键的跨作业结构会让一次作业的证据被下一次悄悄覆盖。凡是从本次作业的来源上读出来的，都归本次作业所有，随作业一起丢掉。这样并不会丢什么：L0 是在编译入队之前就写好的，所以 `prepare` 从 `ContentStore.list` 刷新时，本次作业自己的来源早已在里面，带着它们真实的 id。

**按作业刷新，不是按进程。** 镜像里的东西必须在每一次 `prepare` 时刷新，而不是在进程头一次听说这个用户时读一遍——一个 worker 可以活好几天，而写那份投影的索引作业自始至终跑在别处。两半可以按「什么会变」用不同的方式刷新：`people` 只把它没见过的 L0 来源折进来（一份来源的说话人和显示名就是它信封里写的那些，永远不变），而把称呼词计数整份重读（计数恰恰是之后每一次索引作业都在改的东西）。第二种若是每进程只读一次，一个长命的 worker 就会永远陈述它第一次作业时的那座文库，而从内部看这一切毫无异样。

**而"增量"要增量在存储边界上。** "只要我没见过的"若是等每一行都过了线之后才做的一次过滤，那它就不是增量：那是每次作业把整座文库搬一遍，省下的只有 CPU。读取本身要带游标：`ContentStore.list_since(user_id, after=(created_at, source_id))`，从旧到新。游标是这个**二元组**，绝不是时间戳本身——同一批导入的来源共享同一个墙钟，`> created_at` 的游标会把其中除一个之外的全部永远漏掉。它之所以能当游标，是因为 `created_at` 是**入库时钟**，在来源被写下的那一刻打上，因此只会向前走；材料自己发生的那一天在 `meta.occurred_on` 里，那不是游标。游标随它所描述的那份镜像一起丢弃——一个活得比镜像久的游标，会从一座这个进程已经不再持有的文库的末尾续读。

**"本轮动过这个页面"是什么意思。** `gate_checks` 只针对本轮写过的文档判定，而"写过"只有一个谓词——框架自己的那个，`compile/patch.py:touched_this_round`：**页面的正文或 frontmatter 与本轮开头时不同，或者这个页面是本轮新建的。** 就是提交的文件表所依据的那个谓词。组件若从文档的一半上另行推导这个答案（比如只比 frontmatter），它的规则就只落到它本该管的那一半写入上——往一个没人动过字段的页面追加一条 claim，和别的写入一样是写入，而这恰恰是这类规则要治的那些页面最常见的后续写入。祖父条款的另一半仍然成立：**没人**写过的页面保持它已有的内容，一个旧的错页因此不会让那座文库之后每一次编译都过不去，而修复在动到它的那一轮里始终是够得着的。

**每一条写正本的通道都要跑这些检查。** 组件的 gate check 是一条正本**字段**不变式，而正本并不知道是哪个进程写的它。所以同一次扇出在三条写入通道上都跑：每日编译（`compile/gate.py`）、全库重组（`evolve/gate.py`，用重组后的树对它所依据的基线判定），以及把一次已审阅的重组落地的 **adopt**（`evolve_service.adopt_evolve_job`，用合并后的树对当前主线判定——分支当初过的是对着更早那版主线的闸门，而评审窗口里那些每日编译恰恰是它还没被对照判过的东西）。三者都先打开组件自己的窗口（`component_job` → `prepare`）：一个进程里若从未跑过编译，它手上的镜像就是冷的，没准备就判定等于对着空文库渲染，然后把每一页都盲放过去。把 evolve 落在外面不是覆盖面上的疏漏，而是规则本身破了一个洞：它新建的页面可以绑上同一场对话里的两个说话人，评审把它落进正本，祖父条款再把它一直留在那里。

整条通道上有三条规则：

1. **组件存下的一切都是派生的（I2）。** 框架里没有任何地方把组件的投影当成权威来读。
2. **呈现的地方 fail-soft，判定的地方 fail-closed。** 三处扇出都是记日志然后继续：组件抛错，代价至多是一份陈旧的投影或一段更薄的提示词；绝不会是一次失败的索引作业、一次失败的重建，或一次失败的编译。组件的**写入时**那几个面是例外，也必须是例外：从一份没能加载成功的镜像里读出来的全库尺度事实，不是一条更弱的检查，而是另一条恒真的检查。必需的读取没能成功的组件会拒绝这一轮（`people.not_ready`）——什么都不写，下一次编译重新读。**就绪是按规则算的，不是按组件算的**：有不止一份镜像的组件要分开记录它们的就绪状态，并且只向需要那一半的那一轮索要它。两份镜像共用一个就绪位，会让一张一时读不到的派生表拒掉根本不需要它的工作（只写主题的编译、对分类法做的 evolve、一座空文库）——更糟的是，会让其中一份读取失败顺手清掉另一份健康的镜像。
3. **组件绝不写正本（I7）。** 这条是被执行的，不是被期待的：注册时交到组件手里的正本对象是 `CanonicalReadOnly`，它只暴露 `list`，别的什么都没有。要放宽这个面，就得在 diff 里做一次看得见的决定，而不是某处的副作用。

## 5. 派生事实直接服务检索；进正本只能搭一次普通编译的车

这条原则挡住了组件变成第二个权威的路，也是动手写一个组件之前最值得先弄懂的一条。

组件随来源到达持续推导事实。这些事实立刻**对检索**有用：`people` 组件的称呼词在全库刚够撑起它的那一刻，就能在快通道里解析一个昵称，并标注为派生。没有任何东西需要先批准它们，因为检索里没有任何东西是永久的——一次查询答完就没了。

正本是相反性质的对象，因此进正本的路也是相反的。一条派生事实进文库**只能搭一次普通编译的车**：组件在编译任务的某份来源下说明自己观察到了什么，契约据此裁定，写入走的是和其它每一次写入完全相同的那道闸门。没有升格步骤，没有审核模型，没有"确认这 40 个别名"的队列。

于是两套称呼并存，且永不合并：

| | 派生（`component_people_terms`） | 正本（frontmatter 里的 `aliases`） |
|---|---|---|
| 谁写的 | 索引作业，机械地 | 一次普通编译，写在总览的字段里 |
| 意思是 | *全库的轮次用这个词称呼这个目标，支持度是这些* | *这个人以这个名字为人所知* |
| 服务于 | 检索，标注为派生 | 知识，带引用且永久 |
| 可撤销 | 可以——它是可重建的 | 可以——总览是快照，整体重写 |

这份设计拒绝的诱惑，是一个把高支持度的词自动升格成别名的批处理。它便宜，而且是错的：`@` 后面那个词可能指的是第三个人，计数是证据而不是结论，而一座把计数升格的文库，已经悄悄让自己的索引当了作者。

## 6. `people` 与 `time` 作为参考实现

### `people`——一个主体是谁

绑定到一个契约族（`PNEUMA_KNOWLEDGE_PEOPLE_FAMILY`，skill 自己的路径模板之一）。

- **frontmatter 作为机器可读的键。** `identities`（`scheme:value`——`mailto:` / `im:` / `meeting:`，按来源契约的记录写）与 `aliases`。两者都属于文档的总览——它此刻对这个主体的画像——由 `rewrite_overview(fields=…)` / `set_fields` 整体写入：这里没有任何东西只增不减，因为快照里写错的那一条，下一次重写就没了，而只增不减的那一条不会。没有第三个字段，而且是有意没有：正本记的是关于一个人**已知**的事，一列「不是他的那些名字」，对着为这个人而来的读者，只是一列干扰项。
- **组件机械拒绝的那几件事**，在写入面（`validate_fields`）拒一次，闸门作为最终裁判再拒一次：身份必须是 `scheme:value`，且全库至多一个页面持有它（`people.identity_shape`、`people.identity_duplicate`）；别名不能是别人的名字——不能是另一个人物页的别名、标题或 slug，也不能是全库来源为某个不在本页上的身份记下的显示名（`people.alias_collision`）。一个叫「Yong BAI, Jie WANG, Fan WANG」的群聊里是三个人，其中一个人的页面不能把另外两个的名字收进去。两条都只针对本轮**动过**的页面判定（§4：正文或 frontmatter 变了，或页面是新建的）——没动过的页面保持它已有的内容，一个旧的错页因此不会让那座文库之后每一次编译都过不去——而冲突的另一侧始终拿整座文库来比。这两个字段上的其余一切，都是契约的判断。
- **在同一场对话里都发过言的两个「人的 id」，是两个人**（`people.identity_cospeakers`）。上一条看不见这一类：一个页面把群聊标题里的三个 id 一并吞下时，它和谁都不冲突——另外两个人根本没有自己的页面。它只从 L0 元数据读出来，每份来源存一个说话人 frozenset，而一个轮次要算证据，得同时满足两件事。

  *是发言，不是在场。* 成员表说的是谁在这个房间里，其中两个 id 完全可能是同一个人的两条通路——页面能持有多个身份正是为了这个。轮次是另一回事：一条带发件人的消息、一段带说话人的会议片段。

  *而且那个 id 得是「人的 id」，不只是一个标识符。* 它必须是渠道自己给某个参与者的把手——渠道会用它来说"这两条消息是同一个人发的"。IM 的 `sender_id` 与会议的 `speaker_id` 正是如此，各自的契约会拿归档的用户表、会议的参会人表去校验它们。**邮箱地址不是**，`email` 因此是这件事唯一保持沉默的渠道：一个人同时用 `alex@work.example` 和 `alex@personal.example` 写信是再寻常不过的事，正确的人物页会把两个都绑上，而 `email/v1` 既没有稳定的行为主体 id，也没有任何同一性关系，"两个发件人就是两个人"根本推不出来。一条硬拒绝若立在契约没能确立的东西上，过它就只剩两条路——丢掉一个真实的身份，或者把规则关掉。等哪天有一个带「人一级」发件人 id 的契约版本出现，这条规则就该改挂在那上面。

  拒绝时点名这两个身份，以及两人都发过言的那一场对话。同一件事从别名一侧照样成立：来源为某个「和本页身份同场发过言」的身份记下的显示名，是那个人的名字——哪怕本页自己的身份也担着这个名字，而这恰恰是仅凭计数就会放过它的那一种情形。和上面那几条一样，只针对本轮**动过**的页面判定；这里更需要如此：这条规则要治的那个页面，此刻就错在一座真实文库里，而它最常见的后续写入根本不动任何字段。
- **闸门唯一逼出来的那个决定**（`people.alias_undecided`），而且**只问一次**。组件能核对的是事实，就拒；只有契约能作的是判断，那就要求它被作出。凡是本次编译的来源里出现、且被某个人物页绑定的身份，全库为这个身份**报出**的每一个称呼词，都必须在本轮结束前要么被记进该页的 `aliases`（大小写不敏感），要么被编译工具 `decline_alias(path, term, reason)` **否掉**。否则每一对（页面，称呼词）出一条违规，写明这个词、它的支持度，以及两条出路——每轮至多列八条，其余计数带过，免得一座大文库把修复轮淹掉。这条规则背后的实测：一个在 31 份来源里被报出、报了 88 天的词，始终没进过那个人的页面，而另外十份文档的 claim 早就在用它。证据没错、提示词没错、契约也没错——模型可靠地做闸门逼它做的事，跳过没有任何东西逼它做的维护。至于答案**是什么**，仍然完完全全是契约的判断。
- **一次否掉什么都不存下来，问题在页面被写下时关闭。** 否掉不是知识——好几个人都担得起的一个敬称是一个真实存在的称呼，只是不是这个人的名字——所以 `decline_alias` 把这个决定记在**作业自己的状态**里，满足本轮的闸门，然后什么都不写：不写 claim，不写别名，不写字段。提交里不留任何痕迹，这正是要点。

  真正让这个问题不再无休止回来的，是文库本来就握着的**两个日期**，两者都是派生的、都可重建（I7）。投影记下 `reported_since`——某一对（称呼词 → 目标）第一次越过报出门槛的那一天；正本仓库则免费记着每一页最后一次提交的日子（`written_on`，一次限定在本族路径下的 `git log` 遍历）。规则只有一句：只有当一页的最后一次提交**早于**某个词开始被报出的那一天，这个词才会向它索要决定。之后被写过的页面，就是被摆到过这个问题面前的页面——那个词就在它来源下的前言里，也在那一轮必须清掉的违规里——而那一轮怎么决定，是那一轮自己的事。本轮新建的页面没有提交日，投影里早于这一列的行没有日期：两种「未知」都意味着**要问**，因为沉默只能由两个确实存在、且顺序对得上的日期挣来。

  于是代价是明说的而不是藏起来的：一轮否掉了却没往这一页写任何东西，下一轮还会再问——没提交，就没回答；一轮否掉了却中止，问题原封不动留在那里。把这个词记进 `aliases` 仍然是把答案变成「是」的方式，而且是唯一值得留存的那一半，因为确认是知识，拒绝不是。

  这是这个决定的第三种形态，前两种正是理由。它曾经有过自己一张表：工具一被调用那一行就写下去了，于是一轮编译随后在闸门前失败、正本毫无变动，一个持久的决定却留了下来。之后它是人物页上的一个字段（`declined_terms`），这把它和提交绑在了一起，却让写入面为保护它背上一整套字段归属机制——并且在每个人的页面上放了一列「他不叫什么」。这个组件**唯一**的存储是那份派生计数（I7），而值得存下来的答案是别名。
- **`people.not_ready`，那条不属于任何页面的拒绝。** 上面每一条规则都要拿一份由 `prepare` 在作业开头加载的全库尺度镜像来量——而镜像有**两份**，分开索要。**来源边界**（来源记下了谁、谁和谁同场发过言）是身份与别名规则据以判定的那一半，只有当本轮写过一个声明了这些字段的人物页、或者本轮的来源里本就带着身份时才需要。**称呼词投影**是那条被强制的别名决定据以判定的那一半，只有当那个决定真的适用时才需要——也就是本轮来源里有身份在场。两者都不问的一轮（只写主题的编译、一座空文库）不会被任何一半拒掉。某一份必需的加载失败时，组件不会退回到它手上碰巧有的东西：一份空镜像会把每一条硬拒绝变成另一条恒真的检查，恰好放行那些规则本来要拒的写入。于是这一轮被拒绝，什么都不写，下一次编译重新读。所以这个组件完整的规则集合是六种：`people.identity_shape`、`people.identity_duplicate`、`people.identity_cospeakers`、`people.alias_collision`、`people.alias_undecided`、`people.not_ready`。
- 给编译模型的 **`find_person`**：先正本精确，再走下面的通讯录式名字键，最后才是称呼词投影。
- 给深召回的 **`enumerate_identities`**：来源在某个日期范围内记录到的全部外部身份的闭合集合，每一项带它的来源数、首末出现、显示名，以及绑定到的人物页——或 `(unbound)`。正是它让"所有和……的人"成为对一份完整候选表逐个作出的判断、残差可见，而不是对检索命中作答。
- 给深召回的 **`person_profile`**，以及一条 **`person` 快路**：整页，当前 claim 在前，被取代的历史带标注。
- **通讯录式名字匹配**，人物组件全部查询共用的那一个归一器（`find_person`、`person` 快路、`person_profile`）。只做精确匹配时，写法一变问题就落空：一个标题是 `Kexin ZHOU`、身份是 `im:Kexin ZHOU` 的页面，用「可欣」——同事真正会打出来的那个形式——查不到。所以页面自己的每个名字（标题、已确认的 aliases、slug，以及身份里属于显示名的那一半）都被展开成一组**键**，问题也用同一个函数展开：拉丁名给出每个词、两种词序的空格式与连写式、以及首字母缩写；中文名给出整名、姓与名两半——复姓照顾到，所以「欧阳锋」是欧阳 + 锋，绝不是欧 + 阳锋——以及这三者的无声调拼音，两种顺序、空格式与连写式都有。两种文字**在拼音上相遇**，这正是中文问题能问到英文页面、英文问题能问到中文页面的原因，而两边都不必存对方的写法。两档：两边共有一个键，或者问题的每个词都是页面的词，是 **tier 1**；问题的某个两字符以上的键是页面某个键的*前缀*，是 **tier 2**——单字问题只精确匹配、绝不做前缀，所以「周」是一个姓氏键，而不是半个文库的第一个字。页面先按档排，再按命中的最长键，再按命中键数。**并列会被返回，而不是被替你定夺**：几个页面同样匹配时，快路把其中至多三个连同各自的 definition 一行返回，打上 `via:name-match tier<n>`，由握着问题的那条链路去选——这次查询选不了。敬称只从*问题*那一侧摘（「可欣姐」→「可欣」），且仅在原形没够到 tier 1 时才试，并且排在称呼词投影之后：全库集中在一个人身上的称呼词是语料给出的证据，摘敬称只是对问题的猜测。这里没有任何相似度打分，什么都不写，严格键也依旧严格——alias 冲突那几条规则判的是**事实**，仍然逐字精确比较。
- **称呼词**，那份持久化投影。一个开在轮次开头、称呼 X 或被下一位发言者接住的词，按（称呼词 → 目标身份）对逐对计数，带上它在全库范围的支持度。哪些值得**说出口**，靠的是**集中度**而不是频次：只有当一个词攒够支持度、来自不止一份来源、且某个目标占了它总支持度的大部分时，才对该目标报出。理由是实证的——在单份会话里昵称和常用短语根本分不开，而放到全库尺度上，`是的` 是所有人都会接的，`阿宝` 却总落在同一个人身上。只靠集中度仍会放过话题词——一个开在消息开头、对方随即回答的产品名，按应答率看和昵称一模一样——所以投影同时数这个词在**非呼格位置**（句中、不在 `@` 之后）出现的次数，只有呼格用法至少占一半（`REPORT_MIN_VOCATIVE_SHARE`）的词才报出：称呼住在轮次的开头，话题住在轮次的每一处。这份来源自己重复了、但全库还撑不起来的词，单独标为 *emerging*。
- **没有任何结构能指向的那些名字**，三条线里最弱的一条，并且被明确标成最弱。一个昵称可以只做过一次称呼、却在第三人称里出现五十次（`和 momo 商量`），这五十次里没有任何轮次结构能指向某个人。所以前言只是把这份来源里重复出现、又对不上任何在场身份、对不上文库已能解释的名字、也没在别处被说过的类名字词列出来——不给目标，不给支持度，有上限且写明截掉了多少。它是给契约的语境判断用的发现线索；进文库的路仍是那条普通的路：写进某个人页面的 `aliases`。

### `time`——把主人的日历做成索引

- 每个 L0 块一行派生数据：该块的 UTC 瞬间，以及它落在**知识主体时区**里的哪一个日历日——就是 ingest 写进块所属章节的那一天，而不是 UTC 日期，因为对 +08:00 的主体来说，本地 00:00 到 08:00 之间发出的一切都带着前一天的 UTC 日期。每一行还记录它是在哪个时区下归一化的、那个时区从哪里来，于是改动主体时区绝不会悄悄把两套日历混在一起。
- 一条 **`timespan(since, until)` 快路**，以及深召回的一对：**`timeline`**（按天或按周的摘要，`granularity="verbatim"` 时逐块读完某一天，让一天可以被*读*完而不是被抽样）与 **`as_of(date, …)`**——后者沿主体的取代链回溯，报出某个日期上生效的是什么。
- 编译任务里每份来源一行：它落在主人日历里的日期与钟点；来源自带时区与主体不同时，两个钟点并列写出。
- **它从不解析自然语言时间。** 路由轮——它能看到 `as_of` 与主体时区——先把"上季度"解析成 ISO 日期，参数才到得了组件手上；非 ISO 的参数会变成一条 `invalid_args` 审计行，而不是一个悄悄不同的区间。组件的七条日期规则列在它的模块 docstring 里。

## 7. 检索：组件决定它知道什么，框架决定展示什么

内置的检索路是同质的排名列表，用倒数排名融合。组件路在种类上就不同：它回答的是**结构化**查询（`person(alias="…")`、`timespan(since, until)`），返回没有排名的精确结果。所以它既不盲跑、也不进融合。

只要有至少一条路被提供，**fast** 就花一轮路由 tool call——把这些路绑成工具，一轮里发出零个或多个调用，绝不循环——然后把选中的路与内置检索并发运行，内置检索从不等它。它们的结果构成第四个证据面，在自己的标题下呈现。每个候选都是普通的 claim 锚点或 `source_id + 块区间`（I4），因此引用别名和结构化回答的准入检查原样适用。

接下来就是这一节标题所说的那条规则。**一条路返回它知道的全部**——整页、整段区间——由 core 决定展示什么：

1. 一次确定性的、不用模型的相关度排序（unicode 感知分词的词面重合、`current`／`superseded` 项、时间接近度，并以路自身的顺序作为并列时的定序；接上重排器时它替换词面重合项，失败则 fail-soft 退回）；
2. 把该路声明的上限花在**这个**顺序上，并带两条底线——只要返回过窗口就至少留一个，且每个不同章节至少留最相关的一条 claim；
3. 一个约束整个面的字符预算（`RECALL_COMPONENT_BUDGET_CHARS`），因为条数约束的是一条路贡献了多少件东西，而不是它们有多大。

每一次截断都**被描述而不是仅仅计数**：少了哪些章节、哪些日子，过长的摘录按块边界裁剪并写明没展示的块区间。一次查询悄悄返回它的前 N 条，读起来就是"这就是全部了"，而这恰恰是一次枚举最不能说错的一句话。

把上限花在**文档**顺序上，正是那条能回答问题的 claim 恰好掉到边缘之外的原因。所以排序、截断、去重与预算只在 core 里说一次，绝不写进组件。

还有三条规则完成这次合并：

- **去重从不打扰排名面。** 它们带着相关度顺序，而选择器或重排器已经判过。所以让步的是组件面：它只展示排名面没有的，并说明隐去了多少；排名面上被查询同样命中的 claim 会带上 `via:<path>` 标签——不复制一遍，也把佐证说清楚。
- **在 `evidence_strategy=select` 下**，组件结果不再绕过选择器，而是作为自己的一组进入带编号的候选池；被选中的部分渲染进普通证据面。
- **深召回走相反的纪律**——完整优先于上限。它的组件工具分页，每次响应结尾都给出取回其余部分的确切调用。

路由选了什么、传了什么参数、什么因为格式不合法被拒、哪条路超时，都是 telemetry，不是沉默：它们会到达 HTTP 响应和 Recall 界面。没有路被提供时——或 `RECALL_COMPONENT_PATHS` 关掉时——就没有路由调用，通道与没有这条缝时逐字节相同。

## 8. 写一个组件：清单

1. **说清它回答的是哪个排序答不了的问题。** 如果更好的检索就能答，那答案就是更好的检索。组件靠把一次检索变成一次查询、或把一个开放集合变成闭合集合，来挣得自己的位置。
2. **把它绑到一个契约族上**，用路径模板。这个族就是它的闸门检查与提纲行的作用范围。
3. **定下它存什么，并证明它是可推导的。** 先写 `rebuild`：如果这份投影没法只从 L0 与正本重新推导出来，那它就不是投影，是权威，设计已经错了。
4. **只实现需要的那几个面。** 每个面都有空操作的默认实现。忍住把表填满的冲动。
5. **让正本这一面保持只读。** 注册时它是 `CanonicalReadOnly`；确实需要另一种读法，就在那里加一个方法，让 diff 把这件事说出来。
6. **让这些缝在事实上 fail-soft，而不只是扇出上 fail-soft。** 框架保证一个抛错的组件不会让作业失败；它不保证抛错之后你的投影还是自洽的。写入尽量幂等，重建要显式。
7. **返回全部，不要自己截断。** 一条路的 `cap` 是一份交给框架去花的声明；在组件内部截断，等于把排序的决定权从唯一看得见问题的那一层手里拿走。
8. **只说你观察到了什么，绝不说该得出什么结论。** 工具描述交代东西从哪来、这个工具做什么。判断力属于契约——一旦发现自己在写"只在……时才绑定"，那句话该去编译契约指南里，不该在工具描述里。（机制先于劝说，落到一个组件上就是这样。）
9. **测这条缝，不只是测逻辑。** 至少要有：闸门的那次拒绝、投影的重建复现出增量的结果、按租户隔离（I1），以及组件不注册时每个面都原样不变。

## 9. 测量说的是什么

同一 harness 上的两次 A/B：LoCoMo-refined，A 组关闭组件，B 组开启 `people` + `time`，其余逐字节相同（同一份契约、同一批模型、同样的 `select + structured` 回答路径、官方 refined LLM judge，1,382 道完整配对的题）：

| 轮次 | A（组件关） | B（组件开） | B − A | 精确双侧 McNemar |
|---|---:|---:|---:|---:|
| v3 | 81.19% | 81.77% | +0.58 pp | p = 0.594 |
| v4 | 80.61% | 81.55% | +0.94 pp | p = 0.3902 |

**老实读这张表：两轮的总分差异都不显著**——p = 0.594 与 p = 0.3902，两个点估计都稳稳落在一次 10 场对话的配对实验能分辨的带宽之内。也都没有达到事先定下的 2 pp 实质增益门槛。正确的说法是*"组件被大量用上了，而且没有让质量下降"*，不是*"组件提升了准确率"*。

作为尺度参照：同一 harness 测到过一个**真实**的效应——把回答路径从默认换成 `select + structured`，两座文库分别移动了 +5.2 pp 与 +6.3 pp，p < 1e-6。这里的显著结果长这样，上面那两行也该拿它当尺子来读。

同一轮实验确实立住了的是下面这些，因为它们是计数而不是估计：100% 的题都被提供了路由，其中 99.20% 选出了路；96.96% 的题拿到了非空的组件证据；94.07% 的回答至少带一个 `via:` 标签；诚实截断在 1,195 道题上报出了 47,421 件被舍去的条目，而不是悄悄裁掉它们。在一份真实语料上，这条缝几乎每道题都被用上——这正是那条得先验证、总分才值得拿出来争的性质。

组件带来的价值，按构造也大半对一个总分不可见，因为这套 benchmark 的题目本来就不是为了需要它而写的。闭合集合的枚举只在有残差的题上有意义；日历索引只在点名了某个时段的题上有意义。把这些平均进 1,382 道题里，稀释掉的正是要测的那个效应。这是一个把切片有意测出来的理由，而不是给总分开脱的借口——而 v4 里那些切片，全都没做多重比较校正，同样不显著。
