# 编译契约怎么写

[English](compile-contract.md) | **简体中文**

编译契约是一座文库的宪法。它教编译模型在你的领域里做判断：什么值得被长期记住、记到哪一页、以什么口径记。它是判断力，不是规则清单——这份指南讲的就是这份判断力怎么得出。

契约是一段 markdown 正文，加四个声明字段——`skill_id`、`version`、`path_templates`、`contract_rules`。scaffold 的模板把字段写成正文上方的 frontmatter，正文是编译模型每次任务都会读到的指令：

```markdown
---
skill_id: my-knowledge
version: app-v1
path_templates:
  - people/{slug}.md
  - projects/{slug}.md
  - topics/{slug}.md
---
（记什么、记到什么粒度、用什么口径——即本指南的主题）
```

框架本身不解析这里的任何东西。注册是显式的——`SkillVersion.from_parts(skill_id, version, instructions, path_templates, contract_rules)`——`instructions` 就是 markdown 正文的逐字节原文。frontmatter 是 scaffold 自己的约定（它的驱动器读出字段、剥掉引导注释后再注册）；以编程方式接入的应用直接在代码里声明这些字段。`content_hash` 是这五个部分的 sha256——由 `from_parts` 计算，永不手写——盖进契约产出的每一个正本版本，任何文库状态都能追溯到产生它的那份契约。改契约就是注册一个新 `version`：它塑造将来的编译，永不改写已经记下的内容。可以直接填的骨架在 [`scaffold/templates/contract.zh.md`](../../scaffold/templates/contract.zh.md)，参考契约在 [`packages/pneuma-knowledge-strategies/`](../../packages/pneuma-knowledge-strategies/)，完整的落地示范在 [`examples/opc/`](../../examples/opc/)。

## 1. 核心推理：类型 → 隐含用法 → 入册义务

契约里其余一切都是这一个推理的应用：**现实世界中每种类型的知识，天然暗示它将来会被怎么用；而隐含的用途决定了什么必须被记下来。**

- 反复发生的**事件**，暗示一条**时间线**；
- 在推进的**项目**，暗示一份**持续的进展记录**——目标、决策、里程碑、状态变化；
- 反复出现的**协作者**，暗示一份**不断累积的往来记录**；
- 一个东西**有好几种叫法**（昵称、头衔、缩写、代号），暗示一份**记着别名**的主体页——否则同一主体的故事被名字劈开，检索时再也拼不回来。

两条纪律钉住这个推理：

1. **从材料推，不照抄预设清单。** 上面四条是示范，不是清单。你的领域会暗示它自己的用途；清单会漏，推理不会。用途也随材料演进——数据变了就重推。
2. **用途依赖的事实必须是一等公民。** 检索只能重新浮出被记下来的东西，变不出没人写过的事实。所以「这条用途要靠哪些事实才答得出来」的答案，就是入册义务清单。

动笔前值得知道的两个坑：

- **编译模型偏爱结果，容易丢掉起点。**「什么时候开始的」「谁第一个接手」——这类事实最容易在压缩成结论时蒸发。只要有任何用途要算时长、排先后，就把起点写成显式义务，和终点同等分量。
- **义务成链。** 一次交接同时欠着三条事实：谁交出去、谁接下来、哪一天。推完一条义务，追问一句：要答出它，还缺哪条事实。

契约里写的是推理的**结果**——具体到族的义务（「这一族必须记下 X」）——不是推理过程本身。

## 2. 主体粒度：一个独立演化的东西，一份文档

这是归置知识的第一原则。一页装所有会把文库压塌：页面无边界地长大、轮转被迫频繁触发、每次检索都命中同一张大页，而「这件事后来怎么变的」再也读不出来——二十个故事交织在同一卷里。

该不该立页，只问一个问题：**它会独立演化吗？** 还会再出现的人、有下一步的项目、会回来的主题——立页。一次性的材料、路过一次的名字——不立，留在 L0，需要时检索得到。

对 `path_templates` 里的每个族回答两件事：**它收什么**（哪些事实归它），以及**新主体什么时候够格开页**（第一次出现就开，还是第二次带着实质信息出现才开）。

**归属错误是最贵的一类错：事实是真的，主体是错的。** 它比漏记更难发现——文库看着什么都不缺，只是挂错了地方；而且编译期分错了页，检索期再聪明也救不回来。所以要按族写清**收什么、不收什么**——尤其是天然互相吸事实的相邻族（人与项目、项目与主题、事件与参与者）。别名记录（§1）是同一种失败在名字维度上的形态：不记别名，一个主体就悄悄变成好几个。

## 3. 什么进正本

对每条候选事实只问一个问题：**它将来会被用到吗——行动、判断、解释、协作、复盘？** 会，入册；不会，原文和索引留着它——L0 直取与词法检索无条件可达，从不依赖契约怎么写——不入册也不丢。正本因此可以把门槛定得很高：它是被判断筛过的少数事实，不是原文的副本。

契约在这一节该写的，是你的领域里**最典型的两三条「值得」与两三条「不值得」**，不是通用清单。个人知识场景的中性基线长这样：值得——明确的决定及其理由、约定与验收条件、带日期的里程碑、反馈的原话、实质性的状态变化；不值得——寒暄、没被采纳的建议、一次性的情绪。你的领域多半不长这样，整段重写。

三个口径是同一判断的延伸，写法始终是**先问用途，再定口径**：

- **证据。** 转述不等于同意，提案不等于决策，「跑通了」不等于「验收了」，「第一次被提到」不等于「开始了」。写清你的领域里谁的话算数、模型和工具的输出算什么、数字要带什么限定。
- **时间。** 相对时间（「下周一」）锚定到材料自带的发生日期并保留原话；只有材料或知识主体的日历给出了无歧义口径时，才解析精确日期或区间，否则保留带锚点的表达，不猜端点。
- **隐私。** 凭证、证件号是框架红线；在此之上写你的领域永远不记什么。

**模态通过证据链进入，不能靠把一切压成文本冒充。** 先确定编译模型及其实际 provider 路由，再选择上下文拼接。路径支持原生媒体时，保持消息顺序、让原始媒体可从稳定的 L0 地址取回，并把图片／音频／文件 content block 绑定到引入它的文字轮次；不支持时，使用明确标成派生表示的 caption、转写或 OCR，注明生成者并继续链接原始媒体。把 URL 渲染成文本不等于送入图片。一个具体例子：OpenAI [GPT-5.6 图片输入全系](https://developers.openai.com/api/docs/guides/images-vision)——Sol、Terra、Luna——都能接收原生图片；按证据所需精度选择 detail，并实测 token 与延迟。经过网关时仍须做端到端能力验证。

把每种表示都当成独立的可选观察。缺少图片 URL 不能顺带丢掉已经存在的 caption；缺少 caption 也不能顺带丢掉 OCR、转写或原始媒体。验收上下文转换时，应在归一化前后逐字段比较所有获准输入字段及其顺序与摘要；拿渲染结果和同一个渲染器拼出的「期望字符串」对比，只能证明自身一致，发现不了字段在更早处已被丢弃。原生媒体不可用时，带标签的派生表示仍是可用证据：保留其 provenance，但不能仅因它是派生表示就压掉实质观察，或给每条 claim 都套上通用保留语。

契约负责的是这条路径末端的判断：写清某个主体族能否把对原始媒体的直接查看当作证据、派生 caption/OCR 如何归因、以及它们的不确定性何时与判断有关。契约救不了一条从未把媒体送到模型的上下文管道。

**密度是这一节有没有落地的体检指标。** 一批材料编出的事实条数明显低于常识预期，那很少是克制——多半是某些族的义务没落地，时间线和多跳问题会跟着一起哑掉。

## 4. 机制的归机制：这些不用写

框架已经机械强制了一批规矩：每条 claim 必须带引用、锚点系统分配且不可变、已结卷只读、路径归属、L0/L1 无条件可达（[架构 §5、§9](../architecture.zh-CN.md)）。在契约里重复任何一条都是白花 token——闸门不读散文。

文档前置里的 `title` 同样是机制，而且是派生的而非存储的：系统从文档第一行 `# ` 标题读出它——取的是标题**说出来的那段文字**，锚点标记与行尾的系统注释都会被去掉，这和提纲、鸟瞰展示时的读法是同一个，所以存下来的名字与显示出来的名字不可能对不上——并在每一条「序列化了本轮改动过的文档」的写入路径上都这么读：编译草稿、rollover 写下的两份文件、把一次已审阅的重组落地的 adopt 合并，以及卷内链接的修复通道（那条通道在链接 href 之外逐字节不动，派生 title 是它唯一明说的例外，而不是让一个错的 title 一路带下去）。本轮没被写过的页面保持逐字节不变、连过时的 title 也不动，等它下一次被写时自然收敛。此外，`create_document` 里写的 title 会被它替换，`set_fields` 直接拒绝这个字段——所以契约要决定的不是这个字段，而是那行标题；一个人的**职务**不是他那一页的名字（它属于总览的 `definition`，或者那个族的某个字段）。

拿不准某条该不该写时，用这条判据：**违反了会被机械拒绝的，是机制，不写；只有人读了文库才能分辨对错的，是判断，才写。**

## 5. 总览：一份文档怎么说它自己

每份文档都可以带一段**总览**——断言账本之上一段有界的头部，分四个槽位：`definition`（一句话：这是什么／是谁）、`summary`（现在的状态）、`introduction`（背景、由来、为什么重要）、`connections`（指向其他主体页面的链接，每条一行写清关系），外加属于同一幅画像的结构化 `fields`。编译模型用 `rewrite_overview` 写它：一次调用整体替换整段区域，账本不动。

总览是一张**快照**，不是变更记录；每一次调用都是对已经立在那里的那一版所作的判断——只有四种结果：保持（不调用）、合并或改写（带上整段新内容调用）、丢弃（四个槽位全空且不带 fields，区域被删除，文档回到只有断言）。「上一版确实被看过」是机械保证的，不靠嘱咐：`rewrite_overview` 和 `set_fields` 会拒绝本次编译没读过的文档。

机制不用你重述：`rewrite_overview` 会当场拒绝这次调用——在写下任何一个字节之前，一次点名所有不合格的块——闸门则留在它身后做最终裁判。两者合起来限住了区域大小、要求每个块（`connections` 里的每一条也算）都引用一条账本断言或一段来源、拒绝超出一个短块的 definition、并拒绝指向不存在文档的 connection。它们还会**要求**你写：账本超过 `OVERVIEW_REQUIRED_AFTER_CLAIMS` 条断言（默认 8）之后，本轮改动过的文档至少得有一个 `definition`，`finish_compile` 先拒一次、闸门再拒一次——一个主体刚立时确实可以没有画像，但一份已经装下这么多知识、却不给出任何形状的页面，是机制来补的缺口，不是你的契约要做的判断。归你的是**措辞**——对你这座文库所立的那些主体来说，"当前画像"意味着什么。人物页的契约可以说 definition 写的是与所有者的关系而不是职位头衔；产品页的契约可以说 summary 先讲已经定了什么、还悬着什么。把"这一族的读者应该从四行里知道什么"讲清楚，闸门管的那些一句都别写。

有一条判断值得明说，因为它确实是判断而不是机制：**什么时候该重写**。总览是对账本的一次解读，所以它随解读变化而动，不随账本变长而动。一份告诉编译器"对我的主体来说什么算画像变了"的契约——一个职务结束了、一个决定拍板了、一段关系开始了——换来的是值得一读的总览；一份只说"保持更新"的契约，换来的是每一轮白重写一遍。

## 6. `supersede_claim` 与 `edit_claim`：世界变了，还是我写错了

两个写动词看着可以互换，其实不能。`edit_claim` 就地改写一条 claim，管的是**写下时就错了**的那种：听错的数字、安到别人头上的名字、把来源说过的话拔高了的句子。`supersede_claim` 记的是另一回事——那条 claim **当时是对的，后来世界变了**：职务、东家、期限、价格。前任留在页上，新 claim 紧随其后，作为同一事实的当前状态：

```markdown
- X 是恒印印刷对接人 [cite: s01 ¶8-9] <!-- c:a1f3 -->
- X 自 2026-05 起任新华印务采购总监 [cite: s02 ¶3] <!-- c:c07e --> <!-- supersedes: c:a1f3 -->
```

用 `edit_claim` 去改一个状态，等于把上一个状态从可读的页面上抹掉——它只剩在 git 里——「什么时候变的、凭谁的话变的」从此答不出来。**这是判断，而且是下游谁都替编译器做不了的判断：契约不说清自己哪些事实是「状态」，换来的就是本该留下历史的地方留下了修正。**

机制不用你重述：前任逐字节保留并冻结——正文再不可改，工具面会直接拒掉对它的 `edit_claim` 并点名后继；后继拿到系统分配的锚点和一个 `<!-- supersedes: c:xxxx -->` 标记，沿用前任的块形态，且必须自带 `[cite:]`——没有新证据的状态变更在写入处就被拒，不是靠散文提醒。链恒为线性无环：一条取代一条，一条至多一个后继。

归你的是：**你的哪些族持有随时间变化的状态，以及在你的领域里什么算「换了一个状态」而不是「改错」。** 一个人的职务、东家、联系渠道是状态，籍贯不是；一个项目的期限、负责人、状态是状态，某个决定当初的理由不是。边界真正薄的地方要写具体——「一直是 12，当时打成了 21」是修正，「从 12 涨到 21」是新状态——材料通常说得清，前提是契约让编译器去看。

它换来的东西不用再多写一个字：文档的**当前视图**（没有后继的那些 claim）、单个事实的**历史**（它的链，从根到头），以及在启用 `time` 组件时的 **as-of** 回答（沿链按各条 claim 所引来源的日期取值）。

## 7. `people` 组件：identities、aliases，以及两者都不是的那些词

`people` 组件叠在你的某个族上时，这一族的文档带两个机器可读的 frontmatter 字段。

**`identities`**——`scheme:value`，scheme 来自来源边界，就是官方来源契约记下的那几种（`mailto:`、`im:`、`meeting:`），编译器不自己发明。一个身份在全库唯一：第二个页面来认领它会被闸门拒绝。正是这份唯一性让它成为一把机器可读的**键**，而不是又一个名字——有了它，「所有和……的人」是在一份从 L0 枚举出来的闭合候选表上逐个判断（没被绑定的身份也照样列出），而不是对检索命中作答。

**`aliases`**——材料确认属于这个人的每一种称呼形式。一个人进到文库里往往带着好几种：一个中文名一个英文名、单独一个姓、同事在用的昵称、某个项目给的代号。这个字段就是它们全部的落脚处，因为之后每一次查询都拿它来解析——问题用一种写法提出，页面用另一种写法记着，没被记下的那一种就是这道问题错过的那一页。框架用机械手段把这道缝收窄，但并不合上：人物查询同时按通讯录的方式匹配——拼音、姓名分离、两种顺序、首字母缩写——所以「可欣」能问到一个标题为 `Kexin ZHOU` 的页面，哪怕这一页从没这样写过自己。那是检索：它带排序，它被标成一次匹配而不是一次声明，几个人同样匹配时它把他们一并交回。材料确认过的形式仍然该写进这个字段，因为记下来的形式是精确的、无歧义的、长期有效的。它只收材料**确认**过的形式，而怎样才算确认，是你要定的门槛（见下）。框架负责供给证据、并把问题逼出来：每份来源底下写出全库对在场这些人集中使用的称呼词，闸门则要求它们每一个都在本轮结束前，要么被记进这里，要么被 `decline_alias(path, term, reason)` 否掉。**这个问题只问一次。** 一次否掉是本轮的回答，哪里都不存——不写 claim，不写别名，不写字段，页面上不留一个字——因为「不是某人的名字」并不是关于这个人的知识。真正把问题永久关掉的，是这一页**被写下**：框架知道某个词从哪一天开始被报出，也知道这一页最后一次提交是哪一天，于是之后被写过的页面就是被摆到过这个问题面前的页面，从此不再问，不管它当时怎么决定。在你否掉的那一轮里把这一页写掉，这个词就结束了；否掉却什么都没写，下一轮还会再问——这是对的：没提交，就没回答。放着不管，两样都不会发生，这正是一座真实文库量出来的结果：一个在 31 份来源里被报出、报了 88 天的词，从没上过那一页，而另外十份文档的 claim 早就在用它。

**敬称通常不是别名**，而且它正是值得你专门作一次决定的那一类。「周总」是头衔加姓：人们确实这样称呼某个人，也确实这样称呼每一个够格的姓周的人——所以它标识的是一段对话里的一个角色，而不是一座文库里的一个人。通常的结果就是 `decline_alias(..., reason="honorific")`——理由是说给这一轮听的，什么都不存下来，页面也不例外。当你的材料显示这个形式已经钉死在一个人身上时——全库只有这一个姓周的、书面材料里也这么称呼他、当事人自称也用它——就往另一边判；并且把你想要的判法写进契约正文，因为两种读法都站得住，而只有一种是你的。

两个字段都属于文档的**总览**——它此刻对这个主体的画像——由 `rewrite_overview(fields=…)` / `set_fields` 整体写入，和旁边那几个文字槽位完全一样。总览里没有任何东西只增不减：字段是一张快照，某个值能不能留下来，取决于本轮对已有内容的判断。写错的那个之所以还修得掉，靠的正是这一点。被否掉的那些词没有第三个字段可去，而且是有意没有：页面记的是关于这个人已知的事，不是一张「以后别再问了」的便条。

这些字段上有三件事是**事实**而不是判断，框架机械地拒绝它们——在写入面拒一次，闸门再拒一次，且只针对本轮真正动过的页面。*动过*的意思是这一轮改了页面的正文**或** frontmatter，或者新建了它：一次只往人物页追加一条 claim、不动任何字段的编译，也是写过了这个页面，页面就要为自己声明的东西负责。没人写过的页面保持原样，一个旧的错页因此不会卡住之后每一次编译——而某一轮真动到这样的页面时，修复只值一次 `set_fields`。身份必须是 `scheme:value`，且不能有两个页面持有同一个。**一个页面不能持有在同一场对话里都发过言的两个「人的 id」**——自己开口说过话，正是让他们成为两个人的那件事，不管其中哪一个有没有一个能与之冲突的页面。「人的 id」指渠道自己给某个参与者的把手：IM 的 `sender_id`、会议的 `speaker_id` 是，邮箱地址不是——一个人用工作邮箱和私人邮箱各写一封再寻常不过，正确的页面会把两个都绑上，所以邮件线程对这件事不贡献任何东西。**别名不能是别人的名字**：不能是另一个人物页的别名、标题或 slug，也不能是来源为某个身份记下的显示名——而这个身份不在本页上。一个叫「Yong BAI, Jie WANG, Fan WANG」的群聊里是三个人，其中一个人的页面不能把另外两个的名字收进去。

**编译任务里每个来源下面那行称呼词是「去查」的提示，不是结论。** 它是对轮次结构的算术——这一轮在称呼谁、下一轮谁接的话——报出来的是一份在各身份之间的分布；而 `@` 后面那个词完全可能指的是第三个人（`@X 阿宝怎么样`，称呼的是 X，问的是别人）。框架的工具描述只把分布摆出来就打住，这是有意为之：**一个词什么时候够格成为正本别名，是契约的判断，而这份判断就该写在这份指南里。**

把它写成材料必须跨过的一道门槛。一个词够格成为别名，是在当事人**跨轮次、跨来源地反复应答它**、**自称用它**，或者**有人直接把等价关系说出来**的时候。一次同轮共现不够，一次前后相邻也不够：在单份会话里，昵称和「随口一句、恰好被下一位接住」的常用语，形状一模一样。先不绑不丢东西——这个词照样在计数，等全库攒够支持度，它会带着更硬的证据在下一份来源底下再回来。写早仍然比写晚贵：一条被当作确认的别名，是之后每一次查询解析的依据，它会一直立在那里，直到某一轮真正动这一页时另作判断。

那行上有两个标签，说的是一个词有多少分量。**REPORTED**（报出）指它在全库范围的支持度集中在同一个目标上——出现次数够、来自不止一份来源、且大部分都指向同一个身份、并且多数用在呼格位置（一个住在句中的词是话题不是称呼，无论被应答多少次都不报出）；**EMERGING**（浮现）指它只在这份来源里反复出现，全库还撑不起来。报出的那类才是一页可以据以行动的，浮现的那类是让编译器看着一个昵称正在成形。两者都不是绑定；正本永远赢：一条已确认的别名，不会被一个计数推翻。

## 8. 验收环

契约不是想对的，是**用出来的**。一轮的形状：

```
在空库上重建 → 读鸟瞰 → 拿真问题问 → 判断 →
改契约（新 version）→ 重建 → 再看
```

- **在空库上重建。** 契约改动只塑造将来的编译、永不改写已有正本，所以看一次修订最干净的方式是从头建。
- **先读鸟瞰。** 该立的主体立了没有？有没有一页什么都收？有没有一堆只出现过一次的名字各占一页？
- **拿真问题问，带上引用。** 看的不是答得漂不漂亮，而是**答案依赖的事实在不在页上**——答错时先分清病因是「没入册」还是「没取到」，两者的药完全不同。
- **验证归属，不验证字符串出现。**「这个日期在库里某处出现过」是虚假的安心——一年下来几乎每个日期都在某处出现过。事实挂在对的主体上、绑在对的对象上，才算记下了。
- **看结构、写判断。** 「有变化」不是目标，对未来使用更优的建模才是。一次讲得清道理的「不改」也是好答案，同样写下来。并且永远不要凭一两个问题的对错改契约——同一批问题重问一遍，总有一小撮自己翻面；驱动修订的是结构性变化（某类问题整体好转、某个主体的时间线第一次连上），不是单点噪声。

两三轮之后，文库开始看着对了。那就是交付。

「拿真问题问」这一步也有机械化的形态：可选的**覆盖挑战**（见[配置](../reference/configuration.zh-CN.md)）在每次编译后自动跑一轮——依据材料与你的契约盲出题、对照已入册的 claim 判定、确认的缺口经一次过闸门的补偿编译回填。它不取代这个验收环：挑战审计的是入册覆盖，而「建模本身对不对」只有你能判。
