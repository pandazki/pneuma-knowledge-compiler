# The single-machine edition — `pkc` and `~/.pkc`

**English** | [简体中文](single-machine-edition.zh-CN.md)

Status: design. Builds on [coding-agent-mode.md](coding-agent-mode.md) (the door, the skill,
the backends) and [steward-owner-visitor.md](steward-owner-visitor.md) (the roles).

## 1. Two shapes of the same framework

Until now a deployment has had one shape: a **project directory** — generated by the
scaffold, carrying its own middleware stack, its own `.env`, its own engine, an API and a
worker of its own. That shape stays: it is the right one for an application embedding the
framework, for a team with several libraries on separate stacks, and for every test.

This page adds the second shape, for one person on one machine: **`pkc` plus `~/.pkc`**.
One shared infrastructure, started once and kept; any number of libraries as tenants on it;
a coding agent — Codex, Claude Code — as the whole interface, taught by one skill dropped
into the harness the person already uses; the console optional. Nothing about the library
changes between the two shapes: the same four levels, the same door, the same gate, the same
engine directory. What changes is where the machinery lives and who starts it.

| | Project shape | Single-machine edition |
|---|---|---|
| infrastructure | one stack per project, in the project's compose file | one stack per machine, under `~/.pkc/infra`, started once |
| a library | the project | a named tenant: `~/.pkc/libraries/<name>/` |
| configuration | the project's `.env` | `~/.pkc/config.yaml` + `credentials`, plus each library's engine |
| processes | `app.py up`, `server.py`, `worker.py` per project | `pkc up`: the middleware and one worker daemon for the machine; `pkc console` when wanted |
| the agent's entry | the skill installed into the project | the skill installed into the harness's user-level skills directory |
| where the Owner stands | `cd` into the project | anywhere; the library is chosen once, or bound to a directory |
| isolation | by stack | by tenant (I1), on one stack |

The principle behind the split: **the framework is the same code with two settings
assemblies.** A project's `.env` and a home's `config.yaml` both resolve to one `Settings`;
`pkc`, the API and the worker never know which shape they run in.

## 2. Roles and motivations (the additions)

The roles are the frame's. What the edition adds is one Owner motivation and two Steward
ones, and they are the cold start the harness solves:

| | Motivation |
|---|---|
| O13 | **Start once, keep forever.** Set the machine up one time — infrastructure, a key, a name — and never answer the same question again, in any later session, in any directory |
| S10 | **Know what is already here.** A Steward started anywhere finds the machine's libraries, checks what still works, and continues the right one instead of proposing a new one |
| S11 | **Bring what it already knows.** The Steward runs in the harness the Owner has used for months; its memory of the Owner is the profile's first draft, and the Owner corrects rather than fills in |

## 3. Stories

- **3.1 First time (v1).** The Owner has Codex and Docker. They install the skill once
  (`pkc skill install --global --backend codex`, or the one-liner the README gives) and open
  Codex anywhere: *"set up my knowledge library."* The Steward runs `pkc home status` —
  nothing — and `pkc setup`: it writes `~/.pkc/config.yaml` with probed free ports, starts
  the middleware (`pkc up`), asks the two questions a cold start has (who the Owner is, in
  the form *"I believe you are X, a Y, writing in Z — correct me"*, and whether to run
  without semantic retrieval or with a key), creates the first library (`pkc library create
  notes`), and says where material goes. Ten minutes, two questions.
- **3.2 Weeks later, another directory (v1).** *"Add these meeting notes to my library."*
  `pkc home status` lists `notes` (stack up, key present, skill fresh, last used Tuesday);
  the Steward ingests into it. No setup, no question.
- **3.3 Two libraries (v1).** *"Keep the client work separate."* `pkc library create acme
  --from notes` copies the engine's contract as a starting point; `pkc library use acme`
  makes it current, or `pkc library bind acme .` binds it to this directory so a session
  opened here lands in it. Tenants are isolated by I1 on one stack.
- **3.4 The stack went away (v1).** Docker restarted, ports moved, or the machine is new.
  `pkc home status` says exactly which probe failed; `pkc up` re-creates what the config
  names; a library's data is in the home's data directory and comes back untouched.
- **3.5 Init is remembered (v1).** Every step the setup completed — stack, key, profile,
  skill, first compile — is recorded per library; a Steward that finds a step done never
  redoes it and never asks its question again.
- **3.6 The console when wanted (v1).** `pkc console` starts the API and serves the web
  console over the home; the Owner lens's Steward view runs in the library's directory.
- **3.7 A project joins the home (v1).** A scaffold project can `pkc home register <dir>`
  so `home status` lists and probes it beside the home's own libraries; it keeps its own
  stack and `.env`.

## 4. Rulings

1. **One home per machine, `~/.pkc` (`PNEUMA_KNOWLEDGE_HOME`).** It holds state and
   configuration — never a source, a claim, or a record. A second machine starts with an empty
   home; a library moved by copying its directory is complete without it.
2. **One infrastructure per machine, N tenants.** Postgres, Qdrant, Meilisearch and RustFS
   run once, from a compose file `pkc up` generates out of `config.yaml`; data volumes live
   under `~/.pkc/data/`. A library is a tenant on that stack, isolated by I1 as every tenant
   is; its canonical repository lives under `~/.pkc/libraries/<name>/canonical/`.
3. **Settings assemble from the home exactly as they assemble from a project.** Precedence,
   lowest to highest: framework defaults → `~/.pkc/config.yaml` → the library's engine
   directory → `~/.pkc/credentials` for keys the engine may not hold → the process
   environment. `pkc`, the API and the worker read one `Settings` and never a home path.
4. **Credentials are provided once and never copied.** `~/.pkc/credentials` (mode 0600)
   holds `KEY=value`; no library directory and no engine ever receives a key. A key present in
   the environment wins for one process.
5. **Choices are recorded, and a recorded choice is never asked again.** Per library:
   `semantic_retrieval`, the embedding spec, the backend; per home: the defaults a new library
   inherits. The Steward reads them from `pkc home status` before it opens its mouth.
6. **The library is chosen, not guessed.** Tenant resolution: `--user`/`--library` on the
   command → `PNEUMA_KNOWLEDGE_TENANT` in the environment → a `.pkc` binding in the working
   directory or an ancestor → `~/.pkc/current`. With none of these `pkc` refuses and lists the
   libraries; it never picks one for the Owner.
7. **The skill is global and the contract is not.** The harness-level `pkc-steward` skill
   teaches the door, the round, the postures and the home; it names no contract, because it
   serves every library on the machine. Each library renders its own reference package under
   `~/.pkc/libraries/<name>/skill/` (contract, compile instructions, CLI, gate — the same
   generator, the same hash stamped as `Executor-Skill`), and the global skill's first move in
   a library is to read that package where `pkc library show` says it is.
8. **The worker is the machine's, the round is the agent's.** `pkc up` starts one worker
   daemon (pid file under `~/.pkc/run/`) that drains index, projection and rebuild jobs for
   every tenant; under an agent executor it leaves compile jobs for `pkc draft open` unless the
   library's unattended posture is on, in which case it launches the harness as the project
   shape does. `pkc down` stops what `pkc up` started and nothing else.

## 5. The home

```
~/.pkc/
  config.yaml            framework: {repo | package}; infra: {compose_project, data_dir, ports: {postgres, qdrant, meili, rustfs}};
                         defaults: {backend, language, semantic_retrieval, embedding}; console: {port}
  credentials            KEY=value, mode 0600 (OPENROUTER_API_KEY …)
  current                the library name a session lands in when nothing else chooses
  registry.json          scaffold projects registered with `pkc home register` (path, last probe)
  infra/
    docker-compose.yml   generated from config.yaml by `pkc up`; regenerated when config changes
  run/                   pid files and logs of the worker and the console
  data/                  postgres, qdrant, meili, rustfs volumes
  libraries/<name>/
    library.yaml         tenant id, created, choices {semantic_retrieval, embedding, backend},
                         steps {infra, credentials, profile, skill, first_compile}, last_used, bindings
    engine/              the engine directory (its own git repository), from the framework's templates
    canonical/           the canonical git repository
    skill/               the rendered reference package: SKILL.md (library-specific pointer), references/, skill-version.json
```

`library.yaml` is the init state the frame asked for: a step is written when the command
that owns it completes (`pkc up` → `infra`; a key into `credentials` → `credentials`;
`pkc profile confirm` → `profile`; `pkc skill render` → `skill`; the first `pkc draft finish`
→ `first_compile`), and `pkc home status` reads them back beside a live probe of each.

## 6. Commands

```
pkc setup [--non-interactive --answers <f>]     config.yaml, ports probed, infra up, first library, the two questions
pkc up | down | status                          the machine's middleware and worker; `status` probes every service
pkc home status [--json]                        libraries and registered projects, each probed: infra, key, engine, canonical, skill fresh, steps done
pkc home register <dir> | forget <dir>
pkc library create <name> [--from <name>] [--language …] [--contract <template>]
pkc library ls | show [<name>] | use <name> | bind <name> [<dir>] | unbind [<dir>]
pkc config get|set <key> <value> [--library <name>]   home defaults or a library's choices (semantic_retrieval, backend, embedding)
pkc credentials set KEY [--from-stdin]           writes ~/.pkc/credentials (0600); never echoes
pkc skill install --global --backend codex|claude-code|all    the harness-level skill; `pkc skill render [--library]` the per-library package
pkc console [--port]                             the API and the web console over the home
```

Every other `pkc` command — `ingest`, `draft`, `owner say`, `profile`, `archive`, the
readers — is unchanged and acts on the chosen library. `pkc setup` is the only interactive
command, and only when a terminal is attached; the Steward runs it with `--answers` from what
the Owner said.

## 7. The global skill

`pkc-steward`, installed into `~/.codex/skills/pkc-steward/` or `~/.claude/skills/pkc-steward/`
(marker-stamped, `--force`-guarded, the same installer as the project skill). Catalog-rendered
(`steward.home.*`, en + zh), no contract text. Its sections:

- **Where you are.** `pkc home status` first, always by mechanism rather than by
  instruction: every other `pkc` command refuses with the library list when no library is
  chosen, so a session that skipped the status lands on the refusal.
- **Cold start.** The two questions, and how the Steward answers the first itself: it writes
  the profile from what it already knows of the Owner (`pkc profile set … --provenance
  inferred`) and asks the Owner to correct it, one field at a time; it records the retrieval
  choice the Owner made (`pkc config set semantic_retrieval …` or `pkc credentials set`).
- **Continuing in a library.** Read the library's own package (`pkc library show` names the
  path); from there the round, the door and the postures are the project skill's text,
  rendered per library.
- **What is remembered.** Steps and choices; the Steward does not ask what `home status`
  already answers.

The per-library package under `~/.pkc/libraries/<name>/skill/` is the project skill's
`references/` plus a one-page `SKILL.md` that binds them to the library by name — so the
text a Steward reads inside a library is the same text a project's Steward reads, and
`Executor-Skill` stamps the same hash.

## 8. What the project shape keeps, and what moves

`scaffold/init.py` and the project shape are unchanged in behaviour. Three things move into
the framework package so both shapes share them: the engine and profile templates (the
scaffold reads them from the package instead of its own `templates/`), the compose
generation (ports, project name, data paths — the scaffold's `init.py` already computes
these; it calls the shared function), and the settings assembly's home layer. A scaffold
project may register itself into the home (`pkc home register`) and appears in `home status`
with its own stack probed.

## 9. Invariants

- **I1.** Libraries are tenants; every command resolves one tenant before it runs, and
  refuses rather than defaults. The worker drains per tenant as it always has.
- **I2 / I7.** The home holds no authority and no record: the canonical repository and L0 are
  where they were; the skill packages are derived and re-rendered.
- **I3–I6.** Untouched.
- **Mechanism over persuasion.** "Choose a library first" is a refusal, not a sentence in
  the skill; "do not ask again" is a step recorded by the command that did the work.
- **Secrets.** `credentials` is 0600, outside every git repository (the engine is a
  repository; the home is not), never copied into a library, never in a rendered skill.

## 10. Order of work

1. Settings: the home layer (`PNEUMA_KNOWLEDGE_HOME`, `config.yaml`, `credentials`,
   precedence) and tenant resolution (`--library`, bindings, `current`, the refusal).
2. `pkc library create|ls|show|use|bind`, `library.yaml` with steps and choices; the
   templates moved into the package; `pkc skill render` per library.
3. `pkc up|down|status`, the generated compose, the worker daemon, `pkc home status` probes,
   `pkc home register`.
4. `pkc setup`, `pkc credentials set`, `pkc config get|set`; `semantic_retrieval` as an
   engine knob honoured by intake, index and every lane (coding-agent-mode §5.9).
5. `pkc profile` provenance and the inferred-first flow (coding-agent-mode §5.8).
6. The global skill and its installer; the per-library package.
7. `pkc console`; the scaffold's `init.py` on the shared functions; `home register`.
8. A real cold start on this machine with Codex: from an empty home to a first compile,
   recorded like the acceptance run.

## 11. Boundaries

- One machine. Sharing a home between machines, or a stack between machines, is not designed.
- The home is not a backup: `pkc down` keeps data, but nothing here copies it elsewhere.
- Kimi, the evolve door and single-shot agent roles stay where coding-agent-mode left them.
