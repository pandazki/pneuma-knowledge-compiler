# 所有者、管理代理、访问者——知识库之上的角色

[English](steward-owner-visitor.md) | **简体中文**

## 1. 框架

知识库——[架构](../architecture.zh-CN.md)描述的全部——是程序性的。它的读、写、schema 构建
和演进都是调用，人来调还是 Agent 来调，架构都不变。架构没有命名的是*谁*在调。三个角色，
叠在一个租户的知识库之上：

| 角色 | 做什么 | 看到什么 | 喂给谁 | 未配置时 |
|---|---|---|---|---|
| **Owner（所有者）** | 提供信源、陈述意图、校准（添加、订正、采纳演进） | 全部 | 材料 → 知识 L0；意图 → 契约；每个动作 → 事件 | 租户主体：经 API 的每次写入都是 Owner 的 |
| **Steward（管理代理）** | 编译、起草演进、整理、答复、维护记忆 | Owner 的每个动作；访问者的问询（按级别） | 写入 → 知识库，过与其他写入相同的门禁；记忆 → 路由提示与 evolve 证据 | **空 Steward**：今天的编译模型与 evolve runner，没有记忆 |
| **Visitor（访问者）** | 读 | 知识库，按权限 | 问询 → 事件，按级别 | 每次读都是静默的 |

三条裁定固定了形状：

- **Owner 只通过对 Steward 说话来影响知识库。** Owner 的陈述既是*来源*——像一封邮件一样
  被引用——也是*事件*——像任何事一样被观察。一个动作同时满足"不可编造"（claim 引用该陈述）
  与"Steward 看得到 Owner 做了什么"（陈述在它的事件日志里）。不存在绕过门禁的 Owner 写入
  通道；一次订正是一句陈述，由 Steward 变成 `edit_claim` 或 `supersede_claim`，以该陈述为证据。
- **Steward 的记忆在 Steward 内部，不在知识库里。** 知识库持有知识 L0、正本及其派生物；
  Steward 持有它的事件日志及*由此*派生的东西。依赖单向：Steward → 知识库，知识库永远不读
  Steward 的记忆。记忆是否影响 Steward 怎么编译是 Steward 自己的事，与"它用哪个模型"同类——
  在知识库的归因之外；归因只点名契约、措辞和组件，从未声称能点名模型的方差。
- **契约由 Steward 依 Owner 的意图执笔。** Owner 要改契约，就指示 Steward；指示是事件；采纳
  保持为一个显式动作，因为它触发机械合并。

三个默认叠起来——租户即 Owner、空 Steward、访问者静默——每个接缝都与没有这个概念时字节一致。
这与 schema pack 和索引组件遵守的是同一条纪律：未注册即不存在。

## 2. 两种 L0

知识 L0 是 Owner 放进来的：来源，逐字，按 `source_id + ¶ span` 寻址。正本只从它派生。

**使用侧 L0** 是系统观察到的：一份来源被摄入、一次编译运行、一位访问者提问。这些是
*记录*——保存而非重新推导，也从不是知识的权威。正本不从它派生；Steward 的记忆从它派生。

使用侧的记录是**咨询**：开场记录问题与递交证据，答案到来时再追加答案事件。交接本身就算使用。

## 3. 咨询记录

`ConsultationRecord`（core `domain/consultation.py`）是一个冻结的 dataclass，可表达 `opening`、
`answer` 事件或二者合读的 `complete`。`complete` 不是第三个保留事件：单次应答 lane 一起写入
两个事件，worker 分别投递。`pkc recall --evidence` 在 `business` 或 `audit` 下立即记录开场，
咨询 id 就是 handoff id；`pkc consult answer` 只追加一次答案。handoff 会过期，开场仍保留为
未作答。两个事件都不改写（存储以 `answered_at IS NULL` 为条件，只填入空答案列）。
`silent` 两个事件都不记录。


| 字段 | 含义 |
|---|---|
| `consultation_id`、`user_id`、`created_at` | 身份（系统分配） |
| `lane` | `fast` / `deep` / `briefing_ask` / `direct` |
| `visitor_class` | `silent` / `audit` / `business`（§5） |
| `question`、`as_of` | 问题原文；以及 lane 解析相对时间所用的参照时刻 |
| `library_ref` | **咨询开始时采样到的正本 HEAD**——调用被钉住时则是快照 id，那是同一个字段的精确形态。是采样，不是钉住：证据各面读的是活状态，调用当中它可能越过采样点继续前进（编译在答题中途落地；claim 索引没有版本），所以这个 ref 说的是*读取从哪里开始*，而不是整个答案都出自那一份状态 |
| `evidence_handed` | lane 摆到模型面前的每一个*地址*，除此之外什么都没有：`{kind: claim/window/episode/component/document, ref}`，`ref` 是带页路径的 claim 锚、`source_id ¶a-b` 区间，或一条正本页路径（`document`：lane 整页读过的页）。它既载证据*条目*，也载与条目一同渲染出去的出处区间——一条 claim 笔记会打印自己的 `[cite: …]` 标记，而合约要求模型逐字照抄证据里的这些标记，所以在那里出现过的区间就是模型见过的地址。清单由 lane 在渲染处发布（`recall/fast.py:evidence_manifest`），构造器只是照抄 |
| `answer_kind`、`answer`、`citations` | 回答及可解析地址，每个引用带 `origin: handed` 或 `direct`。模型通道按清单放行；agent 回答还会针对当前租户的 L0 与 canonical 锚点解析直接读取的引用（见下）。模型通道的记录文本去掉无法还原的句柄；agent 回答含无效引用时，在记录前整次拒绝 |
| `citations_direct` | 存储的 origin 为 `direct` 的引用数；交接证据仍严格等于通道交出的内容 |
| `answered_at`、`state` | 答案事件时间；未作答时为 NULL，状态为 `unanswered`，作答后为 `answered` |
| `miss` | 未作答时为 NULL；答案到来后，每条 lane 同一条规则：`answer_kind == "no_record"`，或者什么都没到模型面前（见下） |
| `degraded` | lane 的降级标志，原样复制 |
| `token_usage` | 这次咨询**花掉**了什么：lane 自己的用量映射，按字段顺序存下。只有 token，没有金额——token 数是实际发生的事，永远为真；而价格是一份商业约定，它变的时候不会来问这条记录。所以费用是在有人读取时、用部署当下声明的价格（`MODEL_PRICING`）算出来的；对一个从没被定过价的模型，它是缺席，而不是零 |

记录不含 lane 没有输出过的任何散文。它由 **service** 写入（`infra/schema.sql` 里的
`consultations` 表，adapter 与 `briefings` 并列），core 永远不写——因为记录是 Steward 的，
而 service 就是空 Steward。core 定义类型、事件通道，以及每个 lane 一个纯构造器
（`recall/consultation.py`，与 lane 放在一起而不是与记录放在一起：构造器要读的形状是 lane
的，而 domain → recall 是错的方向）。它没有咨询端口，也不读任何咨询。

**上面那张表是各回答通道的并集，没有哪条 lane 会把它填满：**

- **fast** 全部填满。它的 `citations` 并不是 `FastAnswer` 上的一个字段——那里没有这样一个字段
  ——而是答案自己的引用标记，经 lane 的 `citation_handles` 映射还原；映射里没有的句柄会被丢掉，
  这与 lane 自己的引用过滤是同一条规则。在 `answer_format: structured` 下这些标记是模型声明的
  引用，在 `text` 下是它写进散文里的那些。
- **deep** 不发布 `answer_kind`、不发布降级标志，也没有 episode / component 证据——它的循环会
  跨轮重新检索，所以记录只带 claim 与窗口，那两个缺席的字段保持为空，而不是从文字里猜出来。
  它也不给 source id 起别名，所以它的标记本来就是真的，记下的文本就是调用方收到的文本。
- **briefing_ask** 不发布 `answer_kind`，也不发布降级标志。它的清单是那份冻结的**包**，加上
  `search_knowledge` 在答题中途渲染出去的东西，再加上循环取回的东西：包就是这条 lane 的证据，
  因此把它发布出来，而不是只点名那几次 fetch 就算完。包的那一半是**在包被构建时就记下来**、
  并与包一同存下的（`Briefing.pack_manifest`，即 `briefings.pack_manifest` 列）：每一个被渲染
  的块——claim 笔记、逐字窗口、素材卡、原文摘录——都带着它*据以渲染*的那些地址，以及它在包中的
  字节区间；字符预算截断之后，只有整块存活下来的才进清单。它绝不从渲染出来的文本上读回来：来源
  是别人导入的任意内容，而正文里出现 `[cite: s01 ¶3-4]` 这串字面文字的段落是在*引述*、不是在
  *引用*——解析器分不清渲染器打印的标记与来源恰好含有的标记，分不清的清单就会放行指向从未被检索
  过的证据的引用。在包清单被记录之前存下的简报不带清单，它的提问因此什么都不放行。它的
  `library_ref` 是那份包自己钉住的提交 ref：简报按构造就是钉住的，所以不需要再查一次 HEAD。

**在 agent 执行器下，agent 的阅读就是检索。** 交接清单无法枚举后续的 `canonical read`
与 `source fetch`；无密钥时 glance 选页需要模型，交出的清单甚至可能为空。清单成员关系曾是
「可解析」的替代判据，直接阅读让这个替代不再成立。`pkc consult answer` 逐一解析标记：
若为句柄，先经交接的句柄表还原；否则按真实的 `[cite: <sid> ¶a-b]` 地址或 `c:xxxx` 锚点解析。
来源必须存在于当前租户的 L0，且 `1 <= a <= b <= block count`；锚点必须存在于当前租户的
canonical。清单内的引用（锚相等或区间被包含）保留 `origin: "handed"`；清单外但解析成功的
引用记为 `origin: "direct"`。真实来源上编造的区间以退出码 4 拒绝，点名引用，不写答案事件、不排答案
投影作业，交接保持待答以便纠正回答。`evidence_handed` 不变。

没有交接时，`pkc consult record --question <q> --text-file <f>`（或 `-` 读 stdin）记录回答：
lane 为 `direct`，交接证据为空，所有引用均为直接引用，走相同的解析、fast 记录构造器与
`_spawn_recording` 发出路径。它在记录时采样 `library_ref`，`as_of` 留空，不能重建之前阅读的
快照。两条命令都接受 `--kind no_record`。直接记录默认 `business`，也接受 `audit` 或 `silent`，
记录行与作业的规则与交接回答相同。一个问题，一个 id，两个保留事件：关闭失败后可以纠正回答；重跑 recall
来修复它只会多造一次交接。保留记录不被改写。

**「某样东西在哪」的地图不是证据。** 库**概览**（每一页的路径、标题和一句话定义，fast、deep
与简报包都以它开场）刻意不进任何清单：它是模型据以决定*读什么*的东西，把它算作证据会让每一次
咨询都碰到每一页，而且它根本不带任何引用标记或锚（`canonical_glance` 两样都剥掉）。概览随后
**选中整页读**的那些页则是清单里的 `document` 条目，连同页面正文携带的每一个区间——因为那些页
的文本真的到过模型面前。简报包里某份来源的结构大纲（`- <小节>  ¶a-b`）出局的理由与概览相同。

**`miss` 只在答案存在时计算，对每条 lane 都是同一条规则**：`answer_kind == "no_record"`，或既没有交接证据、也没有可解析的
直接引用——`domain/consultation.py:is_miss(answer_kind, evidence_handed, citations)`。这个判定是机械的，而不是交给
各调用方自行斟酌，因为一切统计「这座库答不上什么」的东西，其真实性都不会超过它。

## 4. 投递，以及组件协议上的两个使用侧接缝

**咨询只被*发出*，绝不在请求路径上被处理。** 路由建好记录、创建一个游离任务就返回；该任务写下
记录行，并在同一个事务里为 `business` 访问者入队一个 `recall_projection` 作业。消费这个作业是
worker 的事，走的是摄入侧早已在排的那条按用户队列。响应——以及流的终帧——什么都不等：不等写入、
不等消费者、也不等一个为二者兜底的超时。代价明说而不藏着：记录是尽力而为的发后不理，进程在答案
与该任务提交之间死掉就把它丢了。它绝不可能付出的代价，是答案。CLI 的显式记录则以 `strict=True` 等待持久化；写入成功后才声明证据已记录，或消耗已回答的 handoff。投影仍只在 worker 上执行。

发出的两半谁也不能单独存在：记录行与作业同事务提交，于是没有作业会点名一条不存在的咨询，也没有
`business` 记录会在无人排队去读它的情况下写下。交接作业携带 `consultation_id` 和 `event`（`opening` 或 `answer`）；单次应答作业保留原来的仅 id 载荷，worker 将合读记录拆为两次事件投递。

- `on_recall(user_id, record)`——`on_source_indexed` 在使用侧的孪生，由 *worker* 在排掉那个作业
  时调用。`notify_recall` 以同样的 fail-soft 规则扇出：组件抛错记日志，绝不让作业失败。只对
  `business` 咨询的每个事件调用；开场不携带答案或 miss 分类。
- `evolve_evidence(user_id) -> str | None`——组件可向 evolve 提案的证据贡献的一段机械文本。
  由 core 汇集各段（`components.collect_evolve_evidence`：每个组件一行标题、逐组件 fail-soft、
  什么都没有时返回 `None`），再由 service 的 evolve runner 把一个
  `demand_evidence: str | None` 交给 `propose_evolution`；human message 只在它不是 `None`
  时多出第四节（I5 成立：系统消息不变）。

`rebuild` 名字不变，多了第二种合法的底（§8）。

## 5. 访问者级别与控制台身份

`/recall` 与 `/briefings/{id}/ask` 上的一个请求字段：`visitor_class`，默认 `silent`。

| 级别 | 请求路径做的事 | 用于 |
|---|---|---|
| `silent` | 什么都不做——没有行，没有作业，连任务都没有 | 评测框架、benchmark、不得留痕的审计员——默认值，因此不带这个字段的调用方字节一致 |
| `audit` | 只写记录行 | 咨询必须可重建、但不得影响 Steward 的调用方 |
| `business` | 记录行 + 投影作业 | 知识库为之存在的人 |

记录与影响是两个轴；轴上要紧的是这三个点，加权留给应用。

**在 Web 控制台上，级别由身份推导而来。**在那里，角色是身份，不是每次请求各选一次的参数：一个顶层
开关——所有者 / 访客 / 无痕访客——同时决定这个应用给你看什么、以及它问出的问题带哪一个级别，问题
旁边不再有任何选择器。所有者是驾驶舱，控制台有的每一个视图都在。访客与无痕访客是阅览室：一个问答
界面，加上只读的正本浏览，此外没有别的。导航与路由都从同一处声明推导
（`apps/web/src/lib/lenses.ts`），因此在访客身份下深链到驾驶舱，落回的是阅览室，而不是那个身份
本就不该拥有的页面。所有者与访客都以 `business` 提问——在这台控制台上问出的问题就是这座库正在被
使用，而没人计数的使用会让这座库把自己报告成无人问津；无痕访客以 `silent` 提问，并且在身份徽标上、
在页面上都把这件事说出来：一个全部意义就在于「什么都不记」的立场，必须让采取它的人看得见。没有
`audit` 身份：审计是 API 调用方的立场，不是坐在控制台前的人。上面那个 `silent` 默认值是 API 的，
面向根本不带这个字段的调用方；控制台总是带上一个。

**于是投影总要滞后于它那次咨询一个队列排空的时间**，而这段滞后诚实的说法就是队列自己的说法：
按用户、FIFO、同一用户同时只有一个作业在飞。闲置的库落后几秒。刚被所有者导入一整批语料的库，
落后的是那位用户那些编译所需的时间——排在它们之后入队的投影，也就在它们之后被认领。任何读账本
的东西都不得假定它说的是最后一个被问出口的问题。

## 6. 访问账本，以及其上的 `attention` 组件

账本是*框架*的，而且内建——它就是队列末端那个默认消费者，对每一条 `business` 咨询都施加，无论
是否注册了任何组件。默认开启，且默认惰性：所有访问者都是 `silent` 时根本没有咨询，于是什么都不
写，每个接缝都与没有这个概念时字节一致。两张派生表（service `access_stats.py`）：

- `recall_access_hits(user_id, target_kind, target_ref, day, hits, last_seen)`——`target_kind`
  为 `claim` / `document` / `source`；每目标每自然日一行，`day` 是事件时刻的 UTC 日期（开场用 `created_at`，答案用 `answered_at`）。
  账本对时区不持任何观点：主体的日历归 `time` 管，而对「这是哪一天」给出第二个答案，
  恰恰就是让两份投影对同一个下午各说各话的原因。行由记录的 `evidence_handed` ∪ `citations`
  写入（被引用的项比仅被递出的项多计一次）；目标按*地址*分派，不按 `kind`——`kind` 说的是 lane
  用哪条路够到了这一项（`component` 同时涵盖路由的 claim 查询与路由的跨度），语法说的才是它是
  什么：`c:xxxx` 是 claim，`<source_id> ¶a-b` 是跨度。一个页面每一趟最多计一次，不管它借出了
  多少条 claim——按 claim 计，一个九条 claim 的页面会比同样被读到的一条 claim 的页面热九倍，
  那量的是篇幅，不是注意力；claim 与来源本身就是条目，照来照计。`last_seen` 是当天最后一条碰到
  该目标的咨询的确切时刻，于是该目标真正的最后访问就是它各行的 MAX——确切的最后访问追踪，落在
  一行本来就要写的行上的一列里，而不是另起一张复述同一件事的表。
- `recall_access_misses(user_id, day, question, count)`——问题按空白归一、封顶 400 字符并标出
  截断，在写入路径上封顶，因为它是这张表的主键。

**访问元数据绝不写进正本文件。** 它住在派生层、以地址为键、在读取时联结——一次读绝不可以变成一次
对权威的写。读面是 `access_stats(user_id, pairs)`，逐目标给出
`{last_accessed_at, hits_7d, hits_30d, heat}`，天然是批量的（单个目标就是只有一项的一页）：
`GET /v1/users/{user_id}/access-stats` 取单个目标，`/access-stats/top` 取窗口内的排行。
`last_accessed_at` 给的是整段历史的答案而不是窗口的：一个四十五天前被读过的页面有真实的最后
访问，也确实没有近期命中。

不存分数。热度在读取时计算：`Σ hits × 0.5^(age_days / half_life)`，`ATTENTION_HALF_LIFE_DAYS`
默认 14。递交地址在开场计权重；引用与落空在答案事件计数。报告在窗口内分别统计开场、递交地址、
答案、引用、落空与未作答咨询；未作答不算落空。

**只有盖过戳的事件才重放**，通过 `list_consultation_events` 按时间排序，同一时刻先开场后答案。
`opening_projected_at` 与答案的 `projected_at` 独立：后来到达的答案仍排队时，重建保留已投影的
开场，把答案交给它自己的投递。每一页折进正在累加的和里随即丢弃，重建的行集原子换入。

**每个 `(consultation_id, event)` 至多施加一次。** 每个事件的增量与自己的戳在同一个事务里
提交；只抢 NULL 戳使重复投递无效。重建不改两个戳或任何保留字段。它持有该用户唯一的在飞作业
认领，因此扫描与换入之间不会插入投影。`scripts/ops/rebuild_derived.py` 仍入队并排掉同一个
`recall_rebuild` 作业。

这个戳*没有*罩住的部分，明说，因为没人能验证的保证比没有保证更糟：进程若死在提交与随后那次组件
扇出之间，那次通知就永远丢了。这是本投递模型选择的「至多一次」这笔交易，用来换掉那种会把每个它
所恢复的计数都翻倍的「至少一次」——而统计，也就是重建能修好的那一半，正是提交的那一半。

**`attention` 组件**是那本账本之上的*各面*，不拥有其中任何一行。它的 `on_recall` 与 `rebuild`
都是明写的空操作：一个也去增量那些表的组件，会在操作者把它打开的那天让每个计数翻倍，而一本
「用量」账本若取决于哪些面被启用，量的就是这套部署而不是读者。取消注册它，统计照样累积；走掉的
只是那些面。

- `evolve_evidence`——按契约族分组的热页；窗口内有 claim 而零命中的族（冷）；高频未命中及计数。
  按字符封顶；缓冲区为空时返回 `None`。「空」是对*表*判定的，不是对「有没有话可说」判定的：
  一座还没被问过的库，按定义就家家族族都是冷的，把它们报出来就是拿证据的缺席造论据，所以冷族
  扫描被挡在「窗口非空」之后。族来自契约，经由一次 service 查询——分组用的是
  `canonical_glance.family_of`，作用在该用户组合出的 `path_templates` 上，由
  `skills.path_templates_for` 解析：`skill_for_user` 的只读兄弟，永不写 manifest、永不调模型，
  像 `user_info` 一样注入。读一个用户的技能是 service 的事，而拿不到的组件照样渲染，只是全归到
  一个未归档组里。
- `recall_tools`——deep lane 的 `attention_report(days)`，同一段文本。
- `fast_paths`——`attention`：最热的 claim 作为带标注的组件面，每条解析到其锚，绝不进 RRF。

## 7. `owner-dialogue/v1`

Owner 的陈述作为一种来源契约（`pneuma.source.owner-dialogue/v1`）：一段对话，若干轮次，
`role: owner | steward`，带时区的时间戳，逐字文本；规范化为每轮一块，claim 引用
`[cite: <sid> ¶n]` 与引用一条聊天消息完全一样。摄入是完整正本处理加完整语义索引。编译任务的
机械来源行写明种类，模型读到一份看起来像转录的材料时，不需要被叮嘱就知道那是一次陈述。
Owner 的陈述*该得到*什么——一次订正、一次取代、一个新页——是契约的判断，本该如此。

由此而来的规则：

- **至少要有一轮是 Owner 自己说的，而且那一轮得真说了话。** 上面的一切都建立在主体亲口说了话
  之上——角色标签、种类行、完整正本处理都由此而来。只有 `steward` 轮次的 payload，是 Steward
  写的关于 Owner 的文档；用这份契约去编译它，等于让 Steward 写的文字成为 Owner 的正本知识。
  而一轮**空白**的 Owner 发言只在形式上满足这条规则，对 payload 的实质毫无改变：说话的仍然
  只有 Steward，空白轮次也成不了任何东西可以引用的块。因此契约要求那一轮 Owner 发言非空白，
  并直接拒绝任一角色的空白轮次——点名是哪一轮、什么角色，而不是悄悄滤掉，因为声明了一轮没人
  说过的话的 payload，它的作者相信着这份契约并不相信的东西。导入表单也在写下一轮非空白的
  Owner 发言之前禁用提交：门禁之前，工具面上的同一条规矩。
- **顺序是被校验的，不是被修正的——这是本契约与 `im/v1` 分道的唯一一处。** 其他契约都会给
  收到的东西排序，因为 provider 归档的顺序是导出的副产物。对话的顺序就是它的内容：一句限定
  前一句的话，两句一换位就不再限定了。`said_at` 倒退的 payload 直接被拒。
- **块上没有放 id 的元数据。** `NormalizedBlock` 只有 `index`、`text`、`section_path`、
  `images`，这是设计如此——因此 `owner_id` / `steward_id` 和 turn id 都留在来源的 `meta`
  信封里，按规范化顺序与块对齐，与 `im/v1` 的 `messages` 信封完全一样。两边都成立的是同一条
  规矩：这些 id 从不进入模型读到的文本，模型看到的是**角色**。
- **契约没有标题，而 `RawSource` 必须有一个。** 对话只带应用自己的 `dialogue_id`，因此存下
  的标题由一个 prompt key（`ingest.owner_dialogue.title`）据它生成，而不是在 core 里内联英文。
  标题不参与 source id 的哈希，所以切换 prompt 语言的部署不会把自己的去重劈成两份。
- **写明种类的那一行是按来源的引言，不是大纲。** `describe_source` 为每份来源生成一句话，
  编译 worker 把它放在那份来源的块之上；大纲是正本的布局，对来源只字不提。这一行只说种类和
  立场——陈述该得到什么被刻意留在外面，因为那是契约的那一半。
- **第五种契约在数据层并非纯增量。** 它自带一个 `SourceKind`（`owner_dialogue`）和一个
  `SourceOrigin`（`console`）；`people` 与 `time` 组件里按 kind 的查表会落到「没有信号」，
  而这正是对的答案——Owner 的陈述在结构上不点名任何第三方。参考契约里点名这一种类的那一句
  在 `v2`，`v1` 保持逐字节不变。

## 8. 对不变量的触碰

I2 与 I7 说投影"从 L0 与正本"可重建。访问账本从咨询重建，咨询两者都不是。成立的读法是：
**投影从其声明的底可重建**，而使用侧记录是一种底——保存而非派生，在 `rebuild_derived` 中
原样存活。权威没有任何移动：咨询不是知识的权威，正本仍只从知识 L0 派生。

其余全部不变：I1（这里每张表、每个方法以 `user_id` 为第一键）、I3、I4（记录里的每个地址都是
同一套寻址）、I5（evolve 的一节在 human message 里且只在非空时出现）、I6（评测框架默认是
`silent` 访问者——泄漏纪律在读侧也有了名字）。

## 9. 边界

框架伸得比机制远，这条界线值得说明。Steward 有事件日志，没有**笔记**——账本之上没有由模型写的
判断层；没有账本垫着的笔记就是自述。记忆只喂路由提示与 evolve 证据，不喂编译。组件没有自己的
HTTP 面；账本经框架自己的路由和脚本读取。访问者级别就是上面三种，不加权；`pinned` 目标是应用的
扩展点，不是框架的一张表。
