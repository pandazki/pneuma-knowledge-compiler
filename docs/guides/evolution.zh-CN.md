# 驱动与评审演进

[English](evolution.md) | **简体中文**

没有哪个领域模型能一直正确。数据在累积、分布在漂移、业务会转向——半年前把一切归对位置的契约，会开始把东西归错。演进就是框架对此的回答：一套基础设施，盯着编译实际发生的样子，在证据足够时起草一个更好的模型，并把改动作为可评审的 diff 摆到你面前。节奏由你驱动；没有你的决定，什么都不会被采纳。

演进的是**模型**——文档族、路径模板、页面怎么切。不演进的是**事实**：已入册的 claim 只会被重新组织，不会被改写；重组中任何会消失的内容，都会在发生之前被点名列给你。

## 1. 演进环一览

```
编译事件累积 ──▶ 触发命中 ──▶ 起草提案
                                  │
              no_change ◀─────────┤ proposed
                  │               ▼
            记录归档，结束   在分支 evolve/<task-id> 上重建文库
                                  │
                                  ▼
                    你来评审：理由 · diff · 被丢弃的锚点
                                  │
                    采纳 ◀────────┴────────▶ 丢弃 / TTL 过期
                      │                          │
              机械对账合入主线                删除分支
```

## 2. 证据与触发

编译器为它新增或修订的每条 claim 记一笔事件。演进的证据是这些事件，不是原始材料：它们显示事实实际落在哪里、哪个族什么都吸、哪个声明了的族一直空着。

一轮提案有两种起法：

- **自动**：某次编译之后，自上一轮以来两个阈值同时越线——足够多的新文档**且**足够多的新 claim（`PNEUMA_KNOWLEDGE_EVOLVE_TRIGGER_TOPIC_DOCS`、`…_NEW_CLAIMS`）。整个行为受总开关 `PNEUMA_KNOWLEDGE_EVOLVE_AUTO_TRIGGER` 控制。
- **手动**：`POST /v1/users/{uid}/evolve`——你已经怀疑模型落后于数据的时候。

一次只飞一轮：已有待评审草稿或在飞任务时，再次请求返回 `409`。先处理桌上的草稿，再要下一轮。

## 3. 提案

给定当前契约、近期事件和现有文库的形状，演进模型产出以下之一：

- **`no_change`** —— 当前模型仍然合身，理由被记录下来。这是一等结果，不是失败：一次讲得清道理的「不用改」，恰恰是你想从评审者——无论机器还是人——那里得到的东西。
- **`proposed`** —— 一份具体的修订：要新增或细化的族、要调整的路径模板、要重组的页面，附带理由。
- 两种中止态（`parse_error`、`invalid_templates`）—— 带原因记录归档；什么都没动。

## 4. 在分支上重建

`proposed` 不止于纸面。框架在专属分支（`evolve/<task-id>`）上按提案的模型重建文库，用的工具面比编译更宽——可以在页面间搬移 claim、可以裁撤页面——主线正本全程不动。

随后演进闸门检查结果。有一条检查和编译不同：锚点连续性是**全库级校验，且缺失不硬拒**。每个将要消失的锚点会成为任务上 `dropped` 清单里的一项。重组有时确实该裁撤内容——但那是你的判断，不是机器的；机器的职责是让这份损失不可能被漏看。

## 5. 评审草稿

一份草稿任务带齐了决定所需的一切：提案与理由、完整的文件 diff（每份改动文档的新旧正文对照）、被丢弃锚点的清单。Web 界面的演化页呈现同样的内容，外加采纳/丢弃两个动作和草稿剩余的存活时间。

真正要判断的，与[写契约](compile-contract.zh-CN.md#5-验收环)是同一把尺：

- **这是对未来使用更优的模型，还是只是一个不同的模型？** 变化不是目标。理由读起来像品味而不像证据（"这十二条 claim 一直落错族"）的，倾向丢弃。
- **先读 dropped 清单。** 里面每一项都是采纳后不复存在的已入册知识。清单为空，其余评审都轻松；清单不空，它就是评审本身。
- **看接缝。** 重组的失败都发生在边界上——原本互相吸事实的那两个族，在 diff 之后应该更可分，而不是更黏。

草稿有存活时间（`PNEUMA_KNOWLEDGE_EVOLVE_DRAFT_TTL_HOURS`，默认 24 小时）：没人评审的草稿会过期作废，而不是作为一个日渐陈旧的分叉一直挂着。

## 6. 采纳与丢弃

**丢弃**：立即删除分支。此外什么都没发生过，也就没有什么需要撤销。

**采纳**：入队一个合并任务，机械对账三方状态——草稿分叉的起点、草稿分支、以及当前主线（评审期间主线可能已经接收了新的编译）。对账不经过 LLM：确定性的、可审计的账目工作，把新模型和重组后的页面带上主线、重建派生层，并在任务上同时记下采纳前后两个版本。对账无法安全推进时，任务留在草稿态、任务记录原因——一次采纳要么干净落地，要么不落地。

采纳之后，往后的编译按新模型归档。已记录的内容一个字没改写；采纳点之前的历史读起来与从前完全一样。

## 7. 策略，不是硬约束

上面这套生命周期，在安全底线之上全部是**策略，软的**。框架硬保证的只有安全底线本身：一次只飞一轮、损失点名列出、采纳走机械对账、已记录的事实永不改写。生命周期怎么呼吸，由业务定。有的业务选择在草稿评审期间暂停主线写入——基座冻住，三方对账退化为平凡情形，迁移难度降到最低；有的让编译照常流入，接受对账多做些工作。数据稀疏的部署把草稿存活时间放宽到一周也正常；数据密集的则收紧 TTL、调高触发阈值，让演进只在真有话说的时候开口。

| 配置 | 默认 | 含义 |
|---|---|---|
| `PNEUMA_KNOWLEDGE_EVOLVE_AUTO_TRIGGER` | `true` | 编译驱动触发的总开关 |
| `PNEUMA_KNOWLEDGE_EVOLVE_TRIGGER_TOPIC_DOCS` | `5` | 自上一轮以来的新文档数（与下一条同时满足） |
| `PNEUMA_KNOWLEDGE_EVOLVE_TRIGGER_NEW_CLAIMS` | `30` | 自上一轮以来的新 claim 数 |
| `PNEUMA_KNOWLEDGE_EVOLVE_DRAFT_TTL_HOURS` | `24` | 草稿存活时长，过期惰性作废 |
| `PNEUMA_KNOWLEDGE_LLM_MODEL_EVOLVE` | — | 提案与重建用的模型角色；缺省回退到编译角色 |
