# OPC 84 天工作生活实验：阶段验收与夜间审查

日期：2026-07-29

实验用户：`u-opc-ninghe`（沈砚）

实验项目：RelayForge / Cedar

真实模型：OpenRouter 上配置的外部推理模型（公开产物已脱敏具体私有路由名）

结论：**编译、引用、噪声防泄漏和三路投影已经达到可演示状态；带时间语义的检索仍是当前最主要瓶颈。**

## 1. 为什么做这轮实验

这轮实验不是继续扩充几条“看起来像工作”的干净 mock，而是建立一个新的 OPC 用户，连续模拟十二周真实工作与个人生活材料，然后按时间逐批导入、编译、检索和回放。

语料结构参考了 Zoom 会议转录、Slack 导出、RFC 822 邮件、Obsidian vault，以及本地 `/Users/pandazki/Tmp/obsidian-playground` 中测试 vault 的目录、frontmatter、wikilink 与附件组织方式。具体研究来源和结构推导见[研究记录](opc-84d-research.md)。

验收关注五件事：

1. 四种正式 source contract 能否共同表达一个持续演进的 OPC 工作世界；
2. 超过一半的自然噪声能否被过滤，而不是被编译成“知识”；
3. 决定、承诺、限制和已经失效的旧设想能否保持正确状态；
4. 所有结论能否回放到真实原文；
5. 98 个来源、531 条 claim 进入系统后，API 和前端是否仍可使用。

## 2. 人物、主线与支线

沈砚是一名独立开发者，独自研发和运营 RelayForge。产品面向十人以内的咨询与产品工作室，核心价值不是生成更长的摘要，而是把散落在会议、文档、IM 和邮件中的决定、承诺与限制编译成可追溯知识。

### 4.1 可重复的脚本控制组

同一份确定性语料先跑完整基线，再跑增量控制：

| 模式 | 总耗时 | 最终来源 | Jobs | 文档 | Claims | Snapshots |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

| 增量脚本控制 | 21.4480s | 98 | 196 | 62 | 240 | 62 |

增量控制相对全量基线缩短 **71.58%**；最终状态完全一致。该组使用确定性模型，作用是验证编排与增量策略，不用于代表真实模型的知识质量。

## 5. 知识质量与噪声过滤

| 维度 | 结果 | 判断 |
| --- | ---: | --- |
| PostgreSQL / Meilisearch / Qdrant 一致性 | 531 / 531 / 531 | 通过 |
| Truth recall | 100 / 108，92.59% | 通过，仍有 8 条低于保守阈值 |
| Durable facts | 32 / 36，88.89% | 可提升 |
| Decisions | 21 / 24，87.50% | 可提升 |
| Commitments | 24 / 24，100% | 通过 |
| Constraints | 23 / 24，95.83% | 通过 |
| 负例未加限定泄漏 | 0 / 36 | 通过 |
| 旧决定被正确替代 | 11 / 12，91.67% | 通过 |
| Claim 引用覆盖 | 531 / 531，100% | 通过 |
| Locator 原文回放 | 754 / 754，100% | 通过 |
| 引用语义支持 | 508 / 531，95.67% | 通过 |
| 精确重复 excess | 16 / 531，3.01% | 可优化 |
| 有限 truth-set precision proxy | 291 / 531，54.80% | 仅作代理指标 |

`precision proxy` 不是实际 precision：truth manifest 只标注了 108 条核心真值，因此许多有引用、但不在真值集中的有效事实和谨慎限定句也会被算作 unmatched。该指标适合观察趋势，不能单独作为删除 claim 的依据。

原始字符中 88.66% 被标为噪声，最终 531 条 claim 中只发现一条直接提及常见自动噪声（Dependabot），而且它被明确限定为“不等于已合并或已发布”。另有 180 条 claim 带“待确认、未核验、不能据此、尚未”等限定语。这说明系统目前更偏向谨慎保留证据边界，而不是把不确定信息静默升级成事实。

结论是：**噪声没有大规模泄漏成确定知识，安全性成立；但 canonical 仍有 3.01% 精确重复和一定程度的谨慎冗长。**

## 6. 检索是当前最明显短板

检索评估结果：

| 指标 | 结果 |
| --- | ---: |
| 预期真值召回 | 28 / 84，33.33% |
| 完整成功 query | 5 / 36，13.89% |
| 当前态 query | 1 / 24 |
| 历史 query | 4 / 12 |

主要失败集中在十二个阶段重复出现的“本周确认了什么”之类问题。当前 L3 检索面向 HEAD 索引，API 没有 snapshot selector，也没有把 `as_of` 和阶段上下文变成有效的检索过滤条件。因此相同客户、相同“本周”表达会召回其他阶段的高相似 claim。

这不是通过调低阈值可以解决的问题。下一轮应优先：

1. 给 retrieval contract 增加明确的 `as_of` / snapshot 语义；
2. 将相对时间标准化为绝对时间区间；
3. 在 claim projection 中保留来源发生时间和有效时间；
4. query planning 先做实体、阶段与时间消歧，再进入 lexical/vector 融合；
5. 分开评估 HEAD 当前态问答与历史快照问答。

## 7. 真实功能链路

浏览器内完成了三条真实模型链路：

- Recall：查询 Cedar 当前范围、成功指标和自动通知边界，返回 20 个 L1/L2 结果，约 1.51s；
- Briefing + Ask：基于一场真实长会议构建 5,067 字 briefing，生成 40 条 claim；问答耗时约 41.45s，返回 17 个可点击引用，并正确区分当前决定、已失效设想和证据不足事项；
- Live Context：输入三段连续工作流文本，约 16.34s 返回 2 条高置信建议，没有解析、重复、无引用、低置信或超额丢弃。

Ask 回答曾把模型 Markdown 的 `##` 和 `>` 原样展示。现已改为安全 Markdown 渲染，同时保留私有 citation link 到可点击脚注，普通链接继续使用受控 URL 转换。

## 8. 规模化前端审查与修复

本轮用 Impeccable 的界面审查框架检查了信息密度、控制数量、主题一致性、焦点负担和长列表退化，并据此完成三项主要修复：

| 页面 | 修复前 | 修复后 |
| --- | --- | --- |
| Ask 来源选择 | 829 DOM / 120 focusables / 6,545px 高 | 268 DOM / 38 focusables / 1,465px 高 |
| Graph | 2,575 DOM / 460 focusables / 108 节点 + 332 边 | 363 DOM / 45 focusables / 9 节点 + 8 边 |
| Ask 回答 | 原始 Markdown 标记直接可见 | 标题、引用、强调和 citation 脚注正确渲染 |

Ask 来源改成服务端分页、搜索、类型筛选和跨页选择；Graph 默认聚焦可读 hub，只渲染确定性的可见邻域，而不是把 108 个节点全部压进画布。

人工界面健康度按本轮实际证据评为 **17/20**：

- Accessibility：3/4。主要交互使用语义控件且可键盘聚焦，但未完成自动 WCAG 审计；
- Performance：4/4。Ask 与 Graph 的主要规模退化已经消除；
- Responsive：2/4。已有响应式 CSS 和生产构建证据，但浏览器控制器无法切换到 390px 视口，本轮不伪造移动端运行结论；
- Theming：4/4。浅色、深色全流程均通过；
- Anti-patterns：4/4。未发现新的原生 select 依赖、横向溢出或 Markdown 注入式渲染。

## 10. 本轮发现并修复的问题

1. **Citation source ID 被模型截短。** 三处引用把 32 位 source ID 缩短为唯一前缀。现在只允许在同一用户完整来源清单中进行唯一前缀恢复；未知或歧义前缀保持失败，gate 两轮都会重新验证。
2. **旧 canonical 格式残留。** 修复 heading/citation 标记后重新投影，并确认所有索引一致。
3. **评估器漏识别限定语。** 补充“待确认、未核验、不能据此、尚未有”等标记，避免把安全限定误报成泄漏。
4. **Ask source picker 无法承受近百来源。** 改为服务端分页、搜索、类型筛选和跨页选择。
5. **Graph 全量渲染不可读。** 改为可读邻域和有界节点集。
6. **真实回答 Markdown 展示错误。** 改为安全 Markdown + citation footnote。
7. **合成时间文本有歧义。** “每周三十五点”已在生成器修正为“每周三 15:00”。历史实验保留原文，真实 Ask 正确把旧文本标为需核实。

## 11. 仍需保留的问题

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0/P1 | 检索没有可靠的阶段与 `as_of` 语义 | “本周”类问题跨阶段串召回 |
| P2 | 超长会议 source reader 未折叠或虚拟化 | 最长页 11,104px、1,025+ DOM |
| P2 | 长时间后台编译时 Sources 计数不会主动刷新 | 切换用户或路由后恢复，状态不丢失 |
| P2 | 未取得真实 390px 浏览器运行证据 | 只能确认桌面和响应式实现，不能宣称移动端验收 |
| 评估限制 | precision 使用有限 truth-set proxy | 有用但未标注的 claim 会被记为 unmatched |

## 14. 最终判断

在 84 天、144 个事件、98 个来源和 88.66% 噪声字符的条件下，系统能够把四类异构原料编译成 531 条三路一致、全部带引用、全部可回放的 claim；负例未发生无保护泄漏，真实 Ask 和 Live Context 也能给出带原文证据的结果。

因此，当前架构的**编译与证据链是成立的，噪声过滤总体安全，前端在百来源规模下可演示**。下一阶段不应继续增加更多漂亮 mock，而应集中解决时间化检索、阶段消歧和历史 snapshot query，使“当前有效状态”和“某个历史时点的状态”都能稳定召回。
